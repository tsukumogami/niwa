# Lead: What exactly is the "second scope" that row 18's declaration comment names, and how do the payload layout and the skills layout relate?

## Findings

**What a payload layout is.** `payloadLayout` (`internal/agentplan/payload.go:275-321`) describes one agent's *generated configuration document* — for Claude, `.mcp.json`; for Codex, `.codex/config.toml` carrying MCP servers, `shell_environment_policy`, `approval_policy`, `sandbox_mode`, and `project_doc_max_bytes` in one file (`payloadLayouts`, `payload.go:352-368`). Each entry's `scope PayloadScope` field says which single tree that document is written into: Claude's row is `PayloadAtInstanceRoot`, Codex's is `PayloadInRepo`. `PayloadPlan` (`payload.go:442-459`) enforces it with `layout.scope != in.Scope` → empty plan, silently. `PayloadProbeSpec` (`payload.go:412-421`) is the pre-write probe for the ownership rule (a file in a tree niwa doesn't own must be free or carry niwa's marker); it also short-circuits on `layout.scope != scope`. `internal/workspace/apply.go:1723-1755` calls `InstallPayloadConfig` twice per agent, once with `Scope: PayloadAtInstanceRoot, Dir: instanceRoot` and once per repo with `Scope: PayloadInRepo`. For Codex this means the instance-root call reaches `PayloadPlan`, fails the scope match, and writes nothing — confirmed by `payload_test.go:114-117` (Claude: root yes/repo no; Codex: repo yes/root no).

**Skills layout is a different, unrelated table with no scope concept at all.** `skillsLayouts` (`internal/agentplan/skills.go:87-89`) maps agent → path segments (`.codex/skills` for Codex, nothing for Claude), with no `scope` field. `skillsDir(dir)` (`skills.go:103-109`) just joins that layout onto whatever `dir` the caller passes — it has no opinion about whether `dir` is a repo or the instance root. `SkillsPlan` (`skills.go:122-154`) gates on `p.delivers(PluginSkills)` (capability row 5) and, for each configured plugin, declares an `OpDeliverTree` entry at `<dir>/.codex/skills/<plugin>`. It is called from exactly one place, `InstallRepoSkills` (`internal/workspace/pluginskills.go:482-511`), which in turn is called only from `apply.go:1659` (once per classified repo) and `worktree_content.go:590` (once per worktree). **Neither payload.go nor skills.go calls into the other; the two are mechanically independent.** `SkillsInputs.Dir`'s doc comment (`skills.go:69-71`) even documents the restriction as "a cloned repository, or a worktree of one" — instance root is outside its documented contract, though nothing in `skillsDir` enforces that; it is a doc-only limit, not a code gate.

**`RootProjectSkills` (row 18) is wired nowhere.** A search for `RootProjectSkills` across `internal/` turns up only the capability constant (`capability.go:110-112`), its catalog row (`capability.go:190`), its gap-list one-liner (`gaplist.go:85`), its two declaration rows (`declaration.go:282,296-302`), and two read sites: `internal/cli/dispatch.go:402` (a warning check) and its test. No producer method anywhere calls `p.delivers(RootProjectSkills)`. `SkillsPlan` gates on `PluginSkills`, not `RootProjectSkills` — those are two distinct capability constants (row 5 vs row 18), independently declared: Claude has both `StateImplemented` (row 5 via its own plugin system + marketplace registration, per `skills.go:84-86`; row 18 the same way, since registration reaches a root session too). Codex has row 5 `StateImplemented` and row 18 `StateUnavailable/ReasonNotBuilt` (`declaration.go:294-302`).

**A crucial detail the lead's framing undersells: `SkillsPlan`, unmodified, already computes the right path for the instance root.** Since `skillsLayouts`/`skillsDir` have no scope check, calling `producer.SkillsPlan(SkillsInputs{Dir: instanceRoot, Plugins: pluginTrees})` today would compute `<instanceRoot>/.codex/skills/<plugin>` correctly and declare working `OpDeliverTree` entries — gated on `PluginSkills`, which is already `StateImplemented` for Codex. The only reason instance-root skills delivery doesn't happen today is that **no caller passes `Dir: instanceRoot`** — `apply.go`'s Step 6.2 only loops over `classified` repos. There is no missing mechanism in `skills.go`; there is a missing call site plus a missing capability-gate distinction (see Implications).

## Implications

**To the load-bearing question — payload table, skills table, or both — the answer is: neither, as literally read.** Widening `payloadLayouts[agent.AgentCodex]` to also carry `PayloadAtInstanceRoot` would make niwa write `.codex/config.toml` (MCP servers, env, posture, doc budget) at the instance root. That is a real, useful change, but it delivers MCP/env/posture at root — not skills. It doesn't touch `skillsLayouts`/`SkillsPlan`/`InstallRepoSkills` at all, so it would not, by itself, deliver row 18. Conversely, `skillsLayouts` needs zero changes — its lack of a scope field is not the gap.

**What the change actually requires:**
1. A gate distinguishing row 18 from row 5, so a workspace's PluginSkills-at-repos and RootProjectSkills-at-root remain independently switchable in the declaration table (as they already are declared to be) rather than one silently riding the other's gate. Concretely: a new producer method — e.g. `RootSkillsPlan(in SkillsInputs) (*Plan, error)` — that calls `p.delivers(RootProjectSkills)` instead of `p.delivers(PluginSkills)`, and otherwise reuses `skillsDir`/`skillsLayout` verbatim (they're already dir-agnostic).
2. A new call site in `internal/workspace/apply.go`'s Step 6.2 (and a corresponding `InstallRepoSkills`-style wrapper, maybe `InstallRootSkills`) invoked once with `Dir: instanceRoot`, alongside — not replacing — the existing per-repo loop. This mirrors the exact idiom `InstallPayloadConfig` already uses: same producer method family, one call at root scope, one call per repo at repo scope (`apply.go:1723` vs `apply.go:1747`).
3. Flipping row 18's Codex declaration in `declaration.go:296-302` from `StateUnavailable/ReasonNotBuilt` to `StateImplemented` once the above ships.

**Existing tests affected:**
- `payload_test.go:114-117` (the scope-support truth table) is untouched by a skills-only fix — it only changes if `payloadLayouts` is widened, which is a separate, unneeded change for this lead's problem.
- `skills_test.go` (`TestSkillsPlanDeliversOneTreePerPlugin` and friends) stay as-is for `SkillsPlan`; a new `TestRootSkillsPlan...` suite would newly apply, exercising the same path-shape assertions against `p.delivers(RootProjectSkills)` and `Dir: instanceRoot`.
- `internal/cli/dispatch_contract_test.go:305` and `dispatch.go:402`'s warning need updating once row 18 flips to `StateImplemented` for Codex — the warning text explicitly says "none of the workspace's skills, MCP servers or posture" reach a root worker; if only skills are fixed, that warning becomes partially wrong and needs rewording (see Surprises).
- A structural/contract test likely exists asserting every `StateImplemented` row has a producer path exercising its capability constant (worth checking `contract_test.go`) — flipping row 18 without wiring `p.delivers(RootProjectSkills)` anywhere would leave that gate looking exercised in the declaration table but genuinely dead in code, which is the current state and is likely already a latent contract-test gap or an untested `Lookup` row.

## Surprises

1. **The row 18 comment's mechanism claim is imprecise/misleading when read literally.** `declaration.go:290-296` says delivering row 18 "means giving the Codex payload layout a second scope." Read literally against the code, that sentence is about `payloadLayouts` (MCP/env/posture/budget), a different producer path than the one that actually needs to change (`skillsLayouts`/`SkillsPlan`). It's not wrong in spirit — see next point — but as a pointer to "where in the code to make the change" it sends a reader to the wrong file for a skills-only fix.

2. **`dispatch.go:388-403`'s comment reveals row 18 is being used as a stand-in for a *bundle* wider than its own name.** It says row 18 is "the closest thing the table has to" a declaration for "delivered in a repository, not at the root," and that the warning text stays custom-written "because what is missing is wider than skills." So the `RootProjectSkills` capability's literal scope (per its doc comment and gap-list line, "Instance-root skills such as `/dispatch`") is narrower than how it's actually being used as a proxy signal elsewhere in the codebase. This is likely *why* the declaration.go comment reaches for "the payload layout" — the author was thinking of the whole root-project-layer gap (which does include the payload table) even though only the skills half is what row 18 formally names. Worth flagging to whoever scopes the fix: fixing only skills closes row 18 by the letter of its declared capability, but leaves the dispatch.go warning's literal claim (which also promises MCP servers and posture) still true and still firing.

3. **The codebase has two different precedents for "one capability at two scopes," and they diverge exactly along the lines the lead asked about.** Orientation capabilities split by scope as *separate capability constants with separate producer methods*: `RootContextPlan`/`RootSessionOrientation` (`context.go:140`) vs `RepoContextPlan`/`RepoOrientationDoc` (`context.go:304`) vs `GroupContextPlan`/`WorkspaceOrientation` (`context.go:210`) vs `WorktreeContextPlan`/`WorktreeOrientationDoc` (`context.go:506`) — four methods, four capabilities, one shared low-level path helper split into `rootContextPath` vs `localContextPath`. Row 5 (`PluginSkills`) vs row 18 (`RootProjectSkills`) already follows this exact pattern at the *declaration* level — they're declared as two independent capabilities, the same way orientation is four. Payload capabilities (`MCPServers`/`SessionEnvironment`/`ApprovalPosture`, rows 8/9/12) instead use *one* capability constant with an internal `scope`-keyed layout table, silently producing nothing outside the matched scope — and, notably, the declaration table doesn't reflect that restriction at all: rows 8/9/12 are declared unconditionally `StateImplemented` for Codex with no scope caveat, even though `PayloadPlan` only ever fires in-repo for Codex. So adding a `scope` field to `SkillsInputs`/`skillsLayouts` to mimic `payloadLayout`'s pattern would introduce a *second, divergent* mechanism for the same repo/root distinction the capability table already expresses via row 5 vs row 18 — and would blur the same distinction the payload table's silent scope-gate has already blurred once (undeclared root-scope gap for rows 8/9/12). The precedent argues for a second producer method (`RootSkillsPlan`), not a scope field.

## Open Questions

- Should fixing row 18 also flip the Codex payload layout to `PayloadAtInstanceRoot` (delivering MCP/env/posture at root), given `dispatch.go`'s warning already promises all three and only skills is this lead's literal scope? That's a larger, separate decision (a new project-layer document at an instance root niwa didn't previously write there, per the "Widening this scope is therefore a decision about what niwa writes outside an instance" note at `payload.go:349-351`).
- Is there a structural/contract test asserting every `StateImplemented` declaration row has a live `delivers()` call site backing it? If so, it currently either doesn't cover row 18 (because row 18 is `StateUnavailable` for Codex) or would need to gain coverage the moment row 18 flips.
- Does `internal/cli/dispatch.go`'s warning need to be split into two — one for skills (closed once row 18 ships), one for MCP/posture (stays open until the payload scope widens) — or is a partial fix (skills only) acceptable with the warning text edited to stop overclaiming?

## Summary
The row 18 declaration comment's "second scope" language points at `payloadLayouts` (`internal/agentplan/payload.go`), but that table only governs Codex's `.codex/config.toml` (MCP/env/posture/budget) and is mechanically unrelated to skills delivery. `skillsLayouts`/`SkillsPlan` (`internal/agentplan/skills.go`) already compute the correct instance-root path with zero code changes — the actual gap is a missing call site (`apply.go` never calls skills delivery with `Dir: instanceRoot`) and a missing capability-gate split (`SkillsPlan` gates on `PluginSkills`, row 5, not `RootProjectSkills`, row 18), which existing precedent (`RootContextPlan` vs `RepoContextPlan` in `context.go`) says should be a new sibling producer method rather than a scope field bolted onto `SkillsInputs`.
