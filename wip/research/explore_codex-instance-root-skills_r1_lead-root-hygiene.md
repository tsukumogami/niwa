# Lead: What cleanup, tracking and hygiene obligations attach to a niwa-written directory at the workspace instance root?

## Findings

### 1. What niwa writes at the instance root today, and what tracks each write

`Apply`/`Create` in `internal/workspace/apply.go` write several things directly at `instanceRoot` (as opposed to inside a cloned repo under it):

- **`.gitignore`** — `EnsureInstanceGitignore(instanceRoot, ...)` (`internal/workspace/apply.go:446`, `:622`). Idempotently created/appended, never removed, never hashed. See finding 2 below (`internal/workspace/gitignore.go:42`).
- **`.niwa/instance.json`** (`StateDir`/`StateFile`, `internal/workspace/state.go:26-35`) — the instance state file itself: `SaveState(instanceRoot, state)` at `apply.go:564`, `:768`. This is the record that holds `ManagedFiles`, not a managed file itself.
- **Context documents** — `InstallWorkspaceContext(effectiveCfg, classified, instanceRoot)` (`apply.go:1559`), one per agent, written to the agent's own root filename (e.g. `CLAUDE.md`, `AGENTS.md`).
- **`.claude/settings.json`** at the instance root — `InstallWorkspaceRootSettings(effectiveCfg, configDir, instanceRoot, repoIndex)` (`apply.go:1578`). (Note the naming trap called out at `internal/workspace/root_materializer.go:107-109`: despite the "WorkspaceRoot" name, this function targets the **instance** root; `MaterializeWorkspaceRoot` in `root_materializer.go` is the *true* workspace root, one level up.)
- **`.mcp.json`**/overlay Claude content — `InstallOverlayClaudeContent(overlayDir, instanceRoot)` (`apply.go:1569`), `InstallGlobalClaudeContent` (`apply.go:1603`).
- **`[instance.files]` verbatim files** — sourced from `MergeInstanceOverrides(cfg).InstanceFiles`, materialized via `materializeVerbatimFiles` and reported through the same `writtenFiles`/managed-file pipeline as everything else (`apply.go:1682` builds `mcpDestinations` from `Files, InstanceFiles, RootFiles`).
- **Directory-trust entries** are the one exception that writes *outside* the instance root, into the developer's own agent config; not relevant here.

All of the above except `.gitignore` and `instance.json` itself feed into `managedFiles` (per-file, content-hashed) and get cleaned by `cleanRemovedFiles` (`apply.go:2185-2208`) on the next apply if their config entry disappears. This is confirmed by `docs/guides/file-distribution.md:76-78`: "**Instance-root files** (`[instance.files]`) are recorded as niwa-managed, so drift detection and cleanup apply."

**Correction to the framing in the task brief:** the instance root is *not* untracked territory today. It has a real managed-file record (see finding 2) covering every plain file niwa writes there. What it lacks is coverage for *directory trees* — which is exactly the gap a `.codex/skills/<plugin>/` delivery would hit, and exactly why `SkillsReconcileSpec` exists as a parallel, non-hash-based tracking mechanism (finding 3).

### 2. The managed-file model, precisely

- **Record**: `InstanceState.ManagedFiles []ManagedFile` (`internal/workspace/state.go:130`), persisted in `<instanceRoot>/.niwa/instance.json` (`StateDir = ".niwa"`, `StateFile = "instance.json"`, `state.go:26,33`).
- **What one entry holds**: `ManagedFile{Path, ContentHash, Generated, Sources, SourceFingerprint}`, built by `hashManagedFile` (`apply.go:2075-2091`), which calls `HashFile(path)` — a whole-file content hash (sha256, per the package import at `state.go:5`). It is a **flat file hash**, one entry per file path.
- **How staleness is removed**: on the next apply, `cleanRemovedFiles(existingState, result)` (`apply.go:2185`) diffs `existingState.ManagedFiles` against the paths this run actually wrote (`result.managedFiles`). Anything in the old record but not the new run's output is `os.Remove`'d, except paths this run explicitly refused to touch (`exempt`, e.g. because the file turned out to be the repo's own — `apply.go:2192-2199`).
- **Why a delivered skills tree is excluded from it**: `hashManagedFile`/`HashFile` operate on a single regular file's bytes. A plugin skills delivery is either a **symlink to a directory** (fast path) or a **copied directory tree** (fallback) — neither has meaningful "content bytes" to hash, and a directory can't be diffed the same way. `internal/agentplan/skills.go:114-118` states this explicitly: "The managed-file record hashes the file it records, and neither a symlink to a directory nor a directory is something it can hash; the set is reconciled against the configured plugins instead" — which is what `SkillsReconcileSpec` is for.

### 3. The skills reconcile model (`SkillsReconcileSpec` / `reconcileSkillsDir`)

- `Producer.SkillsReconcileSpec(in)` (`internal/agentplan/skills.go:184-201`) returns `{Dir, Keep []string, Marker string}`: `Dir` is the absolute skills directory (empty if the agent takes no delivered trees); `Keep` is the set of plugin names that belong there *this apply* (derived from `in.Plugins`, i.e. the currently configured plugins); `Marker` is `generationMarker`, the sentinel line written inside `TreeMarkerFileName()` (`.niwa-delivered-tree`, `skills.go:37`) for copied (non-symlink) deliveries.
- **A closed gate reconciles nothing** — `skills.go:192-196`: if `p.gateClosed`, the function returns a zero spec (empty `Dir`), so `reconcileSkillsDir` no-ops. This is deliberate: a closed gate stops new delivery but must not turn into "delete everything the last open-gated apply delivered."
- `reconcileSkillsDir` (`internal/workspace/pluginskills.go:522-559`) reads `spec.Dir`, and for every entry **not** in `Keep`: if it's a symlink, or a directory carrying the marker (`treeCopyIsNiwas`), it's `os.RemoveAll`'d as a de-configured delivery. Anything else (an entry niwa didn't recognize as its own) is left alone and reported as a warning.
- **Would this model work unchanged at the instance root?** Structurally yes — nothing in `SkillsReconcileSpec`/`reconcileSkillsDir`/`SkillsPlan` assumes a repo. `Producer.skillsDir(dir)` (`internal/agentplan/skills.go:101-108`) just joins `dir` + the agent's layout segments (`.codex/skills` for Codex, `skills.go:88-90`); `dir` is passed in as `SkillsInputs.Dir` by the caller and today that's always a repo/worktree path (`InstallRepoSkills(repoDir, ...)` at `apply.go:1659` and `worktree_content.go:590`), but the function has no repo-specific logic — no git calls, no `.git` lookups. The one caveat is `SkillsPlan`'s `ExcludeAs: excludePattern(in.Dir, path)` (`skills.go:145`), which produces a git-exclude pattern regardless of whether the target directory is a repo; that pattern is only *consumed* by the git-exclude step (finding 5), which itself degrades cleanly on a non-repo tree. So the reconcile/delivery logic itself is repo-agnostic; only its *downstream consumer* (git-exclude bookkeeping) needs to be checked for repo-ness, which it already handles.

### 4. Instance teardown

- `DestroyInstance(dir, ...)` (`internal/workspace/destroy.go:162-175`) does `os.RemoveAll(dir)` on the **entire instance directory** — a single directory-tree removal, not a file-by-file walk of the managed-file record or the skills reconcile Keep set.
- `DestroyWorkspace` (`internal/workspace/destroy_workspace.go:48-49,95,102`) does the same for every instance (`RemoveAll(instanceDir)`) and then the workspace root itself.
- **Consequence for root-tree cleanup**: teardown makes it moot. Whatever niwa wrote at the instance root — tracked (managed-file) or untracked (a `.codex/skills/<plugin>` symlink or copy) — disappears in the same `RemoveAll` as everything else in the instance, including the cloned repos. The managed-file record and `SkillsReconcileSpec` only matter for *live* instances across repeated `niwa apply` runs (de-configuring a plugin, or removing a `[instance.files]` entry, without destroying the instance); they are irrelevant to instance destruction itself.
- `docs/guides/ephemeral-session-instances.md:163` confirms teardown is "delete-only," driven by the reaper (`niwa reap`), which force-destroys via the same `DestroyInstance` path once a session's `~/.claude/jobs/<id>/` entry is gone and its instance is confirmed `ephemeral: true` and not live (`ephemeral-session-instances.md:187-233`). `niwa reap` never selectively removes files — it destroys or it doesn't touch the instance at all.

### 5. Git-exclude bookkeeping (row 24) and non-git targets

- `internal/gitexclude/exclude.go` — `EnsureRepoExclude(tree, extraPatterns...)` calls `gitCommonDir(tree)`, which runs `git -C tree rev-parse --git-common-dir`. If git reports "not a git repository" (`errNotGitRepo`), `EnsureRepoExclude` returns `nil` — **a silent no-op**, documented explicitly: "A tree that is not a git repository at all is a silent no-op: there is no git status to pollute" (`exclude.go:44-46`). It does not error and does not degrade into writing anywhere else.
- This is called today only against `repoDir` (`apply.go:1862-1871`, inside the per-repo materializer loop) — never against `instanceRoot`. So today the question "what happens when the target has no `.git`" is answered but untested against the instance root specifically; the no-op behavior would apply the same way if a caller passed `instanceRoot` **and `instanceRoot` truly has no enclosing git repo**. See finding 6 for the caveat.
- **Conclusion for a root delivery**: `GitExcludeBookkeeping` degrades cleanly (no error) rather than needing to be explicitly suppressed — *provided* the instance root is genuinely outside any git working tree. It is not something a root skills delivery needs to special-case to avoid a crash; the risk is the opposite direction (finding 6).

### 6. Is the instance root ever inside a git repository?

- `git rev-parse --git-common-dir` **searches upward** through parent directories for an enclosing `.git`, exactly like any other git command run from a subdirectory. `gitCommonDir` (`internal/gitexclude/exclude.go`, the `gitCommonDir` helper near the bottom of the file) does not restrict the search to `tree` itself.
- `internal/workspace/gitignore.go:32-34` states this is an expected real-world case, not a hypothetical: "The instance root is a non-git directory itself, but users frequently place it inside a larger tracked working tree; the `.gitignore` at the instance root lets those outer repositories inherit the exclusions." `internal/agentplan/sessionenv.go:151-160` repeats the same point for `InstanceExcludePatterns`.
- **Consequence**: if `EnsureRepoExclude(instanceRoot, ...)` (or any `gitCommonDir`-based call) were ever run against an instance root nested inside an outer tracked repo, it would **not** no-op — it would resolve to the *outer* repo's `.git/info/exclude` and write niwa's exclude block there, scoped by plain glob patterns (`*.local*`, `.niwa/`, plus whatever extras) with no path restriction to the instance subdirectory. That's a wider blast radius than intended: the outer repo's exclude file would gain patterns that match anywhere in *its* tree, not just under the nested instance. This is presumably why niwa already ships the plain, non-git `.gitignore`-at-instance-root mechanism (finding 2/7) as the way outer-repo coverage is achieved *deliberately and narrowly*, rather than by pointing `EnsureRepoExclude` at the instance root.
- **Implication for root skills**: a `.codex/skills/<plugin>` delivery at the instance root should **not** reuse `gitexclude.EnsureRepoExclude` pointed at the instance root itself when an exclude pattern is wanted for the outer-repo-nesting case — doing so risks silently mutating an outer repository's git-exclude file with instance-scoped patterns. The existing plain-`.gitignore`-at-instance-root mechanism (`EnsureInstanceGitignore`) is the correct, narrower precedent to extend instead (add the skills-tree pattern, e.g. `.codex/` or the marker name, to `InstanceExcludePatterns`), since that file lives in the instance root itself and only takes effect if an outer repo chooses to read gitignores from nested directories the normal way (i.e., harmlessly, and only affecting the outer repo's view of files physically under the instance root).

### 7. `[root.files]` / workspace-root skills as the closest existing precedent

Two related-but-distinct existing mechanisms both write into a **non-repo root**, and both establish the same precedent: **no managed-file record, overwrite-idempotent, no cleanup-on-removal.**

- **`[root.files]`** (`docs/guides/file-distribution.md:76-82`, implemented in `internal/workspace/root_materializer.go:158-172`): verbatim files copied from config into `<workspaceRoot>/...`. Per the guide: "Workspace-root files (`[root.files]`) are re-written on every apply (overwrite-idempotent)... The workspace root has no managed-file state store, so removing a `[root.files]` entry leaves the previously written file in place until you delete it by hand."
- **Workspace-root project skills** (`internal/workspace/root_materializer.go:17-27, 175-208`): `writeRootSkills(workspaceRoot)` walks an **embedded** (`//go:embed rootskills`) tree of niwa-owned skills (e.g. `dispatch`) and copies each `SKILL.md` verbatim to `<workspaceRoot>/.claude/skills/<name>/SKILL.md`. The doc comment is explicit about the tracking model: "The writes are plain overwrites — the content is static, so re-running is idempotent." No hash record, no reconcile-by-marker, no removal path if a root skill is retired from the embedded set — it would simply keep existing on disk from the last apply that wrote it, exactly like `[root.files]`.
- **Important distinction from the actual ask**: `writeRootSkills` copies *niwa's own static, embedded* skills, not the *configured plugins'* skills. Configured-plugin skills reach a Claude Code session at any root (workspace or instance) through `settings.json`'s `plugins`/`marketplaces` forwarding (`rootHoistableConfig`, `root_materializer.go:243-249`) and Claude Code's own plugin system — the comment in `skills.go:15-19` calls this out: "a tree delivered beside its [Claude's] settings would be bytes nothing reads." Codex has no such discovery, which is exactly why `SkillsReconcileSpec`/delivered-tree copying exists as a *parallel* mechanism at all, scoped (today) to `agent.AgentCodex` (`skills.go:88`).
- **What precedent this sets for a root skills delivery**: if a `.codex/skills/<plugin>` delivery at the **instance** root followed the `[root.files]`/`writeRootSkills` precedent literally, it would mean: write on every apply, no hash record, no state-store entry, and rely entirely on `SkillsReconcileSpec`'s own Keep-set diffing (finding 3) — which already exists precisely because directory trees can't go through the file-hash managed record anyway. In other words: the existing `SkillsReconcileSpec`/`reconcileSkillsDir` machinery (built for the per-repo case) already *is* the "no managed-file record, but still cleaned up by identity/marker rather than by hash" model that `[root.files]` and `writeRootSkills` fall back to by not having any cleanup at all. A root delivery reusing `SkillsReconcileSpec` would actually be **better tracked** than the existing root-level precedents (`[root.files]`, `writeRootSkills`), which have no de-configuration cleanup story whatsoever.

## Implications

- The instance root is **not** a hygiene blind spot today — `.niwa/instance.json`'s `ManagedFiles` record already covers every plain file niwa writes there, with content-hash-based drift detection and cleanup on every apply (finding 1, 2).
- The one real gap is that this record is hash-based and file-only, which is exactly why the per-repo skills delivery already uses a separate, marker/identity-based reconcile spec (`SkillsReconcileSpec`) instead of the managed-file record (finding 2, 3). That mechanism is repo-agnostic and would work unchanged if pointed at the instance root — the caller just needs to pass `instanceRoot` as `SkillsInputs.Dir` instead of `repoDir`.
- Whole-instance teardown (`DestroyInstance` / `niwa reap`, finding 4) makes any *within-instance* cleanup question moot for the destroy path — it's an orthogonal concern from staying-clean-across-applies-of-a-live-instance, which is what `SkillsReconcileSpec` actually needs to solve.
- Git-exclude coverage for a root delivery should **not** call `gitexclude.EnsureRepoExclude(instanceRoot, ...)` directly, because `git rev-parse --git-common-dir` walks upward and could silently attach niwa's exclude block to an *outer* repository when the instance root is nested inside a tracked tree (finding 6) — a correctness risk, not a crash risk. The already-shipped, narrower `EnsureInstanceGitignore`/`InstanceExcludePatterns` plain-`.gitignore` mechanism (finding 2, 7) is the right place to add coverage for a `.codex/skills` (or its marker) pattern, since it operates purely on a file *inside* the instance root and has no upward-search behavior.
- The `[root.files]` / `writeRootSkills` precedent (finding 7) shows niwa is comfortable shipping non-repo-root writes with weaker tracking (no removal-on-de-configuration at all) than what `SkillsReconcileSpec` already provides. That undercuts any argument that a root skills delivery needs a *new* tracking mechanism — the existing reconcile spec is already the right tool and already exceeds the bar set by the closest precedent.

## Surprises

- The task brief's framing — "the per-repository path has git-exclude bookkeeping and a managed-file/tracking model... the instance root... has a different teardown path" — undersells how much tracking the instance root *already* has. It has its own `ManagedFiles` record in its own `instance.json`, which is functionally the same model as the per-repo case, just without git-exclude coverage (because it isn't a repo) and without a symlink/tree reconcile spec (because nothing writes directory trees there today).
- `InstallWorkspaceRootSettings` is a false-friend name: despite "WorkspaceRoot" in its name, it targets the **instance** root, not the true workspace root. `MaterializeWorkspaceRoot` is the function for the actual workspace root. Anyone searching for "workspace root" code by name will find the wrong layer first (`root_materializer.go:107-109` documents this explicitly as a known naming trap).
- The `git rev-parse --git-common-dir` upward-search behavior means `gitexclude.EnsureRepoExclude` is not simply "safe on non-git dirs" in the way its own doc comment implies in isolation — the no-op only holds when there's truly no enclosing repo anywhere above the target, which the codebase's own comments (`gitignore.go:32-34`) say is *not* always true for instance roots in practice. Nothing in the current code path exercises `EnsureRepoExclude` against an instance root, so this particular interaction (outer-repo nesting + git-exclude call at the instance root) is untested, not just undocumented.
- The closest existing precedent for "write skill-shaped content at a non-repo root" (`writeRootSkills`) has *weaker* de-configuration hygiene than the mechanism already built for per-repo plugin skills (`SkillsReconcileSpec`). A root Codex skills delivery has a stronger tracking tool available to it than niwa's own existing root-level skill writes use.

## Open Questions

- Should `InstanceExcludePatterns`/`EnsureInstanceGitignore` gain a pattern for the Codex skills tree (e.g. `.codex/`) so an instance root nested in an outer tracked repo doesn't risk staging a symlink or copied tree? The mechanism exists and is the right place; whether it needs the new pattern is a design decision for the implementation, not something this exploration needs to resolve.
- If `SkillsReconcileSpec`/`SkillsPlan` is pointed at the instance root, does `excludePattern(in.Dir, path)` (skills.go:145) produce a sensible pattern when nothing downstream ever calls `EnsureRepoExclude` on that `Dir`? Worth confirming the exclude pattern isn't silently dropped or, worse, fed into some other consumer that does call `EnsureRepoExclude` on `instanceRoot`.
- Does anything in `InstallRepoSkills`'s caller (`apply.go:1645-1670`, `worktree_content.go:579-591`) assume `Dir` is inside `classified` repos for logging/reporting purposes that a root-level call site would need to adapt (e.g., "which repo does this warning belong to")?

## Summary
The instance root is already a tracked surface: every plain file niwa writes there (settings.json, context docs, `[instance.files]`) goes through `.niwa/instance.json`'s content-hashed `ManagedFiles` record with cleanup on every apply, and whole-instance teardown (`DestroyInstance`/`niwa reap`) `RemoveAll`s the entire directory regardless. The real gap is that this record can't hash directory trees, which is exactly why the per-repo skills delivery already uses a separate, repo-agnostic `SkillsReconcileSpec`/marker-based reconcile mechanism instead — that mechanism would work unchanged at the instance root and is already better tracked than the closest existing root-level precedent (`writeRootSkills`/`[root.files]`, which have no de-configuration cleanup at all). The one real risk is git-exclude bookkeeping: `EnsureRepoExclude` searches upward for an enclosing repo, so pointing it at an instance root nested inside a tracked outer tree could silently write into that outer repo's exclude file — the existing plain-`.gitignore`-at-instance-root mechanism (`EnsureInstanceGitignore`/`InstanceExcludePatterns`) is the narrower, already-proven way to cover that case instead.
