# Lead: Where do the delivered skills symlink targets live, how often does niwa rotate them, and what does the per-repository delivery already do about that exposure?

## Findings

**Two, and only two, kinds of symlink target `ResolvePluginTrees` can produce** (`internal/workspace/pluginskills.go:161-207`, `marketplaceRoots`):

1. **`repo:`-sourced marketplace** — resolves through `ResolveMarketplaceSource` against the workspace's own clone (`in.RepoIndex`), then `filepath.Dir(filepath.Dir(resolved))` walks back up from the manifest to the marketplace root (`pluginskills.go:187-196`). The target is a directory *inside a cloned repository's working tree*, owned by that clone.
2. **github-sourced marketplace** — fetched into a niwa-owned cache at `<instanceRoot>/.niwa/marketplaces/<name>` (`marketplaceContentRoot`, `pluginskills.go:35-38`) via `ensureMarketplaceContent` (`pluginskills.go:215-260`).

**Materialization of the github-sourced case is fetch-once, not periodic.** `ensureMarketplaceContent` first checks `os.Stat(marketplaceManifestPath(dest))`; if the manifest is already there it returns the existing path immediately with **no re-fetch, no TTL check, no track re-resolution** (`pluginskills.go:223-226`). The doc comment is explicit about why: *"Re-fetching on every apply would put a network round trip in front of every preparation and would swap the tree under a running session for no benefit: the content is pinned by the configured track, and removing the directory is how a workspace asks for it again"* (`pluginskills.go:216-221`). I grepped `pluginskills.go` and its test file for `refresh`, `TTL`, `force`, `stale` — none exist. So in practice the directory is replaced **only if a user manually deletes `.niwa/marketplaces/<name>` and a subsequent `niwa apply`/`ResolvePluginTrees` call runs** (this function is reached from `apply.go` and `worktree_content.go`, i.e. on `niwa apply` and worktree preparation).

**When replacement does happen, it is wholesale but path-stable, not inode-stable.** The fetch path extracts into `dest + ".staging"`, validates the manifest is present, then `os.RemoveAll(dest)` followed by `os.Rename(staging, dest)` (`pluginskills.go:247-260`). The absolute path `dest` never changes — only what's rewritten under it. Because a symlink resolves by path, not inode, a symlink already pointing at `dest` keeps working transparently after a swap: it now reads the fresh content with zero repair needed. The only risk window is the narrow gap between `RemoveAll` and `Rename` during an in-flight apply, where a concurrent reader could see a transiently-missing directory — this is inferred from the code, not measured, and only matters if something is reading through the link *during that specific apply*, which itself only happens when the directory had to be re-fetched (i.e., someone deleted it first).

**The repo-sourced case is materially more stable still.** Repos already on disk are updated via `SyncRepo` (`internal/workspace/sync.go:108`), which does `git fetch` + fast-forward merge **in place** — it never removes or replaces the clone directory. `repoAlreadyCloned` (`apply.go:2621-2624`) gates whether a repo is cloned fresh or synced; a directory is only `os.RemoveAll`'d during `cloneWithRetry` between failed clone attempts on a repo that was never successfully cloned (`apply.go:2677-2695`), which doesn't apply to an already-established clone a plugin tree is being read from.

**What the per-repo delivery already does about exposure (`internal/workspace/applyplan.go:286-340`, `deliverPlanTree`):**
- Every `niwa apply` (and worktree prep) re-declares the same `Entry{Path, Source}` and re-runs `deliverPlanTree`. If a symlink already exists at `Path` and `treeLinkTargets(path, source)` is true (compares both raw and fully-resolved paths, `applyplan.go:342-360`), it's a no-op. This makes ordinary re-application cheap and self-verifying — but it *never had to repair anything* in the common case, because materialization keeps the source path stable (see above).
- If the link exists but points somewhere else, it's removed and recreated pointing at the (possibly new) resolved source — this handles a plugin's resolved root *changing* (e.g. different marketplace), not a target going missing.
- **There is no dangling-link detection or repair anywhere in this pipeline.** The plan entry's precondition is `IfSourceExists` (`agentplan/plan.go`, evaluated at `applyplan.go:118-126`): if `os.Stat(e.Source)` fails with not-exist, `planEntryApplies` returns `(false, nil)` — the entry is silently skipped as a no-op. Critically, this means an *existing* dangling symlink at `Path` is left completely untouched when its source has vanished — `deliverPlanTree` isn't even called, so it can't remove or flag the stale link.
- `reconcileSkillsDir` (`pluginskills.go`, end of file) only removes delivery names that fell out of the configured `Keep` set (de-configured plugins). It recognizes what to remove by shape (symlink) or sentinel (copy fallback's `.niwa-delivered-tree` marker via `TreeMarkerFileName`, `agentplan/skills.go:37-46`) — it does **not** `Lstat`/resolve targets to check for danglingness. A dangling link for a still-configured plugin is invisible to reconcile too.
- Net: the repo-side delivery's implicit protection against rotation is **entirely a byproduct of materialization keeping paths stable**, not any explicit repair/validation logic. If a target path were ever to genuinely and permanently disappear, nothing in this pipeline would notice, report, or heal it — the symlink just stays dangling until the source path reappears.

**Copy fallback changes the analysis only on Windows.** `treeDeliveryPrefersCopy` (`applyplan.go`) is `runtime.GOOS == "windows"`; everywhere else symlink is attempted first and copy is only a fallback if the `os.Symlink` write itself errors. When copying is used, the "target rotates" question doesn't apply the same way: a copy is a point-in-time snapshot re-delivered wholesale (via the `.niwa-delivered-tree` sentinel check) on next apply if the source changed — so a copy actually *does* need, and *does* get, explicit re-sync logic (`treeCopyIsNiwas`, `applyplan.go`), unlike the symlink path which just rides the stable source path.

**No existing design doc discusses symlink target stability.** I checked `docs/spikes/SPIKE-codex-discovery-mechanics.md` (the doc `agentplan/skills.go` cites for the delivery-shape finding) and grepped all `docs/designs/current/*.md` and `docs/prds/*.md` for "root" + "skill" — nothing addresses marketplace/plugin-tree rotation or link staleness. The closest related doc, `docs/designs/current/DESIGN-mcp-root-instance-distribution.md`, is about a *different* root-delivery mechanism (verbatim `[root.files]`/`.mcp.json` materialization, overwrite-idempotent, no managed-file store) and doesn't touch plugin-tree symlinks at all.

**The root-extension work does not exist yet in this codebase.** `internal/workspace/root_materializer.go` currently has no reference to `PluginSkills`, `ResolvePluginTrees`, or `InstallRepoSkills` at all — I grepped for all three and got nothing. What root materialization does today for Claude Code is a *different* mechanism: `writeRootSettings` (`root_materializer.go:238-`) registers `rootHoistableConfig`'s plugins/marketplaces into `.claude/settings.json` at the workspace root, so Claude Code's own plugin system resolves them — not niwa's symlink delivery. And it explicitly **excludes `repo:`-sourced marketplaces from the root today**, with the comment: *"repo:-sourced marketplaces point into an instance checkout that does not exist at the workspace root, so they (and the plugins bound to them) are excluded and reported"* (`root_materializer.go:240-243`).

**The workspace root does have its own `.niwa/` directory** (confirmed by `root_materializer.go:92,110,420` and the `CLAUDE.md`/`workspace-context.md` shown to me — `.niwa/workspace.toml` lives at the root). This matters for the root-extension design: nothing structurally prevents giving the root its own `.niwa/marketplaces/<name>` cache via the exact same `ensureMarketplaceContent` code path (`InstanceRoot` would just be the workspace root instead of an instance root) for **github-sourced marketplaces** — that would have identical stability properties to the instance case, because it's the same code. But **`repo:`-sourced marketplaces have no mechanically valid root target at all**: there is no clone at the workspace root (repos only live inside instance subdirectories, per `workspace-context.md`), and there is no canonical "the instance" a root session could borrow a clone from — the workspace can have zero, one, or many instances, including ephemeral per-dispatch ones that get reaped. This is exactly why `writeRootSettings` already excludes `repo:`-sourced marketplaces for the Claude path today.

## Implications

The rotation exposure question splits cleanly by target type, and the two halves need different answers:

- **github-sourced marketplace → `.niwa/marketplaces/<name>`.** "Inherit" is not actually risky here: reusing `ensureMarketplaceContent` with `InstanceRoot = workspaceRoot` gives the root its own independently-cached copy with the same fetch-once/path-stable/no-TTL semantics the instance already relies on safely. This is not "inherit the repo case's exposure silently" — it's "the root becomes its own owner of a marketplace cache," and that ownership model is what already makes the instance case safe. This can be stated and justified explicitly rather than assumed.
- **`repo:`-sourced marketplace → inside a cloned repo.** True inheritance is impossible to define at the root: there is no repo clone there, and no single instance is canonically "the" one to borrow from. The design must pick one of: (a) exclude `repo:`-sourced plugins from root delivery, mirroring `rootHoistableConfig`'s existing exclusion for the Claude settings path (cheapest, consistent with prior art, but means a root Codex session gets fewer plugins than an instance-launched one when any plugin uses a `repo:` marketplace) — or (b) fetch/mirror that repo's plugin content into the root's own `.niwa` cache the way github-sourced content is fetched (more code, new fetch path for something that's currently resolved purely by local clone lookup, and it would diverge root's resolution semantics from every instance's).

Either way, the answer is not "root links inherit the rotation exposure because the repo case does" — the repo case's safety comes from *path-stable materialization owned at the same scope as the link*, and that reasoning transfers cleanly to a root-owned github marketplace cache but has no analogue for a repo-sourced one at root scope.

## Surprises

- The "rotation" premise in the lead is weaker than it sounds: `.niwa/marketplaces/<name>` is not rotated on any cadence — it's fetched once and kept forever unless a human deletes it. The real exposure isn't periodic churn; it's "what happens on the rare/manual re-fetch," and the answer (path-stable rename) is already benign for a symlink.
- There is genuinely no dangling-symlink detection anywhere in this pipeline, at any level. The system's resilience is 100% incidental — a consequence of materialization always writing to the same path — not a designed repair mechanism. A root-level design that assumes "apply repairs breakage" would be asserting something the current codebase doesn't actually do.
- `rootHoistableConfig` already had to solve a version of this exact problem (repo:-sourced marketplaces have no root-resolvable target) for the unrelated Claude settings.json delivery path, and it chose exclusion + reporting. That's directly relevant prior art for the Codex symlink case and should probably be named in the design rather than rediscovered.

## Open Questions

- Should root-level github-sourced marketplace content share the *same* `.niwa/marketplaces/<name>` cache as some instance (deduplicating fetches), or does each scope (root, each instance) get its own independent cache under its own `.niwa`? The current code has no cross-scope sharing concept; every `InstanceRoot` gets an independent `marketplaceContentRoot`.
- For `repo:`-sourced plugins excluded from root delivery, should `ResolvePluginTrees`/root-materialization surface a `MissingPluginRoot`-style report (the type already exists and is designed exactly for "configured but not deliverable, tell the user why"), matching how `rootHoistableConfig` already reports its exclusions for the Claude path?

## Summary
`ResolvePluginTrees` produces two target kinds: a directory inside a cloned repo (updated in place via `git fetch`/fast-forward, never replaced) and `.niwa/marketplaces/<name>` (fetched once, replaced wholesale only on manual delete + reapply, via remove-then-rename to the same stable path) — in both cases a symlink survives refreshes for free because it resolves by path, not inode, and the only "repair" the per-repo delivery does is incidental re-declaration on every apply, with zero explicit dangling-link detection anywhere in the pipeline. For root-level delivery, github-sourced marketplaces can safely inherit this model by giving the workspace root its own `.niwa/marketplaces` cache (the root already has a `.niwa/` directory), but `repo:`-sourced marketplaces have no valid root target at all since no repo is ever cloned at the workspace root — that half must be excluded (as `rootHoistableConfig` already does for the Claude settings.json path) or handled by an entirely new fetch mechanism, not "inherited."
