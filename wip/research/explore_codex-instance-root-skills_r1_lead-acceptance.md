# Lead: What functional-test surface exists for a Codex acceptance scenario, and how much can be measured without spending model quota?

## Findings

**1. The functional harness.** `test/functional/` runs the compiled `niwa` binary via godog (Cucumber-style). Structure: `features/*.feature` (Gherkin), `suite_test.go` (TestMain, sandbox setup, step registration), `steps_test.go` + per-area step files (e.g. `codex_agent_steps_test.go`, 1858 lines), `localrepo_test.go`/`gitfixture_test.go` (offline bare-repo git fakes). Run commands, verified against `Makefile`:
- `make test-functional` — full suite (builds `niwa-test`, sets `NIWA_TEST_BINARY`, runs `go test -v ./test/functional/...`). No tag filter — this is what CI runs.
- `make test-functional-critical` — same but `NIWA_TEST_TAGS=@critical`.
- A single scenario: `NIWA_TEST_BINARY=$(pwd)/niwa-test NIWA_TEST_TAGS='@critical && "a session started at the instance root is oriented"' go test -v ./test/functional/...` (godog matches scenario name text as a pseudo-tag; simplest is `NIWA_TEST_PATHS=features/codex-agent.feature`).
- Both `test-functional*` targets take a `flock` on `.functional-test.lock` in the repo root, so two runs in the same checkout serialize (matches the "don't run concurrently" constraint already).

**2. Existing Codex-touching tests**, from `grep -rn CODEX_HOME` and `grep -rln codex --include=*.go`:
- `test/functional/features/codex-agent.feature` (995 lines) + `test/functional/codex_agent_steps_test.go` (1858 lines) is the whole surface. It has 19 scenarios; 17 are `@critical` and pure on-disk/modeled assertions (no real binary), 2 are `@codex-live` and do invoke the real binary.
- `@critical` scenarios use a **Go-implemented model of Codex's discovery walk** (the "Codex context at ..." / "Codex payload at ..." / "Codex skills tree ... mirrors ..." steps) to assert file placement and a re-derivation of the first-match/budget/trust rules recorded in the spike. They do not shell out to `codex`. This includes `Scenario: a session started at the instance root is oriented` (line 318, @critical) and `Scenario: the workspace's skills reach Codex whole and namespaced` (line 478, @critical) — the latter only asserts the on-disk mirror (`.codex/skills/demo/...` exists and matches byte-for-byte), not that the real binary resolves it.
- Two `@codex-live` scenarios (lines 933, 968) do call the real binary: `iRunCodexExecFrom` runs `codex exec <prompt>` (a real model turn) and `iStartInteractiveCodexAt` runs the interactive TUI under `script` with a dwell timeout (also a real turn once past trust). Both are gated by `codexIsAvailable` (`internal/../codex_agent_steps_test.go:1690`), which returns `godog.ErrPending` — not fail — if `exec.LookPath("codex")` fails or no developer credential file is found at `$CODEX_HOME/auth.json`-equivalent, so they're skip-not-fail without a login. When they do run, they seed **an isolated `CODEX_HOME`** (`s.homeDir/.codex`, codex_agent_steps_test.go:1613) by copying only the credential file from the developer's real Codex home into the sandboxed one — never pointing the session at the real one directly. `codexLiveEnv` also strips `NIWA_*` and any ambient `CODEX_HOME`. These two scenarios are the only ones that spend model quota, and they're excluded from `@critical`.
- Unit-level: `internal/workspace/codex_trust_test.go`, `internal/agentplan/*_test.go`, `internal/cli/dispatch_layout_test.go` reference `CODEX_HOME` as a symbolic constant / path-composition target, not as a live invocation — they test niwa's own trust-file and layout logic, no `codex` process involved.

**3. `codex` on this machine right now**: present. `command -v codex` → `/home/dgazineu/.tsuku/tools/current/codex`; `codex --version` → `codex-cli 0.147.0` (same version the spike measured against). No `codex exec` or interactive session was run — only `--help` and the zero-cost `codex debug prompt-input` introspection (see finding 4).

**4. The zero-model-cost observable is `codex debug prompt-input [PROMPT]`.** `codex --help` lists a `debug` subcommand with a `prompt-input` child ("Render the model-visible prompt input list as JSON"); this makes no API call. Verified live, with `CODEX_HOME` pointed at a throwaway directory under this job's tmp (never touching `~/.codex`):
- Ran `CODEX_HOME=<tmp>/codex_home_test codex debug prompt-input "hello"` from a directory with **no** `.codex/skills` tree: output is a JSON array of message objects; the first `developer` message contains a literal `<skills_instructions>` block listing every discovered skill by name, description, and a `file:` path to its `SKILL.md`. With nothing project-local, only the 5 built-in `$CODEX_HOME/skills/.system/*` skills appeared (auto-seeded on first CODEX_HOME use).
- Built a project dir with `.codex/skills/demo/skills/greet/SKILL.md` (the two-level `<plugin>/skills/<skill>/SKILL.md` shape the spike's finding 5 and the existing "skills reach Codex whole and namespaced" scenario both use — a flat one-level `.codex/skills/greet/SKILL.md` I tried first was **not** picked up, which matches the plugin-namespaced shape, not a flat one). From inside that directory, the same command's skills list gained a `greet: ... SENTINEL-SKILL-BODY-XYZ (file: <path>/.codex/skills/demo/skills/greet/SKILL.md)` entry — no trust entry configured, confirming the spike's "skills load from an untrusted layer" claim.
- Ran the identical command one directory **up** (the parent, which has no `.codex/skills` of its own): `grep -c "greet\|SENTINEL-SKILL-BODY-XYZ"` on the output → `0`. This is the negative control in miniature: a skills tree one level up did not arrive when the session's cwd is the parent, matching finding 1's bounded-downward-walk (the walk starts at cwd/its project root, never above it).
- This means the full positive/negative pair is measurable today, offline, at zero model cost: `cd <A>; CODEX_HOME=<sandbox> codex debug prompt-input <prompt> | <assert "greet" present>` and `cd <parent-of-A>; CODEX_HOME=<sandbox> codex debug prompt-input <prompt> | <assert "greet" absent>`.
- `codex plugin list --json` and `codex plugin marketplace list` also exist and are zero-cost, but they report *installed/configured* plugins (via `codex plugin add`, which writes into `$CODEX_HOME`), a separate, explicit-registration mechanism from the project-local `.codex/skills/` convention niwa's delivery mirrors — not needed for this acceptance bar, but worth knowing they're a second, unrelated introspection surface if a future scenario needs it.
- No `codex config` dump subcommand exists; `codex doctor --json` reports auth/runtime health and counts MCP servers, not skills.

**5. Negative control precedent.** The spike's own finding 1 was established exactly this way — "Measured both ways at zero model cost with `codex debug prompt-input` and an isolated `CODEX_HOME`" — including the "two experiments misleading" paragraph describing the same shape of error this initiative is trying to avoid (a probe with no marker above it looking like "only cwd is read" when it's really the bounded walk falling back to cwd as root). **None of this is codified as an executable test.** The spike is a markdown record of manual `codex debug prompt-input` runs; `codex-agent.feature` has no scenario that shells out to the real binary and greps its `prompt-input` output. The `@codex-live` scenarios use `codex exec`/interactive TUI, not `debug prompt-input`, and don't construct a negative control (they check "no trust prompt shown" / "reached ready state", not "did NOT load X").

**6. Concrete shapes for the acceptance scenario, ranked:**
- **(a) A functional Gherkin scenario driving the real binary via `codex debug prompt-input`, no model turn — recommended.** New steps: `Given codex is available` (reuse the existing `codexIsAvailable` gate, pending-not-fail without the binary), `Given the sandbox CODEX_HOME is isolated` (reuse the existing sandbox-home pattern from `aFakeCodexForDispatchWithSession`/`codexLiveEnv`, no credential needed since `debug prompt-input` doesn't require login), `When I run codex debug prompt-input "..." from "<instance-root>"` and from `"<instance-root's parent>"`, `Then the Codex prompt input lists skill "workspace-skill-name"` / `Then the Codex prompt input does not list skill "workspace-skill-name"`. This proves: the real 0.147.0 binary, not a model of it, resolves a workspace skill when the session's cwd is the instance root, and the identical binary run one directory up does not — the exact discriminator the acceptance bar asks for. It proves discovery, not that a live turn can *use* the skill (that would need a model turn). It can run in CI iff CI has a `codex` binary (see finding 7 — currently it does not, so it'd be pending there, same as the two `@codex-live` scenarios today).
- **(b) A functional scenario asserting only on-disk layout (no binary) — already exists.** `Scenario: the workspace's skills reach Codex whole and namespaced` (line 478) plus the modeled-walker "Codex skills tree ... mirrors ..." step. Fast, `@critical`, runs everywhere including CI, but only proves niwa wrote the right bytes at the right path — it cannot by itself distinguish "codex will read this" from "codex's own directory convention changed out from under niwa," which is exactly the class of error the spike says burned two earlier attempts. Necessary but not sufficient for the stated acceptance bar.
- **(c) Something requiring a model turn.** Only needed if the bar is "a live Codex *session* actually uses the skill's instructions to act," not just "resolves" it. The `@codex-live` `codex exec` pattern already exists and is the template, but it spends quota and needs the author's explicit sign-off per the stated constraint — flagging this rather than proposing it as default.

Recommendation: (a), added as a new `@codex-live`-style tag (e.g. `@codex-live` reused, or a narrower `@codex-discovery-live` if the author wants it separated from the quota-spending scenarios) so it's excluded from `@critical`/CI-gating by default but runnable locally and possibly promotable to CI once a `codex` binary is provisioned there.

**7. CI codex-binary presence.** `.github/workflows/*.yml` has zero references to `codex` (`grep -rln codex .github/workflows/` → empty). `test.yml` runs `make test-functional` (line 123, full suite, no tag filter) and `make test-functional-claude-integration` (line 184, needs `claude` CLI + `ANTHROPIC_API_KEY` — a different, already-precedented pattern for gating an external-binary-dependent job). Since `codex` isn't installed in that runner and `codexIsAvailable` treats a missing binary as `godog.ErrPending`, any `@codex-live`-tagged scenario — existing or a new discovery one built per (a) — currently skips (not fails) in CI. A discovery-only scenario built on `debug prompt-input` has no auth/login requirement (unlike the two existing live scenarios), so the *only* CI blocker is provisioning the `codex` binary itself; if that's done, this specific scenario could become CI-gating without also requiring `ANTHROPIC_API_KEY` to be present.

## Implications

- The acceptance bar as stated ("real `codex` binary" + "negative control") is achievable **without spending quota**, contradicting an implicit assumption that proving real-binary discovery requires a live turn. `codex debug prompt-input` is the load-bearing primitive, and it's already the exact tool the spike used to earn its own findings — this closes the loop of "recorded as findings, not codified as a test."
- The existing skill-delivery on-disk shape (`.codex/skills/<plugin>/skills/<skill>/SKILL.md`) is confirmed correct against the real binary — my first attempt at reproducing it flat (`.codex/skills/<skill>/SKILL.md`) silently failed to register, which is a plausible trap for anyone hand-rolling a probe instead of reusing the shape the existing `mirrors` scenario already produces.
- Isolation and quota-safety are compatible with this design: `CODEX_HOME` alone (no `HOME` override) is sufficient to sandbox `codex debug prompt-input`, and no credential/login is needed for it to run — simpler than the `codexIsAvailable` gate's credential-seeding, which exists only because the two current live scenarios need auth.

## Surprises

- A flat `.codex/skills/<skill>/SKILL.md` (skill directly under `skills/`) is invisible to the real binary; only the two-level, plugin-namespaced `.codex/skills/<plugin>/skills/<skill>/SKILL.md` shape resolves. This matches the spike's "symlinked plugin tree" description and the existing feature scenario's mirrored layout, but would be an easy way for a fresh probe (or a future scenario author) to manufacture a false negative.
- `codex debug` and `codex plugin` expose a materially richer zero-cost introspection surface than the spike doc's own tool list implies (`debug models`, `debug prompt-input`, `debug app-server`, `plugin list --json`, `plugin marketplace list`) — worth knowing about even though only `prompt-input` is needed here.

## Open Questions

- Should the new scenario reuse the `@codex-live` tag (bundling it with the quota-spending scenarios, so a single `NIWA_TEST_TAGS` exclusion keeps both out of CI/local-critical runs) or get its own tag so it can be promoted to CI-gating independently once a `codex` binary is provisioned there, without also pulling in the quota-spending ones? I lean toward a separate tag given finding 7, but this is the author's call.
- Does the acceptance bar want the scenario to assert on the parsed JSON (robust to prose changes in the skill description) or a raw substring/grep (simpler, more brittle to codex's own output format changes)? The existing `theCodexLaunchArgvContains`-style substring-match steps in this same file suggest substring assertions are the house style; JSON parsing would be a first for this file.

## Summary
The harness already has everything needed except one new scenario: `test/functional/features/codex-agent.feature` + `codex_agent_steps_test.go` provide the godog runner, the `codexIsAvailable` pending-not-fail gate, and an isolated-`CODEX_HOME` pattern, and `codex-cli 0.147.0` is installed here. `codex debug prompt-input <prompt>` is a genuine zero-model-cost introspection command — verified live with an isolated `CODEX_HOME` — that lists exactly which skills a session's cwd would resolve, and running it from an instance-root directory versus its parent reproduces the requested positive/negative control today by hand; none of this is yet codified as an executable scenario, and CI has no `codex` binary so any such scenario would skip there until one is provisioned.
