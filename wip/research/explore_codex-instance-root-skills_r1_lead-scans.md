# Lead: What structural scans, binding rules and drift tests already exist in this repo, and what precisely would each fail on?

## Findings

### Scan 1 — no agent constant at the materializer call site

`TestWorkspaceNamesNoAgentConstant` (`internal/agentplan/layout_scan_test.go:218-233`). Mechanism: parses every non-test `.go` file directly inside `internal/workspace` (`parsePackageFiles`, `layout_scan_test.go:139-160`, `workspaceDir = "../workspace"`) with `go/parser` + `go/ast`, walks each file's AST with `ast.Inspect`, and flags any `*ast.SelectorExpr` whose package identifier is `agent` and whose selector name is in `agentConstants = []string{"AgentClaude", "AgentCodex"}` (`layout_scan_test.go:60-63, 218-233`). It is a syntax-tree walk, not grep — a comment naming `agent.AgentCodex` does not trip it (`parsePackageFiles` never parses comments). No exemption list exists for this half of the scan; the lead's framing ("no exemption may be added to it") matches the code as written — there is no skip/allow mechanism at all, only the flat forbidden-name check. Failure message: `"internal/workspace names an agent constant at %d site(s); the agent is data threaded through the plan, not a branch:\n%s"` with each violation rendered as `file:line: names agent.<Name>`.

"The materializer call site" is `internal/workspace`'s pipeline that invokes `Materializer.Deliver` — concretely `runRepoMaterializers` (`internal/workspace/worktree_content.go:99-201`, called from `apply.go`'s "Step 6.5: Run materializers" at `apply.go:1817` and from `installWorktreeMaterialization` at `worktree_content.go:719-782`), plus the procedure/binding lookup `procedureFor` in `internal/workspace/delivery_binding.go:96-118`. Today none of these name `agent.AgentClaude`/`agent.AgentCodex` directly — `procedureFor` takes an `agent.Agent` *value* and resolves it through `agent.ParseAgent` + `agentplan.Lookup`/`agentplan.Bindings()` (`delivery_binding.go:100-117`), never branching on a named constant. I confirmed via `grep -rln "agent\.AgentCodex\|agent\.AgentClaude"` that the only non-test files anywhere in the repo naming these constants are `internal/cli/dispatch_plugins.go` and five files inside `internal/agentplan` itself (`dispatch.go`, `skills.go`, `binding.go`, `gaplist.go`, `declaration.go`, `payload.go`) — none in `internal/workspace`. New code for rows 18/19 would trip this scan the moment it writes something like `if ag == agent.AgentCodex { ... }` anywhere in `internal/workspace` to decide whether/where to deliver root skills or the plugin manifest; the correct shape is to add a per-agent table (the way `skillsLayouts map[agent.Agent][]string` at `internal/agentplan/skills.go:87-89` or `payloadLayouts map[agent.Agent]payloadLayout` at `internal/agentplan/payload.go:339` already do) inside `internal/agentplan`, and have `internal/workspace` consume it as data.

### Scan 2 — `internal/workspace` names no agent and no agent context filename

Two tests, same file:
- `TestWorkspaceNamesNoAgentContextFilename` (`layout_scan_test.go:239-244`) — walks the same parsed files and flags any string literal (`*ast.BasicLit`, `token.STRING`) whose unquoted value is one of `agentContextFilenames = []string{"CLAUDE.md", "CLAUDE.local.md", "AGENTS.md", "AGENTS.override.md"}` (`layout_scan_test.go:50-56`, detector `contextFilenameViolations` at `layout_scan_test.go:184-198`). Failure message: `"internal/workspace names an agent context filename at %d site(s); the filename belongs to the agent's producer, not to the writer:\n%s"`.
- `TestWorkspaceNamesNoAgentConstant`, described above, is the agent-constant half of the same combined property.

Both are literal/selector scans over the AST, not grep, and both cover only non-test `.go` files directly inside `internal/workspace` (not subpackages, not `_test.go` files — comments are exempt by construction).

**Exemption confirmed removed.** Commit `74c6a2e` ("test(agentplan): close the context-writer conversion window in the layout scan", PR #267) deleted the four-file conversion-window exemption (`content.go`, `worktree_content.go`, `workspace_context.go`, `root_materializer.go`'s dead `rootClaudeFile` constant) that previously let a filename literal in those files skip rather than fail. The current `layout_scan_test.go` source has no skip list left — `TestContextFilenameScanReportsALiteral` (`layout_scan_test.go:260-291`) now only exercises the detector against synthetic in-memory source (`parseSource`), proving it still fires, without exempting any real file. So: no exemption window survives, and the lead's "no exemption may be added to it" instruction is consistent with a scan that has already been proven to have zero tolerance.

**How `internal/workspace` gets agent-specific behavior without naming an agent:** every writer takes an `agentplan.Producer` obtained via `agentplan.For(ag)` and calls its `*Plan`-returning methods (`RootContextPlan`, `RepoContextPlan`, `WorktreeContextPlan`, `SkillsPlan`, `PayloadPlan`, etc.), all declared in `internal/agentplan`. The producer, not the caller, decides filenames (e.g. `skillsLayouts[agent.AgentCodex] = {".codex", "skills"}` at `skills.go:88`, `payloadLayouts[agent.AgentCodex].path = []string{codexPayloadDirName, "config.toml"}` at `payload.go:361-373`) and whether a plan is empty for a given agent (`skillsLayouts` has no Claude entry at all, so `SkillsPlan` for Claude always returns zero entries — see `skills.go:87-89` comment). `internal/workspace` only ever holds an opaque `agent.Agent` value threaded through from the session and forwards it to `agentplan.For(ag)`; it never inspects which one it has. This is the "producer/`agentplan.For` seam" — `internal/agentplan` is the only place agent identity is named or branched on; `internal/workspace` executes whatever `*Plan` (a list of `Entry` values: path, op, source, mode, owner) the producer handed back, filesystem-agnostically as far as agent identity goes.

### The binding rule

Model (`internal/agentplan/binding.go`): a **Delivery** (`type Delivery string`, e.g. `DeliveryEnv`, `DeliveryFiles`, `DeliveryHooks`, `DeliveryCodexTrust`) is a stable name for "one concrete thing in `internal/workspace` that delivers a capability." A **Binding** (`{Capability, Agent, Delivery}`) says which delivery satisfies one implemented `(capability, agent)` pair. `boundCapabilities` (`binding.go:56-63`) is an explicit, hand-maintained list of the capabilities that are *bound at all* today: `DotenvFiles, FileDistribution, Hooks, DirectoryTrust`. `bindings` (`binding.go:76-84`) is the concrete rows: both agents to `DeliveryEnv`/`DeliveryFiles`, Claude only to `DeliveryHooks`, Codex only to `DeliveryCodexTrust`.

On the `internal/workspace` side, `deliveries map[agentplan.Delivery]Materializer` (`delivery_binding.go:24-28`) registers the zero-value materializer instance under each named delivery (used only as an identity check, not as the runnable instance), and `procedures map[agentplan.Delivery]procedure` (`delivery_binding.go:87-89`) does the same for procedure-routed deliveries (currently just `DeliveryCodexTrust → codexTrustProcedure{}`).

**Registration mechanism:** nothing on the `internal/workspace` side is a "test" per se — the binding *rule* is enforced entirely in `internal/agentplan`, over data both sides expose. `TestBindingsMatchTheirDeclarations` (`binding_test.go:14-59`) is the check: for every row in `Bindings()`, it asserts (a) the capability is in `BoundCapabilities()`, (b) the delivery string isn't empty, (c) no `(capability,agent)` pair is bound twice, and (d) `Lookup(capability, agent)` succeeds and returns `StateImplemented` — a delivery whose declaration is missing or unavailable fails with `"(%s, %s) is bound to delivery %q but is not declared implemented; something delivers a capability nobody declared"`. Then, symmetrically, for every capability in `BoundCapabilities()` and every agent in `agent.All()`, it asserts: implemented-but-unbound fails with `"(%s, %s) is declared implemented with no delivery bound to it"`, and bound-but-not-implemented fails with `"(%s, %s) is not implemented yet carries a binding"`. Those are the two drift directions: **a declaration without a delivery**, and **a delivery without a declaration** (the exact language the lead used, verbatim from `binding.go`'s own doc comment at lines 42-46 and the test's doc comment at lines 8-11).

Two supporting tests: `TestBoundCapabilitiesAreInTheClosedSet` (`binding_test.go:64-73`) keeps `boundCapabilities` from naming a capability outside `All()`; `TestBindingAccessorsReturnFreshSlices` (`binding_test.go:75-87`) pins that `BoundCapabilities()`/`Bindings()` return copies, not the package's own backing slices.

**What rows 18/19 need for binding, precisely:** `RootProjectSkills` and `NiwaPlugin` are **currently absent from `boundCapabilities` entirely** (they are neither in `binding.go`'s list nor referenced anywhere in `binding_test.go`), so `TestBindingsMatchTheirDeclarations` says nothing about them today and will not catch a delivery landing unbound. To make them bound-and-implemented pass the drift rule: (1) add `RootProjectSkills` and `NiwaPlugin` to `boundCapabilities` (or leave them unbound and accept `TestBindingsMatchTheirDeclarations` staying silent on them — but the lead's mandate #3 says "a declaration without a delivery" must fail, which only happens for capabilities *in* `boundCapabilities`, so they must be added); (2) flip their Codex row `State` to `StateImplemented` in `declaration.go` (already drafted in the row comments as the intended end-state, currently `StateUnavailable`/`ReasonNotBuilt`); (3) add a `Binding{Capability: RootProjectSkills, Agent: agent.AgentCodex, Delivery: <name>}` and same for `NiwaPlugin` to `bindings`; (4) register that `Delivery` name against a real `Materializer` in `internal/workspace/delivery_binding.go`'s `deliveries` map (or a `procedure` in `procedures`, if the mechanism is procedure-routed like directory trust rather than plan-borne like the existing materializers) — matching whatever concrete writer the implementation lands (this is `internal/workspace`-side code the other leads are covering, not something `binding.go` prescribes the shape of). Skipping any one of steps 2-4 while doing the others is exactly what `TestBindingsMatchTheirDeclarations` is built to catch.

### The gap list and its drift test

`docs/guides/codex-agent.md` carries a generated section delimited by two HTML-comment markers: `<!-- BEGIN GENERATED: codex gap list (internal/agentplan/gaplist.go) -->` … `<!-- END GENERATED: codex gap list -->` (constants `gapBeginMarker`/`gapEndMarker`, `gaplist_test.go:26-29`). `RenderGapSection(agent.AgentCodex)` (`gaplist.go:169-193`) builds the section from `UnavailableFor(ag)` (`gaplist.go:135-158`), which filters `declarations` down to `StateUnavailable` rows for the given agent, in matrix order, grouped by `ReasonKind` into three headed groups (`gapGroups`, `gaplist.go:107-124`): "What %s can't receive" (`ReasonAgentCannotReceive`), **"What niwa hasn't built yet"** (`ReasonNotBuilt`), "What doesn't apply to %s" (`ReasonNoSuchConcept`). Confirmed the two bullets that must disappear once rows 18/19 flip, quoted verbatim from `docs/guides/codex-agent.md:376-381`:

> - **Instance-root skills such as `/dispatch`.** Codex loads a skills tree from the project layer at a root-started session's own working directory, with no trust entry needed; niwa writes no project layer at an instance root.
> - **niwa's own plugin, which carries the migrate-config skill.** Codex accepts the identical plugin manifest; the wiring is unbuilt.

The drift test is `TestCodexGuideGapSectionMatchesDeclarations` (`gaplist_test.go:40-77`): it renders the section fresh via `RenderGapSection`, reads the committed guide, extracts the byte span between the two markers via `generatedSectionBounds` (`gaplist_test.go:264-278`, which also fails if either marker doesn't appear exactly once), and compares byte-for-byte (`got != want`), reporting `firstDifference` (first differing line) on mismatch with the message `"the generated section of %s has drifted from the declaration table.\n%s\nRegenerate with:\n  %s"`. The `-update` flag is a package-level `flag.Bool("update", false, ...)` (`gaplist_test.go:39`) checked inside the same test function — when set, instead of asserting, it rewrites the file in place via `os.WriteFile` and logs either "already current" or "rewrote the generated section." Exact command to run, as named in the test's own `regenerateCmd` constant (`gaplist_test.go:32`):

```
go test ./internal/agentplan -run TestCodexGuideGapSectionMatchesDeclarations -update
```

Four more tests guard the same document from different angles: `TestCodexGuideCarriesEveryUnavailableReason` (`gaplist_test.go:82-99`) checks every unavailable Codex declaration's `Reason` string (whitespace-flattened) literally appears somewhere in the guide — this is what forces the *reason prose* itself, not just the generated section boundaries, to move off "not built" wording once rows 18/19 are removed from the unavailable set (their old reasons simply stop being checked, since `UnavailableFor` no longer yields them). `TestEveryCapabilityHasAGuideSubject` (`gaplist_test.go:106-124`) keeps `gapSubjects` (the reader-facing name table) in sync with the closed capability set — unaffected by this change since both capabilities already have subjects. `TestUnavailableForFiltersAndOrders`, `TestGapSectionSeparatesNoSuchConceptFromGaps`, `TestUnavailableForRejectsUnknownAgent`, `TestGeneratedSectionWrapsToTheGuidesWidth`, `TestWrapHangsContinuationsAndKeepsLongWordsWhole` round out the file but assert generic renderer properties (ordering, kind-splitting, fail-closed on unknown agent, wrap width) that this change doesn't specifically stress.

## Implications

Flipping rows 18/19 to `StateImplemented` will break, and require updating, at least these tests beyond the four the lead already named:

1. **`TestCodexColumnTotals`** (`internal/agentplan/capability_test.go:176-196`) — hardcodes `const wantImplemented, wantUnavailable = 13, 11`. Must become `15, 9`.
2. **`TestCodexColumnStatesWhatIsDelivered`** (`capability_test.go:203-231`) — checks every capability against two hand-maintained lists: `codexDelivered` (`capability_test.go:154-167`, a `[]Capability` of the 13 rows delivered today) and `codexFinalGaps` (`capability_test.go:130-141`, a `map[Capability]ReasonKind` of the "ten final gaps," which today still lists `NiwaPlugin: ReasonNotBuilt` and does *not* list `RootProjectSkills` at all — per the comment at `capability_test.go:118-124`, row 18 was deliberately left "pending on the side" of both lists after row 2's correction). Both `RootProjectSkills` and `NiwaPlugin` must move into `codexDelivered` and be removed from/never added to `codexFinalGaps`. Failure without the fix: `"capability %s is declared delivered for codex, but nothing here delivers it yet"` (if the declaration flips before this list updates) or `"capability %s is delivered to codex but declared unavailable"` (if this list updates before the declaration flips) — this test is itself a small drift-detector pinned to `declaration.go`, independent of `TestCodexColumnTotals`.
3. **`TestLookupAnswersEachDeclaredPair`** (`capability_test.go:76-104`) — has a literal test case `{"niwa's own debt for codex", NiwaPlugin, agent.AgentCodex, StateUnavailable, ReasonNotBuilt}` (`capability_test.go:88`) that will fail outright once `NiwaPlugin`/Codex flips to `StateImplemented`. Needs either updating to `StateImplemented`/`0` or swapping to a different still-`ReasonNotBuilt` example (there won't be any left, since these were the two `ReasonNotBuilt` rows — meaning after this change **no capability has kind `ReasonNotBuilt` for Codex**, so this row's whole label "niwa's own debt for codex" needs a different capability entirely, likely dropped or replaced by a same-shape case for a different reason kind).
4. **`TestBindingsMatchTheirDeclarations`** and **`TestBoundCapabilitiesAreInTheClosedSet`** (`binding_test.go`) — as detailed above, these are silent today on rows 18/19 (unbound, unlisted) but become load-bearing the moment `boundCapabilities`/`bindings` are extended for them, per the lead's mandate #3.

None of these four are in the lead's original "recent commits" pointer list, but all four are direct, mechanical consequences of the two-row flip and would fail `go test ./internal/agentplan/...` immediately if the declaration table changed without them — this is exactly the kind of "everything that would react" inventory item 1 asked for.

`TestEachAgentTakesOneScope` (`payload_test.go:107-127`) is a related but likely *unaffected* invariant worth flagging precisely because its name looks alarming next to declaration.go's row-18 comment ("giving the Codex payload layout a second scope"). This test pins `PayloadScope` behavior specifically for `PayloadPlan` (the MCP-servers/environment/posture document, rows 8/9/12) — it is not about skills delivery (`SkillsPlan`, which takes only a `Dir`, no `PayloadScope` at all — see `internal/agentplan/skills.go:67-76`). Whether rows 18/19's implementation needs to touch `PayloadScope`/`payloadLayouts` at all depends on the concrete delivery mechanism the other leads (`lead-layout-scope`, `lead-niwa-plugin`, `lead-skills-path`) are designing; from what's readable in `agentplan` alone, `SkillsPlan`'s `Dir` parameter is scope-agnostic (any caller-supplied directory), so a second call site passing the instance root as `Dir` would not by itself require touching `PayloadScope`. If the eventual design *does* reuse `PayloadPlan`/`payloadLayouts` for the plugin-manifest delivery (row 19, `NiwaPlugin`) rather than a bespoke writer, `TestEachAgentTakesOneScope`'s four-case table would need a fifth case for Codex-at-instance-root, and its doc comment's claim "Claude reads a project document at the instance root, and Codex reads a project layer only from a project root downward, which an instance root is not" would need revising — that sentence is exactly the now-corrected reasoning root_materializer.go's neighboring `payloadLayouts` comment (`payload.go:339-358`) already disclaims for the general case, but the test's own comment hasn't caught up to that correction and still states the old (false, per the corrected row 2/18 reasoning) claim.

## Surprises

- **Root-level project skills for Claude do not go through `agentplan.SkillsPlan` at all.** `internal/workspace/root_materializer.go` embeds a separate `rootSkillsFS embed.FS` (niwa's own hand-authored skills like `/dispatch`, materialized to `<workspaceRoot>/.claude/skills/<name>/`) via bespoke logic (`rootSkillsDir`, `rootSkillsTargetDir`, `rootSkillFileName` constants, `root_materializer.go:20-33`) that is entirely separate from the `PluginSkills` capability's producer (`skillsLayouts` in `agentplan/skills.go`, which only has a Codex entry and is used for repo/worktree-scoped *workspace-configured marketplace plugins*, not niwa's own bundled skills). This means "instance-root project skills" (row 18, capability `RootProjectSkills`) is a *third* distinct skills-delivery capability/mechanism, separate from row 5 (`PluginSkills`, repo-scoped workspace plugins) and separate from whatever row 1 (`WorkspaceOrientation`)/context composition does. Whatever the other leads design for Codex's instance-root skills will most likely need its own new writer or an extension of `root_materializer.go`, not a trivial second call to the existing `agentplan.SkillsPlan`/`skillsLayouts` machinery — worth flagging since the scan and binding mechanisms described above are agnostic to which shape this takes, but the shape determines exactly which `Delivery` name and which materializer/procedure get registered.
- The layout scan's context-filename exemption removal (`74c6a2e`) landed in the *same PR* as the four conversion sites it was meant to eventually catch, so the "window" was, by the commit's own account, "closed before it was committed" — it never actually caught a real violation in production history, only in the synthetic `TestContextFilenameScanReportsALiteral` fixture. Worth knowing in case anyone assumes this scan has a track record of catching real regressions; it has a proof-of-detection test, not field evidence.
- `codexFinalGaps`/`codexDelivered` in `capability_test.go` already anticipated exactly this two-row change: the comment at lines 118-129 explicitly names row 18 as "pending on the side" and cites `docs/prds/PRD-agent-capability-contract.md`'s amended matrix as the authority — meaning there is a PRD, separate from the guide, that also needs to already agree with (or be checked against) whatever final state this work produces, though nothing in `internal/agentplan` mechanically drift-tests the PRD the way `gaplist_test.go` drift-tests the guide.

## Summary
Four scans/drift tests directly govern this change as described (`TestWorkspaceNamesNoAgentConstant`, `TestWorkspaceNamesNoAgentContextFilename`, `TestBindingsMatchTheirDeclarations`, `TestCodexGuideGapSectionMatchesDeclarations`), all confirmed by reading their source in `internal/agentplan/layout_scan_test.go`, `binding.go`/`binding_test.go`, and `gaplist.go`/`gaplist_test.go`, plus the exact `-update` regeneration command and the two guide bullets that must vanish. Flipping rows 18/19 additionally breaks three tests the lead didn't name — `TestCodexColumnTotals`'s hardcoded 13/11 count, `TestCodexColumnStatesWhatIsDelivered`'s `codexDelivered`/`codexFinalGaps` lists, and a literal `NiwaPlugin` test case in `TestLookupAnswersEachDeclaredPair` — all in `internal/agentplan/capability_test.go`, all mechanical one-line-message failures once the declaration table changes. Build, vet, and `go test ./internal/agentplan/...` are all green today (baseline confirmed), and a genuine surprise worth carrying forward is that Claude's existing instance-root skills delivery is a bespoke `embed.FS`-based writer in `root_materializer.go` entirely outside the `agentplan.SkillsPlan`/`skillsLayouts` machinery used for repo-scoped plugin skills — so row 18's delivery is very unlikely to be a trivial second call into existing skills-producer code.
