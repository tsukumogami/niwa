# Lead: What discrete capabilities does niwa's workspace preparation deliver to a coding agent, and what governs each?

## Findings

niwa's preparation path delivers roughly twenty distinct capabilities, and they split cleanly into two families. A handful are genuinely agent-agnostic: file distribution (`[files]`/`[instance.files]`/`[root.files]`/global `[files]`), the generic `[env]` dotenv pipeline, git-exclude bookkeeping, and vault-backed secret resolution. Everything else is Claude Code-shaped at the point of materialization, and most of it is Claude Code-shaped by construction, not by an accident of a missing `if agent == codex` branch: the destination file is literally `.claude/settings.json`, the JSON keys are literally Claude Code's schema (`permissions.defaultMode`, `enabledPlugins`, `extraKnownMarketplaces`, `hooks.PreToolUse`), and one capability (`SupportsWorktreeHooks`) shells out to a binary literally named `claude`.

The `[claude]` table in `workspace.toml` (`internal/config/config.go:28-61`, `ClaudeConfig`) is the single config surface almost every one of these capabilities is declared under, and `ClaudeEnabled` (`internal/workspace/override.go:1061`) is the single gate almost all of them are conditioned on. Both carry the agent's name directly in the Go identifier and the TOML table name. Critically, `ClaudeEnabled` is not a narrow "install the Claude plugin marketplace" switch — `worktree_content.go:176-181` uses it to skip the **Hooks** and **Settings** materializers outright for any repo where it is false, and `apply.go:1516-1519` uses the identical bool to skip **repo-level context-file installation** (which is itself already agent-parameterized via `agent.Agent.LocalContextFileName()`). So a workspace running under `default_agent = "codex"` still gates its Codex-targeted content delivery behind a boolean spelled `claude.enabled`.

Separately, `agent.Agent` (`internal/agent/agent.go`) is a real, working discriminator — but it is wired into exactly two things: context-file naming (`RootContextFileName`/`LocalContextFileName`, used by `content.go` and `root_materializer.go:373-380`) and dispatch model-name resolution (`internal/cli/dispatch_model.go`). Every other materializer in `internal/workspace` — hooks, settings, plugins, marketplaces, remote-control, keep-alive, root skills, worktree-hook delegation — takes no `agent.Agent` parameter at all and writes unconditionally to Claude Code's file formats regardless of what `DefaultAgent` resolves to.

## Implications

The property "no agent constants at materializer call sites" currently fails almost everywhere outside `content.go`/`root_materializer.go`'s context-file writers and `dispatch_model.go`. `buildSettingsDoc` (`materialize.go:654`) is the worst offender by volume: one function that unconditionally emits `permissions`, `hooks`, `env`, `enabledPlugins`, `extraKnownMarketplaces`, `remoteControlAtStartup`, and `keepAliveOnDispatch` — seven of the twenty capabilities above — into a single Claude Code-shaped JSON document, called from three sites (`writeRootSettings`, `InstallWorkspaceRootSettings`, `SettingsMaterializer.Materialize`), none of which take an `agent.Agent` argument. A contract that routes agent-specific behavior would need `buildSettingsDoc` itself either to become agent-aware or to be replaced by an agent-keyed dispatch table that `SettingsMaterializer`/`writeRootSettings`/`InstallWorkspaceRootSettings` all call through.

`ClaudeEnabled` is a second, narrower problem: it is used as a generic "install anything for this repo" kill switch (contents + hooks + settings) even though its name and its TOML spelling (`[repos.X.claude.enabled]`) say it's Claude-specific. Any contract redesign needs to decide whether the on/off switch becomes agent-parameterized (`enabled_for = ["claude"]` or similar) or is renamed to something agent-neutral like `agent.enabled`, since today a Codex-targeted repo has no independent way to say "materialize my AGENTS.md but skip Claude's hook/settings machinery" — or the reverse.

For property 2 ("every capability is either implemented or explicitly declared unavailable with a reason"), the closed set to quantify over is the eighteen delivery capabilities in the table minus the two housekeeping/infra rows (git-exclude, vault resolution) that aren't agent-facing deliverables — call it a 16-capability set. A test enumerating "for agent X, for capability Y, either a materializer exists or a stub declares unavailability+reason" would immediately fail today for Codex against every row tagged "Inherently agent-specific? Yes" except the two context-file rows.

## Surprises

- **The niwa self-plugin installer and root-skill installer are the least agent-aware code in the whole path** — no `ClaudeEnabled` check, no `agent.Agent` parameter, not even a `[claude]` config gate. They run every single apply, for every agent, writing directly into `~/.claude/...` and `<root>/.claude/skills/...`. This is a stronger violation than anything gated by `ClaudeEnabled`, because there's no gate at all to reroute.
- **`SupportsWorktreeHooks` literally execs a binary named `claude`** (`harness_compat.go:37`) to decide a materialization branch. This is the most literal possible "agent constant at a materializer call site" — not a config field, a hardcoded process name.
- **MCP server configuration is not a capability niwa implements at all** — it is entirely an emergent use of the generic `[files]`/`[instance.files]`/`[root.files]` mechanism, per the lead's own candidate list. This is good news for the contract: it needs no agent-specific work, and any doc treating it as a discrete "capability" should instead cite it as the worked example of the generic-files escape hatch.
- **`agent.Agent` already has an unused generalization seam**: `WritesRepoLevelContext()` (`agent.go:80-87`) exists specifically because Codex's repo-level write was deferred, with a comment noting "the deferred repository-level Codex work may revisit the exact mechanism" — i.e., the codebase already anticipated needing a per-agent capability-availability declaration, just for one capability, not all sixteen.

## Open Questions

- Does `EphemeralSessionMode` (a root state flag, not a `workspace.toml` field) belong inside the closed capability set the same way as the `[claude]`-table capabilities, given it has no config-surface gate at all today — only an init-time CLI flag?
- Should "niwa's own plugin auto-install" and "root skill install" count as one capability (niwa-authored Claude Code plugin/skill delivery) or two, given they share no code path but share the same "unconditional, ungated, hardcoded `~/.claude`" shape?
- Is `[claude.env]` (settings-injected env) meant to collapse into the generic `[env]` pipeline under an agent-neutral contract, or does the "lands in the agent's own settings file" delivery mode deserve to stay a separate capability per agent?
- The lead asked specifically about `[claude]`-named booleans/tables as gates. `ClaudeEnabled`'s dual duty (contents + hooks + settings) wasn't explicitly on the candidate list — worth confirming with the team whether that scope creep is itself a defect the redesign should fix, independent of the multi-agent contract.

## Summary

niwa's preparation path delivers roughly eighteen agent-facing capabilities plus two agent-agnostic infrastructure mechanisms (file distribution, vault resolution), and nearly all of the agent-facing ones are declared under a `[claude]` TOML table and gated by a function literally named `ClaudeEnabled`, which conflates "install Claude Code machinery" with "install anything for this repo" including the already agent-parameterized context files. The single function `buildSettingsDoc` (`materialize.go:654`) is the biggest concentration of un-parameterized Claude-shaped output — seven capabilities, three call sites, zero `agent.Agent` arguments — while the plugin auto-installer, root-skill installer, and the worktree-hook-support probe (which execs a binary named `claude`) are ungated entirely and would need to become agent-aware from scratch rather than merely re-routed.
