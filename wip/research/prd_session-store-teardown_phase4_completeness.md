# Completeness Review

## Verdict: FAIL
The PRD is well framed and most requirements are testable, but several requirements have no acceptance criterion (including the most destructive failure mode, R12), a few behaviors an implementer must decide are left unspecified, and two layouts the research flagged (single-instance workspaces, several mappings sharing one instance) aren't addressed at all.

## Issues Found

1. **R12 has no acceptance criterion.** R12 covers the worst outcome the research found: a mapping write's `MkdirAll` recreating `.niwa/sessions` inside the swap's rename window, so the swap and its rollback both fail with ENOTEMPTY and `.niwa` holds only the mapping while the real snapshot sits in `.niwa.prev` until the next preflight deletes it. No AC checks that the configuration directory keeps its `workspace.toml` (or equivalent content) after a write lands mid-swap. Fix: add an AC that forces a mapping write into the target-to-prev / staging-to-target window and asserts the directory still holds its configuration content and the write either landed or was ordered after the swap.

2. **R10's second half is untested.** R10 says a mapping write "never fails because a refresh moved the directory under it" (the WriteFile-then-Rename ENOENT that makes a detached dispatch roll back and destroy its instance). The ACs only check that the mapping is present afterwards. Fix: add an AC that the write returns no error when a swap lands between its temp-file write and its rename, and that the dispatch that issued it exits 0.

3. **Several mappings can point at one instance, and teardown by session would act on all of them.** Research found `niwa list` picks the newest of several mappings for one instance (list.go:175-205), yet the PRD's Decisions section rests on "a dispatched instance belongs to one session." If two mappings share an instance, tearing down session A destroys worktrees that session B (possibly still live) is using. Fix: state what happens when the resolved instance has more than one mapping — refuse, warn, or act only if the other sessions are not live — and add an AC for it. At minimum, record it as a Known Limitation with the reasoning.

4. **Single-instance layout is not addressed.** Research flagged that when the workspace root is itself the instance, worktree lifecycle records would live in the root's rotated `.niwa/sessions`, alongside the mappings. That collides with R8 ("no subcommand treats the root mapping store as worktree records"), with the R5 ambiguity rule, and with the concurrency requirements (lifecycle records in a rotated dir). Fix: say whether single-instance workspaces are supported by this work, and if so how R8 and R5 apply there; if not, put them in Out of Scope.

5. **Worktree lifecycle records in instance config dirs have the same race, and the PRD is silent.** `niwa apply` refreshes each instance's configuration directory (apply.go:640), and `materializeAndSwap` carries `<instance>/.niwa/sessions` across the same way it carries root mappings. A `worktree create` or `destroy` writing a lifecycle record during an instance-level refresh can be lost or resurrected — which would also undo exactly what teardown just recorded ("marks the worktree record ended"). R10/R11 speak only of "session mappings." Fix: either extend R10/R11 to "session mappings and worktree lifecycle records," or name lifecycle records explicitly in Out of Scope / Known Limitations.

6. **R4 leaves handle-collision cases unspecified.** R4 requires uniqueness only for the prefix fallback. It doesn't say what happens when (a) two mappings record the same handle, or (b) one mapping's recorded handle equals an 8-hex prefix of a different, handle-less mapping's session id. The AC for "two such mappings the command refuses and names both" also has no backing clause in R4 (refusal and exit code live only in the AC). Fix: add to R4 that any value matching more than one mapping, by any route, is refused with both named and a non-zero exit, and add an AC for the recorded-handle-vs-prefix collision.

7. **R8 lets the implementer pick per command, and the AC inherits the vagueness.** "Either resolve per R1-R3 or fail with a message" means `attach`, `detach`, `apply`, `go` and `create` at the root could each go either way, and the AC can't fail. R8 also doesn't list `worktree create` (a `resolveInstanceRoot` caller), shell completion (`completeSessionIDs`, which returns empty at the root), or `runFromHookRemove`; and it's silent on the exit code of the "run inside an instance" message. Fix: decide per command in the PRD (a short table is fine) — for example destroy resolves by session, list/create/apply/attach/detach print the message and exit non-zero — and state the exit code. Say whether completion should offer session ids at the root. Resolve the Open Question on `list` rather than leaving it to the design.

8. **Output contract for scripts is not specified.** The script user story wants to distinguish "destroyed", "nothing to destroy" and "no such session," and never miss a kept-branch warning. R6 gives destroyed and nothing-to-destroy the same exit 0, and refusal and no-such-session the same non-zero exit, so a script has to parse human text whose wording no requirement pins down. There's no `--json`. Fix: either give distinct exit codes (e.g. a separate code for "no such session" versus guard refusal), or require stable, documented output lines for each outcome and kept branch (stdout vs stderr stated), and add an AC that checks them.

9. **Partial-failure ordering is ambiguous.** R6 says a guard refusal "exits non-zero after reporting which worktrees were and weren't destroyed," but doesn't say whether teardown continues to the remaining worktrees after the first refusal or stops. The AC ("reports which other worktrees (if any) were destroyed") passes either way. Fix: state continue-past-refusal (or stop) and make the AC use two worktrees where the refused one is processed first.

10. **Attach-refusal guard has no AC.** R2 names the attach refusal as one of the carried-over guards, but only the uncommitted-changes guard is tested. A finished worker whose worktree is still marked attached (for instance after a crash) is a realistic teardown case. Fix: add an AC, and say whether a stale attach from a dead session blocks teardown.

11. **R7 is incompletely specified and tested.** "Names an instance of the same workspace" doesn't say how the path is canonicalized (symlinks, `..`), and the AC only covers a path outside the workspace. A path inside the workspace that isn't an instance (the root itself, a repo directory, another group folder) is the more interesting case, since lifecycle listing there could read the wrong directory. The exit code for this case is also unspecified. Fix: define "instance of this workspace" (e.g. resolved path is a direct instance directory enumerated for this root), give the exit code, and add an AC for an in-workspace non-instance path.

12. **R9 overlay and global directories have no AC.** R9 explicitly extends the guarantee to overlay directories and the global configuration directory, but every concurrency AC exercises "one configuration directory" with a non-GitHub source at the root. Fix: add an AC (unit-level is fine) for concurrent refreshes of an overlay dir and of the global config dir, or narrow R9.

13. **GitHub-source refresh path has no AC.** Research found the GitHub no-drift branch rewrites the provenance marker non-atomically (O_TRUNC, no rename), so a concurrent refresh can read a partial marker or hit ENOENT on it. That's an "error caused by another command's refresh" under R9, but the ACs only use non-GitHub sources, and the marker isn't mentioned anywhere else (not in scope, not in Out of Scope, not in Known Limitations). Fix: add an AC for concurrent refreshes against a GitHub-style source in both drift and no-drift branches, or list the marker as a known limitation.

14. **R14 refresh-versus-refresh has no AC.** R14 says a slow fetch must not hold up another command's mapping write *or refresh*. The AC covers only the mapping write. Fix: add an AC that a second refresh completes its swap while the first's fetch is held.

15. **R15's bound is undefined.** "A bounded wait" has no value and no statement that it's configurable for tests; the AC "a command blocked past the bounded wait" can't be written without knowing it. The AC also drops the half of R15 that says the message must say another niwa command is using the directory. Fix: state the bound (or that the design sets it, with a test override), and extend the AC to check both parts of the message.

16. **No requirement against self-deadlock or crash leftovers.** Research noted the existing flock pattern contends within one process, and a dispatch refreshes twice and writes a mapping in the same process. Nothing requires that one command never waits on a lock it already holds. Likewise nothing says what happens when a command is killed mid-refresh: leftover staging and prev directories, and whether the next refresh recovers without manual cleanup. Fix: add a requirement that a single command never blocks on itself, and that a refresh interrupted at any point leaves the directory usable and is cleaned up by the next refresh, each with an AC.

17. **Other readers of a transient `.niwa` aren't addressed.** R13 protects the reaper, but research found other readers that treat an absent directory as empty or default. The ephemeral-session hook reads `EphemeralSessionMode` as false on any `LoadState` error, so a session started mid-swap silently gets no instance. `config.Discover` can walk up to an enclosing workspace. Teardown's own resolution reads the mapping store, so a destroy run mid-swap would print "no such session" and exit non-zero, a false negative a script would log as a failed lookup. Fix: either extend R13's guarantee to teardown resolution and the hook's mode read, or list these readers in Known Limitations.

18. **R16 macOS and R17 lack ACs.** The AC runs tests on Linux only, though R16 promises the guarantee on macOS and CI already runs `go test -race` there. R17's "no new dependency" and "no new prompts" have no check, and "documented where the fallback is defined" has none either. Fix: extend the last AC to `go test -race ./...` on macOS, and add a check that `go.mod` gains no new module requirement.

19. **`--by-path` regression isn't covered.** R1 keeps `--by-path` working, but no AC runs it after the change. Fix: add an AC alongside the worktree-id regression AC.

## Suggested Improvements

1. **Say what teardown does not touch.** State that teardown by session never deletes the mapping, the instance, or the instance's repo clones, and that running it twice is safe (the second run reports nothing to destroy). Scripts depend on this ordering with `niwa reap`, and it's currently only implied.

2. **Address the instance-name id.** A developer who got their list from `niwa list` holds instance names, not session ids (and `niwa list --json` carries neither id nor handle). Either accept an instance name, or state in Out of Scope that instance names and display session names aren't accepted and point to `claude agents --json` as the source of ids.

3. **Add user stories for the handle-less and Codex cases.** The ephemeral-hook session (no recorded handle) and a Codex session (handle equals session id) each have requirements and a decision but no user story, which makes it easy to lose them in the design. A developer who has already run `claude rm` is the concrete person behind the prefix fallback.

4. **Tie the "no niwa-managed worktree" wording to the Known Limitation.** The limitation says the message "must not imply the worker's branches were checked," but that's not a requirement and has no AC. Promote it into R6 and check the message text in the zero-worktree AC.

5. **Mark which ACs must fail on pre-fix code.** R18/R19 require fail-before tests, and some ACs say so, but the reaper AC and the root-level `worktree list/apply/...` AC don't. Stating it per AC keeps a test that passes either way from sneaking in.

6. **Tighten Out of Scope for `niwa list --json` and completion.** Adding session id/handle to `niwa list --json` is the obvious follow-on a reviewer will ask for; say it's out, or in.

## Summary
The teardown half is close: the id forms, ambiguity rule and outcome set are well chosen, but R4, R6, R7 and R8 each leave a case the implementer has to guess, the script-facing output contract is unstated, and the multiple-mappings-per-instance and single-instance layouts can make teardown act on the wrong worktrees. The concurrency half has the bigger hole: R12's catastrophic case, R10's write-failure case, R14's refresh-vs-refresh case and R9's overlay/global scope have no acceptance criteria, lifecycle records in instance config dirs share the same race without being in or out of scope, and there's no requirement against self-deadlock or crash leftovers. All of these can be fixed in the PRD without changing its direction.
