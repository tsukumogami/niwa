# Lead: How does the Codex plugin-skills delivery run end-to-end today, and what in that path is repository-shaped rather than directory-shaped?

## Findings

### 1. Capability declaration: row 18 already names the exact gap and the fix shape

`internal/agentplan/declaration.go:281-302` (Row 18, `RootProjectSkills`) declares Claude implemented, Codex `StateUnavailable`/`ReasonNotBuilt`, with a reason string and an inline comment that is unusually specific about the fix: "Delivering it means giving the Codex payload layout a second scope -- it is bound to the repository scope alone today -- and that is a change to what niwa writes rather than to what it claims, so it belongs with the rest of the instance-root project layer." This confirms the lead's framing is already the maintainers' own diagnosis, not a new hypothesis. `internal/cli/dispatch.go:395-403` reads this exact row today to print a warning at `niwa dispatch` time ("the worker starts at the instance root... none of the workspace's skills, MCP servers or posture... reach it only from inside a repository"). Note the dispatch warning is deliberately worded wider than skills alone -- MCP and posture are separate gaps this lead does not need to close.

### 2. Config -> marketplace materialization -> `ResolvePluginTrees`

- `internal/workspace/pluginskills.go:113-153` `ResolvePluginTrees(ctx, PluginSkillsInputs)` takes `InstanceRoot`, `Plugins []string`, `Marketplaces config.MarketplaceConfigs`, `RepoIndex map[string]string`, `Fetcher`. It resolves each configured plugin entry to a `agentplan.PluginTree{Name, Root}` via `marketplaceRoots` (pluginskills.go:160-201) and `resolvePluginRoot` (pluginskills.go:305-366).
- Two marketplace source kinds: `repo:`-sourced (resolved through `RepoIndex`, a clone already on disk in the workspace) and github-sourced (fetched into `<instanceRoot>/.niwa/marketplaces/<name>` via `ensureMarketplaceContent`, pluginskills.go:211-270).
- **Not repository-shaped in itself**: none of this reads or writes into the *destination* tree at all -- it only reads marketplace manifests and populates a niwa-owned cache under `<instanceRoot>/.niwa/marketplaces/`. `instanceRoot` here is the *workspace instance root*, which already exists and is fully available when a session is also started at that same root -- resolution needs no change for a root delivery.
- `instanceRepoIndex(instanceRoot)` (pluginskills.go:433-459) builds the same `RepoIndex` map by walking `<instanceRoot>/<group>/<repo>` directories, skipping dot-directories. This is the function used by the worktree path (`worktree_content.go:583`) precisely because it has no live "classified repos" list to reuse. A root-scoped call could reuse the same function or the apply path's own `repoIndex` built for the classified-repo loop (`apply.go:1649` uses the latter).

### 3. `agentplan.SkillsInputs` / `SkillsPlan` / `SkillsReconcileSpec` (agentplan/skills.go)

- `SkillsInputs{Dir, Plugins}` (skills.go:67-76) -- **no scope field**, and the doc comment for `Dir` is literally "a cloned repository, or a worktree of one" (skills.go:69-71). This is prose narrowing, not an enforced constraint: nothing downstream actually checks that `Dir` is a git repo.
- `skillsDir(dir)` (skills.go:101-109) is a pure `filepath.Join(dir, layout...)` -- agnostic to whether `dir` is a repo, a worktree, or an arbitrary directory. **Directory-shaped, not repository-shaped.**
- `SkillsPlan` (skills.go:122-154) builds one `Entry{Op: OpDeliverTree, ...}` per resolved plugin tree, gated only on `p.delivers(PluginSkills)` (the agent's own declaration-table gate) and `skills != ""` (i.e., this agent has a non-nil layout, currently only `AgentCodex`). Nothing here inspects `Dir` for repo-ness.
- `ExcludeAs: excludePattern(in.Dir, path)` (skills.go:149) is `filepath.Rel(root, path)` in slash form (context.go:436-441) -- a pure string computation, no filesystem/git access. It is only ever *consumed* later by `gitexclude.EnsureRepoExclude`, which is where repo-shape actually matters (see §5).
- `SkillsReconcileSpec` (skills.go:183-200) is likewise a pure function of `Dir` + configured plugin names + the producer's own `gateClosed` state. No repo assumption.
- Entries are deliberately **not Managed** (skills.go:118-121 doc comment, confirmed empirically: `InstallRepoSkills`'s returned `Delivered` paths are never appended to `apply.go`'s `writtenFiles` slice, so they never reach `hashManagedFile`/`ManagedFile` tracking at `apply.go:1963-1976`). Reconciliation is the only cleanup mechanism, and it runs fresh on every `InstallRepoSkills` call keyed by the `Dir` passed in that call.

### 4. `InstallRepoSkills` / `reconcileSkillsDir` (workspace/pluginskills.go:475-563)

- `InstallRepoSkills(repoDir, trees, producer)` (pluginskills.go:482-511): builds `SkillsInputs{Dir: repoDir, Plugins: trees}`, calls `reconcileSkillsDir(producer.SkillsReconcileSpec(in))` first (removes stale deliveries), then `producer.SkillsPlan(in)`, then `applyPlan(plan)`. The parameter is literally named `repoDir` but is only ever used as a path -- same conclusion as above.
- `reconcileSkillsDir` (pluginskills.go:522-563): `os.ReadDir(spec.Dir)`, `os.Lstat` per entry, removes symlinks unconditionally and directories that carry the `.niwa-delivered-tree` sentinel (`treeCopyIsNiwas`), warns and leaves anything else alone. Pure filesystem, zero git/repo dependency.
- The function explicitly disclaims a containment check "unlike the content installer's" (pluginskills.go:493-498) because a delivery is meant to be a symlink *out of* the tree by design -- this reasoning is unaffected by whether the tree is a repo.

### 5. `OpDeliverTree` execution (workspace/applyplan.go:286-340ish, `deliverPlanTree`)

- Pure filesystem: `filepath.Abs(source)`, `os.MkdirAll(dir(path))`, `os.Lstat(path)`, then symlink-or-copy. **Zero git/repo dependency** -- confirmed by reading the full function body.
- Symlink is the default everywhere except Windows (`treeDeliveryPrefersCopy`, applyplan.go); copy is the fallback when the symlink write fails, walking up to `treeCopyMaxLinkHops` (4) internal symlink hops.
- Idempotency: existing symlink pointing at the right source is a no-op (`treeLinkTargets`); existing symlink pointing elsewhere is removed and relinked; existing directory is verified as niwa's own (via the sentinel) before being wholesale replaced; anything else at the path fails the whole apply with `errForeignDeliveryTarget`.
- Permissions: `mode` (`skillsTreeMode = 0o755`, skills.go:29) is only used by the copy-fallback path (`copyTree(source, path, mode, ...)`); a symlink carries no mode of its own.
- **Conclusion: this step is fully directory-shaped already. It would behave identically writing into `<instanceRoot>/.codex/skills/<plugin>` as into `<repoDir>/.codex/skills/<plugin>`.**

### 6. Reconcile (de-configured plugin removal)

Covered above (§3, §4): keyed purely on `spec.Dir` + `spec.Keep` (the currently-configured plugin names) + the marker/symlink shape test. No git or repo dependency. Runs once per `InstallRepoSkills` call, so a root-scoped call site gets the same cleanup guarantee for free as soon as it exists.

### 7. `Entry.ExcludeAs` / git-exclude consumption -- the one step that IS repo-shaped, but safely so

- `ExcludeAs` values collected per repo into `contentExcludes[repoDir]` (`apply.go:1664`, `worktree_content.go:595`) are consumed by `gitexclude.EnsureRepoExclude(repoDir, excludeExtras...)` (`apply.go:1873`, `worktree_content.go:703`).
- `gitexclude.EnsureRepoExclude` (`internal/gitexclude/exclude.go:37-79`) resolves `commonDir, err := gitCommonDir(tree)`; on `errNotGitRepo` it **returns nil -- a silent no-op** (exclude.go:56-59, and documented at exclude.go:19 "so there is no git status to keep clean and EnsureRepoExclude is a no-op"). So calling this against a non-git `instanceRoot` today would not error; it would simply do nothing.
- But the instance root is *not* left uncovered for git purposes generally -- it has its own, separate, directory-shaped mechanism: `EnsureInstanceGitignore(instanceRoot, agentplan.InstanceExcludePatterns()...)` (`apply.go:446` and `apply.go:622`, implemented at `workspace/gitignore.go:42-79`). This writes a plain `.gitignore` *file* at `<instanceRoot>/.gitignore` -- not `.git/info/exclude` -- specifically because "the instance root is a non-git directory itself, but users frequently place it inside a larger tracked working tree" (gitignore.go:31-34) and the pattern is meant to be inherited by an outer tracked tree, not by the instance root's own (nonexistent) git status.
- **Important scoping detail**: `agentplan.InstanceExcludePatterns()` (`agentplan/sessionenv.go:150-189`) is explicitly limited to *secret-bearing* generated configuration (the MCP/session-env payload names) -- "Context documents are not here: they carry orientation prose, not credentials" (sessionenv.go:159-161). A delivered skills tree is neither a secret nor a niwa-generated single file (it's a symlink to plugin content that already lives in the workspace's own marketplace clone or cache), so it plausibly does **not** need to appear in this list at all -- there is no secret-staging risk from a symlink to already-public plugin content, unlike the MCP/session payload files this list protects.
- If a root delivery still wants explicit git-ignore coverage for tidiness (e.g. so `.codex/` at the root doesn't show as untracked in an outer tree), the existing `EnsureInstanceGitignore` call already runs unconditionally at every apply (`apply.go:446`, `apply.go:622`) and would just need `.codex/skills`-shaped patterns added to its `extra` set the same way MCP payload patterns are today -- no new mechanism required.

### 8. `AgentEnabled` gating -- workspace-level gate already used at the instance root today

- `AgentEnabled(ws *config.WorkspaceConfig, repoName, agentName string) bool` (`workspace/override.go:1083-1109`): resolution order is per-repo override, then the workspace-level `[claude]`/`[codex]` block, then default-enabled. When `repoName == ""` there is by construction no repo override to look up (`ws.Repos[""]` will never match a real repo), so it degrades exactly to the workspace-level gate.
- **This is already exercised at the instance root today**: `apply.go:1702` -- `producer := agentplan.For(ag).Gated(AgentEnabled(effectiveCfg, "", string(ag)))` -- used for Step 6.3's root-scope MCP/session-env/posture payload (`InstallPayloadConfig` with `Scope: agentplan.PayloadAtInstanceRoot`, apply.go:1724-1737). The comment right above it (apply.go:1699-1701) states the rationale explicitly: "The instance root belongs to no repository, so the gate that applies here is the workspace-level one -- the same lookup, asked with no repository name." **A root-scoped skills delivery would reuse this exact call verbatim** (`AgentEnabled(effectiveCfg, "", string(ag))`), with no new gating logic needed.

### 9. What `apply.go` installs at `instanceRoot` today, per agent -- the precise delta

Walking Step 5-6.6 of `apply.go`:
- Step 5 (~1540-1608): workspace-level orientation context (`workspace-context.md`, overlay, global CLAUDE content) -- directory-shaped, written once at the instance root, agent-agnostic prose.
- Step 5b/5c: root settings files, group content, global CLAUDE.md.
- Step 6 (1610-1636): **repo-level** orientation documents -- looped over `classified` (configured repos) only; `instanceRoot` itself never appears as a `repoDir` in this loop.
- Step 6.2 (1638-1666): **plugin skills delivery** -- looped over `classified` only, via `InstallRepoSkills(repoDir, pluginTrees, producer)`. **This is the step with no instance-root counterpart at all today.** `ResolvePluginTrees` itself (1645-1651) is called once, agent/repo-agnostic, so it already has everything needed; only the per-repo delivery loop is missing a root-scoped sibling.
- Step 6.3 (1668-1764): MCP servers + session env + posture, generated **both** at the instance root (`PayloadAtInstanceRoot`, 1724-1737, gated by `AgentEnabled(effectiveCfg, "", ...)`) **and** per repo (`PayloadInRepo`, 1744-1763). This is the one capability that already has the "second scope" the row-18 comment describes -- it's the template to copy.
- Step 6.4-6.6: worktree-delegation hook wiring, per-repo git-exclude bookkeeping (1850-1876, only over `classified`), directory-trust delivery (only over `classified` repo roots), worktree-env refresh. None touch `instanceRoot` as a delivery target for skills.

So: **today, the instance root gets orientation context and payload config (MCP/env/posture) for every agent, gated by the workspace-level `AgentEnabled` call -- but it gets no plugin-skills delivery at all, for any agent, because Step 6.2's loop only iterates `classified` repos.** Adding root skills delivery for Codex is precisely: call `InstallRepoSkills(instanceRoot, pluginTrees, agentplan.For(ag).Gated(AgentEnabled(effectiveCfg, "", string(ag))))` once per agent, alongside (or folded into) the existing Step 6.3 root loop, using the `pluginTrees` already resolved once at 1645-1651.

## Implications

1. **The whole `OpDeliverTree` execution path, `SkillsPlan`, `SkillsReconcileSpec`, and `reconcileSkillsDir` are already directory-shaped, not repository-shaped.** No code in this path inspects `.git`, calls `git`, or assumes a configured repo. The `Dir` doc comment on `SkillsInputs` ("a cloned repository, or a worktree of one") is aspirational/narrowing prose that happens to be true of every caller today, not an enforced invariant -- it can be widened to include the instance root with a one-line comment update, no code change to `agentplan/skills.go` itself required.
2. **The only genuinely repo-shaped consumer in the whole chain (`gitexclude.EnsureRepoExclude`) already no-ops safely on a non-git directory**, and the instance root already has its own parallel, correctly-scoped mechanism (`EnsureInstanceGitignore`) for the one thing that actually needs covering there (secret-bearing generated files). Skills delivery likely needs no new exclude coverage at all, since a symlink to already-installed plugin content carries no secret material; if desired for tidiness, it's an `extra` pattern on an already-unconditional call.
3. **`AgentEnabled` already has, and already uses, a workspace-scope (empty repoName) mode exactly suited to gating a root delivery** -- apply.go:1702 is the precedent to copy verbatim, not a new mechanism to design.
4. **The fix is additive and narrow**: add one more per-agent loop at the instance root (mirroring Step 6.3's existing `PayloadAtInstanceRoot` loop, or literally extending it) that calls `InstallRepoSkills(instanceRoot, pluginTrees, agentplan.For(ag).Gated(AgentEnabled(effectiveCfg, "", string(ag))))`. `pluginTrees` is already resolved once per apply and is agent/repo-agnostic, so no change to `ResolvePluginTrees` or `PluginSkillsInputs` is needed. The declaration table (`declaration.go:298-301`) needs its row-18 Codex entry flipped from `StateUnavailable/ReasonNotBuilt` to `StateImplemented`, and the `dispatch.go:402` warning (keyed on that row) would then stop firing for Codex once skills are the only thing it covers -- but note that warning's own text also mentions "MCP servers or posture," which **are already delivered at the root** (Step 6.3) even while the warning fires, so the warning's wording may already be slightly stale/overbroad independent of this fix; worth flagging to whoever writes the row-18 correction, since the row only ever claimed to cover skills.
5. **The worktree path (`worktree_content.go`) is a second, independent call site** with its own `InstallRepoSkills(worktreePath, pluginTrees, gated(ag))` (worktree_content.go:590) and its own `ResolvePluginTrees` call (579-584, using `instanceRepoIndex` instead of the apply path's `repoIndex`). This is out of scope for the lead (worktrees are already a repo-shaped concept, and a Codex session started inside a worktree already gets skills per row 18's *implemented* Claude precedent and would get them for Codex too once `skillsLayouts` covers it) but is worth noting as a parallel, not the root-delivery path -- fixing the root gap does not touch this call site.

## Surprises

- **The fix is already fully diagnosed in a code comment.** `declaration.go:283-296` reads like a mini design note for exactly this lead, written by whoever last touched row 18 -- it even names the "second scope" framing and explicitly defers the work rather than doing it inline. This is not a fresh discovery so much as confirmation that the codebase already agrees with the lead's premise.
- **Skills entries are deliberately excluded from the managed-file tracking system** (`ManagedFile`/`hashManagedFile`), which means there's no state-file plumbing to extend for a root delivery -- reconciliation is self-contained per `InstallRepoSkills` call and needs nothing added to `InstanceState`.
- **The declaration comment's phrase "Codex payload layout" is slightly imprecise/conflated language** -- there is no unified "payload layout" shared between skills and MCP/session-env; those are two separate mechanisms (`skillsLayouts` in `agentplan/skills.go` vs. `payloadLayout`/`PayloadScope` in `agentplan/payload.go`). The *pattern* to replicate (a second scope value, gated the same way) is the same, but literally reusing `PayloadScope`/`payloadLayout` machinery for skills would require either extending `SkillsInputs` with a scope-like field or (more consistent with the current zero-config `Dir`-is-just-a-path design) simply calling `InstallRepoSkills` again with `instanceRoot` as `Dir` -- no scope enum needed, since nothing in the skills path currently branches on scope at all.
- `gitexclude.EnsureRepoExclude`'s silent no-op on non-git trees (rather than an error) means a root delivery that *does* eventually want `.git/info/exclude`-style coverage (e.g. if the instance root is later made git-tracked by a user) would get it for free/no-op safely either way -- there's no failure mode to guard against here.

## Open Questions

1. Should root-delivered skills reuse the exact same `pluginTrees` resolved for the classified-repos loop (no per-scope filtering), or could a workspace want a different plugin set at the root vs. inside repos? Nothing in the current config schema (`Plugins []string` is workspace-wide, not scope-qualified) suggests scope-specific plugin sets are a concept today, so the straightforward answer is "same set, same trees, no new config surface" -- but this is a product decision, not something the code settles on its own.
2. Does the `.codex/skills` directory at the instance root need any `.gitignore`/exclude coverage at all, given the reasoning in §7 that it carries no secret material? If the answer is "yes, for tidiness," where should that pattern be declared -- as a new `agentplan.Producer` method analogous to `InstanceExcludePatterns()`, or just inlined as a literal extra pattern in `apply.go`'s existing `EnsureInstanceGitignore` call?
3. The row-18 declaration and the `dispatch.go:402` warning both currently bundle "skills, MCP servers, posture" together in prose even though MCP/posture are *already* delivered at the root (Step 6.3) while skills are not. Once skills are fixed for Codex, does the warning need to be re-scoped/removed entirely for Codex, or does some other still-real root-vs-repo gap for Codex remain that keeps the warning relevant? This wasn't chased down in this pass and would need its own lead if pursued.
4. Whether `deliverableName`/`checkContainment`-style safety checks need re-examination for a delivery target that is the instance root itself (vs. a repo subdirectory) -- reading the code, they don't (name safety is about the *plugin name* becoming a path element, unrelated to what directory it's joined onto), but this is worth a second pair of eyes given how much of niwa's security posture (`DirectoryTrust`, containment checks) is otherwise repo-scoped.

## Summary

Every mechanical step in the Codex skills-delivery path -- `SkillsPlan`, `SkillsReconcileSpec`, `reconcileSkillsDir`, and `OpDeliverTree`'s symlink/copy executor -- is already directory-shaped with zero git or repo-configuration dependency; the only repo-shaped piece (`gitexclude.EnsureRepoExclude`) already no-ops safely on a non-git tree, and the instance root already has its own correctly-scoped `.gitignore` mechanism plus a precedent for workspace-level `AgentEnabled` gating (`apply.go:1702`) used today for the sibling MCP/session-env payload delivery at `PayloadAtInstanceRoot`. The implication is that closing row 18 for Codex is a small, additive change -- one more per-agent call to `InstallRepoSkills(instanceRoot, pluginTrees, agentplan.For(ag).Gated(AgentEnabled(effectiveCfg, "", string(ag))))` inside `apply.go`'s existing Step 6.3 root loop, plus flipping the declaration-table row -- not a rework of the delivery mechanism, which `declaration.go`'s own inline comment already anticipated. The biggest open question is whether the currently-bundled dispatch-time warning (which mentions MCP/posture alongside skills, even though MCP/posture already reach the root) needs its own follow-up once skills are fixed, since it wasn't chased down in this pass.
