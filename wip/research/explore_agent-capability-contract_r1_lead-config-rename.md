## B. Rename & Alias Precedent

niwa has one directly on-point precedent: **`[content]` → `[claude.content]`**, commit `81aae0b` *"feat(config): rename [content] to [claude.content] (#51)"*, designed in `docs/designs/current/DESIGN-claude-key-consolidation.md`.

**The mechanism, precisely (cite-able):**

1. **Compatibility alias, not silent accept, not hard break.** Both the old key (`[content]`) and the new key (`[claude.content]`) are accepted; using the old form emits a **warning**, not an error. Using **both simultaneously is a hard parse error** — no silent precedence rule. Design doc explicitly rejected the two alternatives: hard-break-immediately ("painful short-term") and silent-accept-no-warning ("the deprecation never surfaces to users; they never migrate") — `DESIGN-claude-key-consolidation.md:120-140`.
2. **Deprecation window is a version line, not a time window.** "until v1.0" — niwa is pre-1.0, and 1.0 is the documented line for locking the schema (`DESIGN-claude-key-consolidation.md:136-137`; also `config.go:57-59`, `:527`).
3. **Where the alias lives:** on the struct itself, as a second field with a different TOML tag, not a separate compat-shim file. `WorkspaceConfig.Content ContentConfig` (deprecated) sits alongside `WorkspaceConfig.Claude.Content` (canonical) — `config.go:244-245` (`Content` and `Claude` are sibling fields). Detection is a **zero-value struct comparison after `toml.Decode`**, not the BurntSushi `md.IsDefined(...)` metadata API — the design doc considered and rejected the metadata-walk approach as more complex for no benefit (`DESIGN-claude-key-consolidation.md:223-243`). The actual migration logic is `config.go:513-528` inside `Parse()`:
   - both non-zero → error: `"config uses both [content] and [claude.content]; pick one -- [claude.content] is canonical, [content] is deprecated"`
   - old only → copy into new, clear old, warn: `"[content] is deprecated; use [claude.content] instead (removed at v1.0)"`
   - new only / neither → no-op.
4. **Override-position leakage is closed at the type level, not by runtime validation.** Before the rename, adding `Content` to the single `ClaudeConfig` type would have let `[repos.<name>.claude.content]` parse silently and get dropped by the merge pipeline (content never merges). The fix was splitting `ClaudeConfig` (workspace-level, full) from a narrower `ClaudeOverride` (repo/instance/global-override level, no `Content`, no `Marketplaces`) so the TOML decoder's own `md.Undecoded()` unknown-field warning catches misuse "with no runtime validation needed" (`DESIGN-claude-key-consolidation.md:143-196`; `config.go:22-27`, `63-68`). This is the pattern to reuse for any rename that also needs to stay out of the override cascade.
5. **Warnings ride existing plumbing.** No new warning channel was built — deprecation and unknown-field warnings both append to `ParseResult.Warnings`, the same list `Parse()` already returns (`config.go:511`, `:526-527`, `:545-547`).
6. **Test coverage shape**: unit tests for deprecated-migrates, both-forms-error, and canonical-no-warning paths, plus a functional feature exercising the same three scenarios end-to-end through `niwa create` (commit message, `81aae0b`).

**Docs/schema surface that needs updating alongside a rename:** there is **no `*.schema.json`** anywhere in the repo (searched exhaustively) — config shape is documented, not schema-validated. The doc that would need a parallel edit is `docs/designs/current/DESIGN-workspace-config.md` (has a full `[claude.content...]` example block at lines 130-163 and 434-446) plus the README scaffold example and `internal/workspace/scaffold.go` (which literally writes `content_dir = "claude"` into new workspace.toml files at `scaffold.go:16,151` — a generated-file surface a rename must also touch, confirmed by the PR #51 commit message: *"the `niwa init` scaffold, README, and `DESIGN-workspace-config.md` show the canonical form"*).

There is a second, unrelated skill also named "migrate-config" (`internal/plugin/files/niwa/skills/migrate-config/SKILL.md`) — it's about migrating a workspace **config source's repo layout** (rank-2 whole-repo → rank-1 `.niwa/` subtree), not about renaming a TOML key inside workspace.toml. Not relevant to this precedent; noted so it isn't confused with the actual rename mechanism above.

## Implications

- Any rename of `claude.enabled` (or a future split of `[claude]` hooks/settings/env per-agent) has a ready-made, cited pattern to follow: sibling field + zero-value detection + hard-error-on-both + warn-on-old + version-gated removal (v1.0) + type-level leakage guard via override-position type splitting.
- `content_dir` is unfinished business from the *same* design doc that established this precedent — it's the cheapest first target for whoever picks up the capability-contract work, since the design already scoped it and the mechanism is proven.
- The dispatch/attach/stop/continuation binary-launch seam (`exec.LookPath("claude")` at four call sites) is a bigger structural gap than any single config key: even if every config key were renamed agent-neutral, dispatched sessions still can't run as Codex today. This is likely out of scope for a config-rename contract narrowly, but it's the thing that would make "no agent's name gates another agent's delivery" actually true end-to-end, and the design should at least name it as a known gap rather than let the config-level fix imply full agent parity.

## Surprises

- The codebase already has a clean, per-agent-branching pattern (`dispatch_model.go`'s `modelCategoriesByAgent`/`agentBinaryName` maps) sitting right next to code that hardcodes `"claude"` as a literal with no agent branch at all (`dispatch_launcher.go`, `watch.go`). The contract design doesn't need to invent the pattern — it needs to propagate an existing one.
- `EnvMaterializer` (agent-neutral `[env]`) is deliberately *not* gated by `ClaudeEnabled`, while `HooksMaterializer`/`SettingsMaterializer` are. That asymmetry is already correct today (env is agent-neutral, hooks/settings are Claude-Code file formats) and is worth preserving as a design constraint: any future per-agent hooks system should NOT get folded into the existing `claude.enabled` gate, precisely because that gate is what the mandate warns about.
- `DESIGN-claude-key-consolidation.md` already used the word "coupling" to describe `ClaudeEnabled` in passing, months before this lead was asked — the prior design authors saw the shape of this problem and chose not to act on it beyond the `content_dir` deferral.

## Open Questions

- Does `internal/agent` (or a sibling) need its own `LaunchBinary(Agent) (string, error)` seam so dispatch/attach/stop/continuation can be tested against "the launched binary matches the resolved agent," the way `agentBinaryName` already exists for warning text only? This wasn't asked for directly but is the most testable structural property adjacent to the lead.
- Should `claude.enabled` be renamed now (`content.enabled`? `repo.enabled`?) preemptively, or left alone until a second agent actually needs repo-level hooks/settings, given YAGNI vs. "a missed misnamed gate becomes a shipped bug"? The precedent (`content_dir`) suggests deferral risks the debt never getting paid.

## Summary

The one real misnamed-gate risk is `claude.enabled` (`config.go:29`, read via `ClaudeEnabled()` at `override.go:1061`): it's correctly named today because it only gates genuinely Claude-Code-owned artifacts (CLAUDE.local.md, hooks, settings), but the codebase's own design doc already flagged it as evidence of coupling, and it becomes exactly the mandate's cautionary example the moment repo-level hooks/settings exist for another agent. niwa has one precise, citable rename precedent — `[content]` → `[claude.content]` (commit `81aae0b`, `DESIGN-claude-key-consolidation.md`): accept both keys, warn on the deprecated one, hard-error if both are set, remove at the v1.0 line, with override-position leakage closed via a type split rather than runtime checks — and that same design doc left a second rename (`content_dir`) deliberately unfinished, which is the cheapest immediate test case for the pattern. No JSON schema exists to keep in sync; only `DESIGN-workspace-config.md`, the README, and `internal/workspace/scaffold.go`'s generated example need to move in lockstep with any future rename.
