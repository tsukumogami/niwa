# Lead: Where should niwa's own embedded plugin tree be materialized so a Codex session can reach it, and how should that delivery be structured and bound?

## Findings

### 1. What `plugin.Install` actually does today (Claude path)

`internal/plugin/installer.go` (`Install`, `stageAndRename`, `writeEmbeddedTree`) copies the embedded tree at `internal/plugin/files/niwa/` (root `manifest.json` + `skills/migrate-config/SKILL.md`) into `~/.claude/plugins/marketplaces/niwa/` -- the developer's **global** home, not anything instance-scoped (`internal/plugin/embed.go:58-80`, path computed from `os.UserHomeDir()`).

- It is idempotent by design: `readInstalledManifest` reads the on-disk `manifest.json`'s `Version` and compares to the embedded one (`installer.go:100-113`); equal versions short-circuit to `UpToDate` with no filesystem writes.
- The actual write is atomic stage-and-rename: write to `<installPath>.next`, move existing install to `<installPath>.prev`, rename `.next` over `installPath`, best-effort `RemoveAll(.prev)`. Crash-safe rollback on any step failure (`installer.go:130-176`).
- `SkipInstall` (wired from `--no-install-plugins` or `auto_install_plugins = false`) short-circuits before any filesystem read/write and just emits `NoticeIDPluginSkipped` (`installer.go:83-87`).
- **It records nothing in `InstanceState`.** `state *InstanceState` is accepted only to satisfy `EmitPluginNotice`'s nil-state contract (notice bookkeeping); no field of `InstanceState` tracks that the plugin was installed or where. The only durable record is the plugin's own `manifest.json` on disk, read back next time for the version comparison.
- `writeEmbeddedTree` is a generic `fs.WalkDir` copy of the whole embedded tree -- it copies whatever is under `files/niwa`, sight unseen. Adding a file to the embedded tree requires no installer code change.

### 2. When `InstallNiwaPlugin` actually fires -- narrower than "every apply"

All five call sites (`internal/workspace/apply.go:524-525, 692-693, 1064-1065, 1093-1094`, plus one more in the overlay-rank branch) call `a.InstallNiwaPlugin(nil, a.Reporter, a.SkipPluginInstall)` **only inside a `teamConfigRank == 2` or `overlayRank == 2` branch** -- i.e. only when niwa detects a deprecated rank-2 (whole-repo) config source and is about to emit the rank-2 deprecation notice. It is not installed unconditionally on every `niwa create`/`niwa apply`. This is distinct from `PrewarmDeclaredPlugins`, which does run on every provisioned instance (`apply.go:127-135`).

The wiring itself is a bare function-field seam, not the `procedure`/`Materializer` interfaces described below: `Applier.InstallNiwaPlugin func(state *InstanceState, reporter *Reporter, skipInstall bool)` (`apply.go:116-122`), populated by `internal/cli/plugin_adapter.go:14-16` (`installNiwaPluginAdapter`), which every CLI surface that constructs an `Applier` must call `configurePluginAutoInstall` to wire (`plugin_adapter.go:19-33`). It carries **no agent parameter** -- it is Claude-only by construction, not by a table lookup.

`internal/cli/dispatch_plugins.go`'s `prewarmDeclaredPlugins` is a *different* mechanism: it pre-warms the workspace's own *configured* marketplaces/plugins (read back from the instance's just-written `.claude/settings.json`) via `claude plugin marketplace add` / `claude plugin install --scope local`, to close a race with Claude's own startup enumeration. It has nothing to do with niwa's *own* embedded plugin tree.

### 3. Where a Codex-reachable materialization should live

`marketplaceContentRoot(instanceRoot)` = `<instanceRoot>/.niwa/marketplaces/<name>` (`internal/workspace/pluginskills.go:36-39`) is where `ensureMarketplaceContent` fetches a github-sourced marketplace's tree into the instance (`pluginskills.go:211-260`), gated by presence of `.claude-plugin/marketplace.json` at that root (`marketplaceManifestPath`, `pluginskills.go:44-46`). Both the containment check (`checkContainment`) and the manifest-presence check are specific to *fetched, github-sourced, third-party* marketplaces -- niwa's own tree is neither fetched nor does it carry a `marketplace.json`.

Candidate destinations for niwa's own tree, evaluated against the actual delivery mechanism used for Codex row 18-shaped capabilities (`agentplan.PluginSkills`, `internal/agentplan/skills.go`):

- **A sibling niwa-owned path under `<instanceRoot>/.niwa/`** (e.g. `.niwa/niwa-plugin/` or reusing `.niwa/marketplaces/niwa/` with a name collision risk against a workspace that configures a marketplace literally named `niwa`) is the natural fit. It plays the same role `ensureMarketplaceContent`'s `dest` plays for a configured plugin: a `Root` on disk that `agentplan.PluginTree{Name: "niwa", Root: <path>}` can point at, letting the *existing* `SkillsPlan`/`SkillsReconcileSpec`/`InstallRepoSkills` machinery (`internal/agentplan/skills.go`, `internal/workspace/pluginskills.go:475-560`) deliver it by symlink at `.codex/skills/niwa` exactly the way a configured plugin is delivered today (`skillsLayouts[agent.AgentCodex] = {".codex","skills"}`, `skills.go:83-84`). This reuses `OpDeliverTree` (symlink-preferred, sentinel-file fallback via `.niwa-delivered-tree`) and `reconcileSkillsDir`/`treeCopyIsNiwas` for cleanup verbatim -- no new reconcile logic needed.
- **Reusing `marketplaceContentRoot` itself** (`.niwa/marketplaces/niwa/`) works mechanically (nothing stops writing there) but conflates niwa's own always-present tree with the fetched-and-gated-by-manifest.json semantics `ensureMarketplaceContent` documents for *configured* marketplaces, and risks a name collision if a workspace configures `[claude.marketplaces.niwa]` for something else. A sibling directory name avoids that collision by construction.
- **Materializing directly into `.codex/skills/niwa` as a copy, bypassing the intermediate on-disk source root** does not fit the `PluginTree{Root}` abstraction, which expects `Root` to be a *source* that `OpDeliverTree` symlinks or copies *from* -- there is no delivery primitive that writes a tree's final bytes as its own destination with no separate source. It would need a bespoke Entry/Op outside the existing `agentplan.Plan` vocabulary, which is more invasive than option A for no behavioral gain (whether the destination tree is reached by symlink-from-a-niwa-owned-source or copy-in-place is invisible to Codex, which only cares about `.codex/skills/niwa`'s final shape).
- **Whether the embedded tree needs to hit disk inside the instance at all**: yes, under the current `PluginTree.Root`-based delivery contract -- `Root` is documented as "the absolute path of the whole plugin tree" (`skills.go:56`), and `OpDeliverTree`'s source must exist on the real filesystem for `os.Symlink`/`copyTree` to work. `embed.FS` cannot be symlinked to directly. So: extract the embedded tree to `<instanceRoot>/.niwa/<niwa-owned-name>/` once per instance (idempotent write, mirroring `writeEmbeddedTree`), then deliver it to `.codex/skills/niwa` via the existing `PluginSkills`/`RootProjectSkills` machinery once that machinery gets an instance-root scope (see row 18 below).
- **Survives `niwa destroy`/`reap` cleanly**: yes for any of the `.niwa/`-rooted options, since destroy/reap remove the whole instance directory; nothing external is touched, unlike the Claude path which writes to the developer's global `~/.claude/` and is explicitly *not* instance-scoped (see Finding 1) and therefore is never cleaned up by `niwa destroy`.

### 4. Should `.claude-plugin/plugin.json` be added to the embedded tree?

**Mechanically safe for the Claude path, behaviorally unverified.**

- Nothing in `plugin.Install`/`writeEmbeddedTree`/`Embedded()`/`readInstalledManifest` reads or cares about `.claude-plugin/`. `Embedded()` only ever reads `files/niwa/manifest.json` (niwa's own custom `{name,version,description,skills:[...]}` schema, not Claude Code's plugin/marketplace manifest shape) for the version-pin/name-invariant check (`embed.go:58-80`). `writeEmbeddedTree` is a blind `fs.WalkDir` copy, so an added `.claude-plugin/plugin.json` is copied through with zero code changes.
- No test in `internal/plugin/` (`installer_test.go`, `embed_test.go`) asserts the embedded tree's exact file list or count. `embed_test.go` only checks `manifest.json`'s `Name == "niwa"` and `Embedded()`'s returned install path suffix. Adding a file breaks nothing there.
- **What is genuinely unverified**: how Claude Code itself resolves the skill namespace for this tree today. The user-facing command is documented everywhere (`internal/workspace/disclosure.go:41`, `internal/cli/plugins.go:18-27,36`) as `/niwa:migrate-config` -- note this is `niwa:migrate-config`, using the manifest's `skills[].name` field (`"migrate-config"`, per `internal/plugin/files/niwa/manifest.json`), **not** the SKILL.md frontmatter name `niwa-migrate-config` that the round-2 lead measured Codex resolving to. That means Claude's resolution of this tree (installed at `~/.claude/plugins/marketplaces/niwa/`, with no `.claude-plugin/marketplace.json` or `.claude-plugin/plugin.json` present) is already going through some directory-name-or-manifest.json-driven convention distinct from both of the two mechanisms round 2 measured for Codex. Adding `.claude-plugin/plugin.json` (name `"niwa"`) would very likely leave the namespace prefix unchanged (`niwa:...`) since the plugin name matches the directory name already in use, but it is **not measured** whether Claude Code would then prefer the frontmatter skill name (`niwa-migrate-config`) over the manifest's declared name (`migrate-config`) once a real `.claude-plugin/plugin.json` makes it recognize the tree as a "real" plugin -- which would silently change the documented `/niwa:migrate-config` command to `/niwa:niwa-migrate-config` for Claude users. This needs a direct measurement (same `codex debug prompt-input`-style harness, but for Claude Code) before shipping, not an inference from this codebase alone.
- The two manifests (`manifest.json` at root -- niwa's own bookkeeping/versioning format -- and a hypothetical `.claude-plugin/plugin.json` -- Claude Code's/Codex's discovery format) coexist without structural conflict: different paths, different consumers, disjoint schemas. `manifest.json` stays the installer's version-pin source of truth regardless.

### 5. How row 19 (NiwaPlugin) should bind

**Critical constraint, not previously stated in the brief**: `Route` is a property of the *capability*, not of the (capability, agent) pair. `internal/agentplan/capability.go`'s `catalog` declares `{NiwaPlugin, "niwa-plugin", RouteProcedure}` once, for the capability -- both Claude's and Codex's row 19 bindings are therefore forced to resolve through the `procedures` map, never the `deliveries` (Materializer) map. This is enforced by `internal/workspace/delivery_binding_test.go:26-27` (`TestDeliveriesMatchTheBindings`): `switch b.Capability.Route() { case agentplan.RouteProcedure: ... require procedures[b.Delivery] ... default: ... require deliveries[b.Delivery] }`. The route decision is keyed on `b.Capability`, so **there is no legal way for Claude's row 19 to be procedure-routed while Codex's is plan-routed** -- the brief's framing ("Claude sounds procedure-shaped... Codex sounds plan-shaped... can one capability bind to one Delivery name per agent, with different shapes?") is half right and half not: one capability *can* bind to a different `Delivery` **name** per agent (nothing stops `{NiwaPlugin, Claude, "niwa-plugin-claude"}` and `{NiwaPlugin, Codex, "niwa-plugin-codex"}` as two rows, per `Binding{Capability, Agent, Delivery}`'s shape and the un-uniqueness of `Delivery` across rows), but both deliveries **must** be registered in the `procedures` map (not `deliveries`), i.e. both must implement the `procedure` interface (`Name() string; Deliver(procedureInput) (procedureResult, error)`), regardless of whether the underlying write actually lands outside the instance (true for Claude) or inside it (true for Codex, under the destination this lead recommends in Finding 3).

What legal binding for both agents of row 19 requires, concretely:

1. **A `procedure` type wrapping the existing Claude installer.** `installNiwaPluginAdapter`/`plugin.Install` today is called through the ad-hoc `Applier.InstallNiwaPlugin` function field (Finding 2), which is *not* the `procedure` interface and is not registered in `procedures`. To bind legally, something like `type claudeNiwaPluginProcedure struct{}` with `Name() string { return "niwa-plugin-claude" }` and `Deliver(procedureInput) (procedureResult, error)` calling `plugin.Install` needs to exist, registered in `procedures` (`internal/workspace/delivery_binding.go:89`), and the *actual pipeline call site* needs to route through `procedureFor(agentplan.NiwaPlugin, agent.AgentClaude)` the way `deliverDirectoryTrust` does (`apply.go:2038-2069`) -- otherwise the registration is inert bookkeeping that no test currently catches, since `TestDeliveriesMatchTheBindings` only checks that a *name* resolves to *something* registered, not that the real call site uses it.
2. **A second `procedure` type for Codex**, writing the embedded tree into the instance-root location from Finding 3 and delivering it to `.codex/skills/niwa` (either by driving the same `agentplan.SkillsPlan`/`InstallRepoSkills` path this lead recommends reusing for row 18, or a bespoke symlink write) -- registered under its own `Delivery` name, e.g. `"niwa-plugin-codex"`.
3. **`procedureInput` needs a new field.** Today it carries only `DeveloperHome`, `RepoRoots`, `Recorded` (`delivery_binding.go:33-48`) -- there is no `InstanceRoot`. Claude's procedure doesn't need one (global home only), but Codex's procedure, writing inside the instance, cannot function without it. This is a real code change to a shared struct, not just a new registration.
4. **`procedureFor`/`Deliver` carries no agent parameter into the call**, and neither Claude's nor Codex's existing procedure-shaped work has needed one before (`DirectoryTrust` only has one implemented agent today). With two agents each needing a *different* procedure body for the *same* capability, the natural shape is two distinct procedure types/registrations (per point 1-2) rather than one procedure branching on an agent it is never told -- consistent with how `Binding` already allows distinct `Delivery` names per (capability, agent) row.
5. **Trigger-condition tension, worth flagging explicitly**: `deliverDirectoryTrust` (the only existing multi-call-site procedure loop) runs its procedure loop unconditionally every apply, gated only on `DeveloperHome != ""` (`apply.go:2038-2043`). Claude's current `InstallNiwaPlugin` trigger is much narrower -- only fires inside the rank-2-detected branches (Finding 2). If row 19 is bound by mechanically converting the call site to an unconditional `for _, ag := range agent.All() { procedureFor(...) }` loop (mirroring `deliverDirectoryTrust`), that silently changes Claude's install trigger from "only on rank-2 detection" to "every apply" -- a real behavior change needing an explicit decision, not an incidental side effect of satisfying the binding test.
6. `Row 19` also needs adding to `boundCapabilities` (`binding.go:60-65`) for the structural suite (`TestBindingsMatchTheirDeclarations`) to require and check both agents' rows.

### 6. Row 18 (RootProjectSkills, Claude) -- what materializer, briefly

The Claude side of row 18 is **not** delivered by anything shaped like `Materializer` or `procedure` today. `InstallWorkspaceRootSettings` (`internal/workspace/workspace_context.go:319`) is a bare function -- `func InstallWorkspaceRootSettings(cfg *config.WorkspaceConfig, configDir, instanceRoot string, repoIndex map[string]string) ([]string, error)` -- with no `Name()` method and a signature that does not match `Materializer.Materialize(ctx *MaterializeContext) ([]string, error)` (`materialize.go:221-224`). It writes `enabledPlugins`/`extraKnownMarketplaces` (among hooks/permissions/env) into `<instanceRoot>/.claude/settings.json`, comment-documented as relying on "Claude Code's startup reconciler" to do the actual materialization from that declaration (`workspace_context.go:317-319`).

Since `RootProjectSkills`'s catalog route is `RoutePlan` (`capability.go:190`), and `RoutePlan` is `TestDeliveriesMatchTheBindings`'s `default` case (routes through the `deliveries` Materializer map, not `procedures`), binding `(RootProjectSkills, Claude)` legally requires wrapping `InstallWorkspaceRootSettings` (or the specific plugin/marketplace-writing slice of it) in a `Name()`-carrying `Materializer`-shaped adapter, exactly the same shape of work the `DirectoryTrust`/`codexTrustProcedure` conversion already did for a bare function (`EnsureCodexTrust`) on the procedure side. This is a known, previously-solved pattern in this codebase, not a novel one -- but it is real code, not just a registration line.

## Implications

- The clean way to deliver Codex's row 19 reuses machinery already built for row 18/`PluginSkills` (extend `agentplan.skillsLayouts`-style resolution and `PluginTree`/`SkillsPlan`/`SkillsReconcileSpec` to include niwa's own tree as an always-present `PluginTree{Name: "niwa", Root: <instance-local extracted path>}`), rather than inventing a parallel delivery mechanism for Codex. This is consistent with the brief's own framing that row 18 and row 19 are closely related for Codex.
- But that reuse only closes the *plan-shaped* half of the requirement. Because `NiwaPlugin`'s Route is `RouteProcedure` for both agents (Finding 5), the actual binding entries for BOTH agents still have to be `procedure`-interface registrations, even for Codex's tree write, which is otherwise mechanically identical to a `RoutePlan` skills delivery. In practice this likely means: the Codex `procedure`'s `Deliver()` body internally calls the same `SkillsPlan`/`InstallRepoSkills`-shaped code the row-18 work builds, but the *binding* is still a procedure registration, not a plan-tagged entry. The two questions (destination/mechanism vs. binding shape) are more separable than the brief implies.
- Extending `procedureInput` with `InstanceRoot` is a small, low-risk struct change but touches a currently agent-neutral, side-effect-outside-the-instance-only contract (its doc comment: "what it is told about the apply is not where the variety belongs" -- `delivery_binding.go:32-37`). Adding an inside-the-instance field to a struct whose existing doc comment leans on "outside the instance" is worth a one-line doc update alongside the code change, since a future reader would otherwise reasonably assume the struct's fields are exhaustively about developer-home-scoped side effects.
- Deciding whether Claude's row 19 install trigger changes from "only on rank-2 detection" to "every apply" (Finding 5, point 5) is a real product decision that should be made explicitly, not left to fall out of whichever call-site pattern gets copied.

## Surprises

- The documented `/niwa:migrate-config` command uses the manifest's `skills[].name` (`"migrate-config"`), not the SKILL.md frontmatter name (`"niwa-migrate-config"`) that round 2 measured Codex resolving to. Claude's actual resolution mechanism for this specific tree shape (no `.claude-plugin/marketplace.json`, no `.claude-plugin/plugin.json`, installed at a `.../marketplaces/niwa/` path) is not evidenced anywhere in this codebase and was not part of round 2's measurements -- it needs its own direct measurement before anyone changes the embedded tree's shape, since the risk is a silent, user-visible command-name break for existing Claude users.
- `InstallNiwaPlugin` is not an "every apply" install for Claude -- it is gated behind rank-2 config detection specifically, which the brief's framing (comparing it structurally to `DirectoryTrust`'s always-on loop) does not surface.
- `plugin.Install` records nothing in `InstanceState` and is not instance-scoped at all -- it is entirely orthogonal to the instance lifecycle (`niwa destroy`/`reap` never touch it), whereas any Codex-side delivery this lead recommends is instance-scoped by construction. The two agents' row-19 deliveries are not just differently-routed technically; they have fundamentally different lifecycles (global, once-per-developer-machine vs. per-instance, reaped with the instance).

## Open Questions

- Does Claude Code, given this exact tree shape with an added `.claude-plugin/plugin.json`, resolve the skill as `niwa:migrate-config` (unchanged), `niwa:niwa-migrate-config` (frontmatter-driven, breaking the documented command), or something else? Needs direct measurement, not inference.
- Should Claude's row 19 install trigger become unconditional (every apply, matching `DirectoryTrust`'s pattern) as part of this binding work, or should the existing rank-2-gated trigger be preserved by keeping the procedure call embedded in the same conditional branches rather than a new top-level unconditional loop?
- Should the Codex-side instance-local extraction target be named to avoid any collision with a workspace-configured marketplace that happens to be named `niwa` (e.g. `.niwa/niwa-plugin/` rather than `.niwa/marketplaces/niwa/`)?

## Summary
Claude's row 19 (`plugin.Install`) copies the embedded tree to the developer's *global* `~/.claude/plugins/marketplaces/niwa/`, fires only inside rank-2-detection branches (not every apply), and is wired through an ad-hoc function-field seam that is not a `procedure`/`Materializer` registration today. Codex's row 19 should reuse the existing `PluginTree`/`SkillsPlan` skills-delivery machinery via a niwa-owned instance-local extraction of the embedded tree (e.g. `<instanceRoot>/.niwa/niwa-plugin/`), delivered to `.codex/skills/niwa` exactly like a configured plugin; but because `Route` is fixed per-capability (`RouteProcedure` for `NiwaPlugin` on both agents, enforced by `delivery_binding_test.go`), both agents' bindings must be registered as `procedure`-interface implementations under distinct `Delivery` names, `procedureInput` needs a new `InstanceRoot` field for Codex's procedure to use, and the real pipeline call sites (not just map registrations) must be rewired through `procedureFor` for the binding to be more than inert bookkeeping. `.claude-plugin/plugin.json` is mechanically safe to add (nothing reads or tests against the current file list) but its effect on Claude's own skill-namespace resolution is unmeasured and risks silently breaking the documented `/niwa:migrate-config` command.
