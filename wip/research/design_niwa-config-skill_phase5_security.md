# Security Review: niwa-config-skill

## Dimension Analysis

### External Artifact Handling

**Applies:** Partially -- one narrow, pre-existing sub-path is touched; the design's own new content is not itself an external artifact.

The design's three changes (rank-1 install trigger, `edit-config` skill content, bootstrap wiring fix) don't add any new external download, fetch, or execution path. The plugin content that gets written to `~/.claude/plugins/marketplaces/niwa/` is `go:embed`-compiled into the niwa binary at `internal/plugin/embed.go:25` (`//go:embed files/niwa`) and read via `pluginFS.ReadFile` in `writeEmbeddedTree` (`internal/plugin/installer.go`). Nothing in `plugin.Install` fetches from the network or from the adopting repo's own source -- confirmed by reading `Install`, `stageAndRename`, and `writeEmbeddedTree` end to end. The only "external" input in the affected code path is `teamConfigRank`, an `int` computed from probing the shape of the workspace's already-configured, already-trusted config source (see Permission Scope below for the attacker-influence analysis of that value).

The one legitimate external-artifact-adjacent risk is Decision 2's content strategy: the `edit-config` skill instructs an agent to read `internal/config/config.go` "live" and treat it as ground truth. That is source code inside the same repo the agent is already operating in (the niwa repo, when this skill teaches an agent working on niwa itself) -- it is not fetched from a URL, not downloaded, and not executed. It's addressed in its own dimension below since it's really a supply-chain/trust question, not a download/execution one.

### Permission Scope

**Applies:** Yes.

No new permission *type* is introduced -- `InstallNiwaPlugin` already writes to `~/.claude/plugins/marketplaces/niwa/` on every `apply`/`create` today, gated on rank-2. Decision 1 doesn't change what gets written, how it's written (same atomic stage-and-rename), or what triggers respect the opt-out. Verified: `internal/cli/plugin_adapter.go`'s `configurePluginAutoInstall` wires `applier.SkipPluginInstall = flagOptOut || skipFromGlobal` once per `Applier`, and all four existing `apply.go` rank-2 call sites *and* the two new rank-1 sites (~443, ~595, ~927, ~956, all confirmed present in `internal/workspace/apply.go`) pass the same `a.SkipPluginInstall` field into `a.InstallNiwaPlugin(nil, a.Reporter, a.SkipPluginInstall)`. A user who has already set `--no-install-plugins` or `auto_install_plugins = false` stays opted out under the broadened rank-1 trigger exactly as they are today under rank-2 -- confirmed, this is not weakened.

What *does* change is population and frequency: today the filesystem write to `~/.claude/` only fires for rank-2 (deprecated, rare) sources; after this design it fires for rank-1 (the default, common case) too. That's a meaningful expansion of how many workspaces get an unattended write into `~/.claude/plugins/marketplaces/niwa/` on a routine `apply`/`create`/`init --bootstrap` call, even though each individual write is the same trusted, embedded, idempotent content as before. This is a scale change to an already-accepted mechanism, not a new capability -- rated **low severity**. The main residual risk is user surprise/consent: an owner of a rank-1 workspace who never encountered rank-2 might be seeing an unrequested `~/.claude/` write for the first time, without having made any decision to trigger it (compare to rank-2 users, who at least get the deprecation notice as a "your setup needs attention" signal alongside the install). Mitigation: the design's own notice content (`EmitRank1Notice`, distinct notice IDs `NoticeIDRank1TeamConfig`/`NoticeIDRank1Overlay`) already covers this by explaining *why* the install fired, separate from `EmitPluginNotice`'s *what happened* -- this is adequate; no further mitigation needed beyond ensuring the notice text is not silent about scope (i.e., it should be clear this is normal/expected behavior, not an error).

**Rank attacker-influence analysis** (specifically investigated per the task brief): `teamConfigRank` is derived purely by probing the *directory layout* of the config source the workspace already points at -- confirmed in `internal/workspace/fallback.go` (`rank = 2` / `rank = 1` set from marker-file presence) and `internal/workspace/snapshotwriter.go` (`probedRank`, `RankDecider`). There is no separate "declare your own rank" field an attacker could set independent of what their repo's actual file layout is -- rank is a structural fact about the config source, not an attacker-supplied claim. So the question "could a malicious source repo trick niwa into a rank it doesn't actually have" doesn't really have content: whatever layout a malicious repo owner publishes *is* its actual rank by construction. The more meaningful question is what an attacker gains by controlling rank at all, and the answer is: very little. The embedded plugin content is fixed (`go:embed`, not sourced from the remote config repo), so forcing rank=1 vs rank=2 only toggles *whether* niwa's own trusted plugin gets installed/refreshed -- it cannot be used to smuggle attacker content into `~/.claude/`. A malicious config-source owner already has far larger leverage over a workspace that trusts it (arbitrary hooks, arbitrary `claude.settings`, arbitrary `env.vars`/`env.secrets` wiring) than "install/skip a legitimate, versioned skill." This is **not a meaningful new attack surface**.

### Supply Chain or Dependency Trust

**Applies:** Yes, specifically for Decision 2's "live-source-grounded content" strategy.

Re-confirmed Decision 2's actual chosen scope by re-reading it directly (design doc lines 240-267): the skill teaches an agent to read **niwa's own** `internal/config/config.go` and `internal/config/vault.go` -- i.e., when this skill is invoked, it is running inside a niwa repo checkout and reading that same checkout's source to learn the config schema, in order to then go edit a *different* repo's (the adopting workspace's) `.niwa/workspace.toml`. It does not read or execute the adopting workspace's own source as its schema-learning step. This scoping is correct and matters: it bounds the trust question to "how much do we trust the niwa repo checkout this skill ships from," not "how much do we trust arbitrary workspace repos this skill might later edit."

Given that scoping, the residual risk is: a compromised niwa fork, or a workspace-local `public/niwa` checkout with an attacker-modified `config.go`, could cause the `edit-config` skill to teach an agent something wrong (stale field names, a subtly malicious "recommended" TOML shape, or misleading doc comments) at the moment an agent reads the doc comments as ground truth. This is a real but **low-severity, low-likelihood** risk, for three reasons: (1) it requires an attacker to already have write access to the niwa repo an engineer is running against, which is a far more direct path to arbitrary code execution than steering a config-editing skill's prose (an attacker who can edit `internal/config/config.go` in a checkout an agent trusts can just as easily edit `internal/plugin/installer.go` or any Go source that actually runs); (2) the plugin's *installed* SKILL.md content is still the `go:embed`'d, release-pinned text from `internal/plugin/files/niwa/skills/edit-config/SKILL.md` -- the live-read step happens only when the skill is *invoked inside a niwa checkout*, which per the design's own framing is the expected operating context for this skill (an agent working on niwa itself, or -- per Decision 2's stated purpose -- an agent in an adopting workspace's own niwa instance that has a niwa checkout available to consult); (3) the worst plausible outcome is bad advice text steering a human/agent toward a malformed or non-idiomatic `workspace.toml` edit, not code execution -- the skill's own procedure (read struct tags/doc comments, don't execute anything) has no code-execution primitive in it.

This is a legitimate trade-off the design accepts (traded a static, reviewed-at-release schema copy for a live one that can't go stale) and it's the correct trade for the stated problem (drift), but it should be named explicitly in the doc's security considerations so a future reader doesn't have to re-derive it: **live-source-grounded content inherits the trust level of whatever niwa checkout is on disk at invocation time**, which is normally the same trust level as the niwa binary/build the agent is already running, but is a materially different guarantee than "reviewed and pinned at release," and is worth calling out as a named, accepted trade-off rather than an unstated assumption.

### Data Exposure

**Applies:** Minimally.

`EmitRank1Notice`/`EmitRank2Notice` and `EmitPluginNotice` write plain informational log lines to the CLI reporter (stderr, per existing convention) -- confirmed by reading `internal/workspace/disclosure.go`: `EmitRank2Notice` logs the source identifier (a repo URL/slug) and a fixed instructional string; `EmitPluginNotice` logs a fixed string plus, on skip, the fixed `manualInstallCommand` ("niwa plugins install"). None of these lines carry secret material, vault provider config, or file contents -- they're operational notices, not data dumps. The new `EmitRank1Notice` mirrors this shape per the design (Components section), so no new exposure surface is introduced by Decision 1.

The more relevant data-exposure question, given the skill teaches editing `vault.*`/`env.secrets`/`claude.settings`, is what the *skill's guidance* might cause a human/agent to write into a committed file -- that's a write-side risk, covered in the additional dimension below (Secret-Handling Guardrails), not a transmission/logging risk. There is no telemetry, no network call, and no external transmission introduced anywhere in this design's three changes.

### Skill-Guided Secret Handling Guardrails (design-specific, investigated per task brief)

**Applies:** Yes -- and this is the most concrete, actionable finding in this review.

The task asked whether skill guidance walking an agent through `vault.*`, `env.secrets`, and `claude.settings` edits needs explicit anti-plaintext-secret guardrail language, given this repo's own `docs/guides/vault-integration.md` documents a public-repo guardrail for exactly this mistake class. Investigated the actual code-level guardrail to check its real coverage rather than trusting the doc's framing at face value, and found the coverage is **narrower than the doc's prose suggests, in a way directly relevant to this skill's stated editing surface**:

- `internal/guardrail/githubpublic.go`'s `offendingKeys` function -- the one that powers `CheckGitHubPublicRemoteSecrets`, niwa's actual public-repo plaintext-secret block -- walks exactly six struct paths: `cfg.Env.Secrets`, `cfg.Claude.Env.Secrets`, each repo's `repo.Env.Secrets`/`repo.Claude.Env.Secrets`, and `cfg.Instance.Env.Secrets`/`cfg.Instance.Claude.Env.Secrets`. Confirmed by direct read of the function body (lines ~203-230).
- `docs/guides/vault-integration.md` itself states this narrowness explicitly: "The guardrail walks `*.secrets` tables only. Plaintext in `[env.vars]` is allowed" (lines ~547-549).
- Critically, **`claude.settings` (`SettingsConfig`, `internal/config/config.go:345`) is typed `map[string]MaybeSecret`** -- the doc comment directly above it says "Values are MaybeSecret so a vault reference can back a setting value... the plaintext path still accepts raw strings through MaybeSecret's TextUnmarshaler." So the schema explicitly anticipates that `claude.settings` values may carry secret-shaped material -- but `offendingKeys` never walks `cfg.Claude.Settings`. A plaintext secret placed there by an agent following the new skill's guidance would **not** be caught by the existing public-repo guardrail, even though the type system flags it as secret-capable.
- Similarly, **`vault.provider`/`vault.providers.<name>`'s `Config` field (`internal/config/vault.go:41`, `VaultProviderConfig.Config map[string]any`) is untyped `map[string]any`** -- not even `MaybeSecret`-wrapped, let alone guardrail-walked. For the v1 Infisical backend this is low-risk in practice (the guide's quick-start shows `[vault.provider]` only ever carrying `kind` and `project`, a non-secret project identifier -- the actual credential lives in the Infisical CLI's own session cache and "niwa never sees it," per the guide). But the schema is explicitly built pluggable for future backends ("provider interface is pluggable; sops + age is deferred to v1.1" per the guide's own framing), and nothing in the type system or the guardrail would stop a future backend's config shape, or an agent's over-eager edit today, from placing a raw token directly in `vault.provider.*` config.

This means the design's Decision 2, as currently scoped ("teach the agent to read config.go live, write short procedural walkthroughs for... wire a secret... add a plugin...") walks an agent through exactly the two blocks (`claude.settings`, `vault.provider`) where the codebase's own automated guardrail provides **no backstop**, unlike `env.secrets` where a code-level check exists as a safety net even if the skill's guidance is imperfect. The current design doc has no language addressing this. Given this repo already treats plaintext-secret-in-public-repo as a named, actively-guarded-against failure mode elsewhere, a config-editing skill that walks an agent through the exact blocks where that guardrail doesn't reach should carry explicit, skill-owned guardrail language rather than relying on the (partial) automated check. This is a **document-and-mitigate** finding, not a blocking design flaw -- it's a one- or two-sentence addition to `SKILL.md`'s content, not a re-architecture.

## Recommended Outcome

Two things need to land, one as a design-doc addition (below, ready to paste) and one as an implementation note for Phase 3 (skill authoring):

2. No changes are needed to Decisions 1-3's chosen approaches themselves; the rank-1 trigger broadening, the live-source-grounded content strategy, and the bootstrap wiring fix all check out as sound on direct source verification, with no corruption window in the install mechanism and no meaningful new attacker leverage from the rank signal.

### Security Considerations

**External artifact handling.** This design introduces no new download, fetch, or execution path. The plugin content written to `~/.claude/plugins/marketplaces/niwa/` is compiled into the niwa binary via `go:embed` (`internal/plugin/embed.go`) and is identical regardless of which trigger (rank-1 or rank-2) fires the install -- `plugin.Install` never reads from the network or from the adopting repo's own source.

**Permission scope.** No new permission type is introduced. `InstallNiwaPlugin` already writes to `~/.claude/plugins/marketplaces/niwa/` on every `apply`/`create`; this design changes which condition (rank-1 in addition to rank-2) triggers that existing, unchanged write. The existing opt-outs (`--no-install-plugins`, `auto_install_plugins = false`) apply identically to the new rank-1 branches -- verified all four new call sites pass the same `a.SkipPluginInstall` field used by the four existing rank-2 sites. The practical effect of this design is a scale/frequency change: the same trusted, idempotent write now happens for the common case (rank-1) instead of only the rare, deprecated case (rank-2). `teamConfigRank` is a structural property of the config source's own directory layout (marker-file presence), not an attacker-settable flag independent of that layout; a malicious config source can only "claim" the rank its actual file layout implies, and controlling that rank yields no leverage beyond toggling installation of niwa's own fixed, embedded, already-trusted plugin -- a source repo an operator already trusts enough to point a workspace at already has far larger avenues of impact (arbitrary hooks, arbitrary `claude.settings`, arbitrary `env.*` wiring) than this toggle.

**Supply chain / dependency trust.** Decision 2's live-source-grounded content strategy has the `edit-config` skill read `internal/config/config.go`/`vault.go` from the **niwa repo checkout the skill is invoked in** -- not the adopting workspace's own source -- to learn the schema before editing that workspace's `.niwa/workspace.toml`. This bounds the trust question to the niwa checkout on disk at invocation time, which is normally the same trust level as the niwa binary/build already in use. A compromised niwa fork or an attacker-modified local niwa checkout could in principle steer the skill's live-read step toward bad advice (stale field names, misleading doc comments), but this requires an attacker who already has write access to a checkout the agent trusts -- a position from which far more direct compromise (editing the Go source that actually executes) is already available. The installed `SKILL.md` prose itself remains the release-pinned, `go:embed`'d text; only the schema-learning step is "live." This is an accepted, intentional trade-off (drift-resistance over release-pinned staleness) and should be treated as such by future maintainers, not rediscovered.

**Data exposure.** No new telemetry, network call, or external transmission is introduced. The new `EmitRank1Notice` mirrors `EmitRank2Notice`'s existing shape: a plain informational stderr line naming the config source identifier and a fixed instructional string, no secret material or file contents.

**Secret-handling guardrails in skill guidance.** niwa already enforces a public-repo plaintext-secret guardrail (`internal/guardrail/githubpublic.go`), but it walks a specific, narrow set of struct paths: `env.secrets` and `claude.env.secrets` (workspace-, repo-, and instance-level). It does **not** walk `claude.settings` (`SettingsConfig`, typed `map[string]MaybeSecret` precisely because it can carry vault-backed values) or `vault.provider`/`vault.providers.*` config (`VaultProviderConfig.Config`, untyped `map[string]any`). Both are blocks the `edit-config` skill's Decision-2 walkthroughs explicitly cover ("wire a secret," "add a plugin," provider setup). This means the codebase's automated safety net does not reach two of the exact blocks this skill teaches an agent to edit. `SKILL.md`'s procedures for `claude.settings` and `vault.*` edits must therefore carry their own explicit guardrail language: never write a literal secret value into those blocks; always use a `vault://` reference for anything secret-shaped in `claude.settings`; and for `vault.provider`/`vault.providers.*` config, only non-secret fields (e.g., a project identifier) belong in `workspace.toml` at all -- actual credentials are handled out-of-band by the provider's own CLI (e.g. `infisical login`), matching the existing pattern documented in `docs/guides/vault-integration.md`. This is a content requirement on Phase 3's `SKILL.md` deliverable, not a code or architecture change.

**Install-mechanism integrity.** `plugin.Install`'s `stageAndRename` (`internal/plugin/installer.go`) writes the full embedded tree to a `.next` staging directory first, then promotes it into place via `os.Rename` (atomic on POSIX), moving any existing install aside to `.prev` first and rolling back on a failed promote. Verified by direct read: there is no window in which a partially-written tree is visible at the install path -- Claude Code will only ever observe a complete old tree, a complete new tree, or (in the narrow case of a crash between the move-aside and promote renames) a momentarily absent directory, never a mixed-version or truncated one. The manifest version-bump discipline required for `edit-config` to reach already-installed users (Decision 1's "Key assumptions") should be enforced by the functional test the design already plans (Phase 4: assert the `edit-config` skill file exists in HOME post-install), which is an adequate mitigation for that specific risk.

## Summary

The three source-verified changes -- the rank-1 install-trigger broadening, the live-source-grounded skill content strategy, and the bootstrap wiring fix -- introduce no new download/execution surface, no permission-type escalation, and no meaningful attacker leverage over the rank signal or the install mechanism (which is confirmed atomic with no corrupt-tree window). The one concrete, actionable gap is that the codebase's own public-repo plaintext-secret guardrail does not cover `claude.settings` or `vault.provider` config -- exactly two of the blocks the new `edit-config` skill teaches an agent to edit -- so `SKILL.md`'s guidance for those blocks needs its own explicit "never write a plaintext secret, always use vault:// / out-of-band credential handling" language rather than relying on the automated check. Recommended path is Option 2: paste the Security Considerations section above into the design doc, and carry the guardrail-language requirement into Phase 3's `SKILL.md` authoring as an explicit content requirement.
