# Lead: What does SPIKE-codex-discovery-mechanics record, and what does it constrain?

Source: `docs/spikes/SPIKE-codex-discovery-mechanics.md` on `origin/worktree-codex-findings` (unmerged PR tsukumogami/niwa#254). Status: Complete. Measured against `codex-cli 0.147.0` on Linux, cross-checked against upstream source at tag `rust-v0.147.0`, in an isolated `CODEX_HOME`. The spike explicitly warns findings 1-3 (discovery, precedence, budget) are the most version-fragile and most expensive to get wrong.

## Constraints Extracted

| # | Constraint | What the spike says | Status |
|---|---|---|---|
| 1 | Bounded downward walk | Codex walks **up** from the working directory to the nearest ancestor containing a `project_root_markers` entry (default `.git`) to find the project root, then reads context/config **down** from that root to the working directory. It never walks above the root. Every cloned repo has `.git` at its root, so under default settings the walk starts and stops *inside* the repo — content placed at an instance root or group directory above the repo is never visited (Finding 1). | Measured |
| 2 | One file per directory, strict first-match | Each directory in the walk contributes **at most one** context file, by hardcoded precedence: `AGENTS.override.md`, then `AGENTS.md`, then any configured fallback filenames — in that order. The configured fallback list **cannot reorder** this. An empty/whitespace-only file still counts as a match, claiming the slot and suppressing all remaining candidates for that directory — "worse than writing nothing at all." Practical consequence: `AGENTS.override.md` is the only filename that wins in *every* repo; `AGENTS.md` delivers nothing in any repo that ships its own (Finding 2). | Measured |
| 3 | Shared, outermost-first byte budget | `project_doc_max_bytes` defaults to 32768 bytes. It is a **single counter** spent across the whole root-to-working-directory chain, draining **outermost-first**. Truncation is a raw byte cut — no marker in the text, nothing on stderr. Under-declaring the budget silently costs the *innermost* layer (the context closest to the actual work) with no signal anything was lost (Finding 3). | Measured |
| 4 | Trust gates writability and cannot be self-granted | A directory with no `[projects."<path>"]` entry in the developer's own Codex config is a read-only sandbox; the interactive TUI blocks on a trust prompt. Trust **cannot** be granted from inside a project-level config layer — "a project config vouching for itself is ignored by construction" (Finding 4). | Measured |
| 5 | Project config layer is real but trust gates it unevenly | `.codex/` found during the walk is a genuine config layer carrying instruction context, skills, general configuration (incl. byte budget), and MCP server declarations. Trust applies unevenly, and this was **measured, not inferred**: skills load from an untrusted layer with no rewriting (a symlinked plugin tree at `.codex/skills/<plugin>` resolves under the same `<plugin>:<skill>` namespace Claude Code uses); but configuration keys require trust — a 60KB context file was silently cut to 32768 in an untrusted directory even though the layer declared a larger budget, and adding a trust entry made the declared value take effect. MCP servers behave the same: `[mcp_servers.*]` in a project layer shows in `codex mcp list` only inside a trusted repo, absent outside one. "The byte budget and the trust entry are load-bearing for each other" (Finding 5). | Measured |
| 6 | What the project layer cannot carry at all | Trust itself, project-root marker configuration, hook trust state, marketplaces and plugin registration, and eleven denylisted keys (provider URLs, `notify`, profiles, and similar) (Finding 5, closing paragraph). | Measured |
| 7 | `shell_environment_policy.set` works at project layer | Environment variables can be delivered to a session via `shell_environment_policy.set` in the project config, which "parses cleanly at this layer." Spike calls this "the route for anything a session needs in its environment" (Finding 6). | Measured |
| 8 | Hooks: plugin-delivered, trust-gated, blocking-prompt problem | A loose `hooks.json` placed in a Codex home registers **nothing**. The working route is a plugin carrying its own `hooks.json`, with per-plugin trust state recorded as `trusted_hash` under `[hooks.state]`. An interactive session **blocks on a review prompt** for any hook it can't verify against that recorded hash. So automated hook installation "either solves the trust hash or accepts a modal in front of every session start. No route that avoids both has been demonstrated" (Finding 7). | Measured, with an explicit unresolved gap ("no route... has been demonstrated") |
| 9 | Claude plugin manifests install into Codex unmodified | `codex plugin marketplace add` accepts a local path or `owner/repo` and reads `.claude-plugin/marketplace.json` verbatim; plugins authored for Claude Code install and their skills load with no changes to the plugin. Two limits: (a) plugin `agents/` directories are copied into the plugin cache but never surface — "Claude-style named subagent types do not exist under Codex"; (b) for a marketplace sourced from GitHub (not a local path), the installed tree lives under **Claude Code's own user-global plugin directory** — so anything resolving skills from there inherits a dependency on Claude Code being installed and having already fetched the marketplace (Finding 8). | Measured |
| 10 | No per-directory config discovery outside the walk | A `.codex/config.toml` in a directory with no project-root marker above it is not read at all — direct consequence of Finding 1, called out separately as "the specific way a naive experiment fails" (Finding 9). | Measured (stated as logical consequence of Finding 1) |

## What a Codex Project Layer Can and Cannot Carry

Directly from the spike's closing section ("What this rules in and out for a writer"):

**Reachable from a workspace instance, without touching the developer's own Codex configuration:**
- Instruction context — via `AGENTS.override.md` at each repository root (not instance/group root — see Finding 1)
- Skills — via a project-layer `skills/` directory (loads even untrusted, per Finding 5)
- The context budget — but only where a trust entry exists (Finding 5)
- MCP servers — only where a trust entry exists (Finding 5)
- Environment variables — only where a trust entry exists (Finding 6 says it parses cleanly at this layer; the summary section groups it with the trust-gated set)

**Not reachable from the project layer at all:**
- Trust itself
- Project-root marker configuration
- Marketplace and plugin registration
- Hook installation (route exists via plugins but is trust-gated with a blocking-prompt problem, not a clean "reachable" path)

"Trust in particular has to be written into the developer's own configuration or answered by the developer at a prompt."

## Capabilities the Spike Implies Are Unavailable to Codex

The spike does not use the phrase "capability declaration," but the following are capabilities it explicitly says niwa cannot deliver through the project config layer, or cannot deliver without an unresolved dependency:

1. **Instance-level or group-level shared context.** The downward-walk-from-root-marker design (Finding 1) means content placed above a repository's `.git` root is structurally invisible to a session working inside that repo. This is not a trust or budget problem — it is unreachable by the discovery mechanism itself.
2. **Trust auto-grant / self-vouching.** No project config layer can grant its own directory trust (Finding 4). Any capability that depends on trust (budget override, MCP servers, env vars per Finding 5) is therefore conditionally unavailable — available only if the developer has separately trusted the directory.
3. **Named/typed subagents (Claude Code "subagent type") equivalents.** Plugin `agents/` directories are copied but never surface under Codex (Finding 8). This is an outright capability gap, not a trust gate.
4. **Hook installation without either solving the trust hash or presenting a blocking modal at every session start.** The spike states no route avoiding both has been demonstrated (Finding 7) — this reads as the strongest candidate for something a niwa implementation must declare unavailable-with-reason rather than silently attempt.
5. **Marketplace/plugin registration from the project layer.** Explicitly listed as not carryable by the project config layer (Finding 5, Finding 8's GitHub-source caveat). Registration must happen elsewhere (developer's own Codex config), and GitHub-sourced marketplaces additionally depend on Claude Code being installed and having already fetched the marketplace — a cross-agent dependency, not just an access gate.
6. **Project-root marker configuration.** Cannot be set from the project layer (Finding 5) — meaning niwa cannot use the project config layer itself to widen or redefine what counts as a root, which reinforces gap #1's unreachability.
7. **Any of the eleven denylisted keys** (provider URLs, `notify`, profiles, and similar) — the spike doesn't enumerate all eleven by name, only gives these three examples. Note: the spike does not name the remaining eight keys — treat that list as incomplete rather than filling it in.

## Implications

- **No agent constants at materializer call sites, applied to Codex specifically:** a materializer cannot assume "write context to instance root" or "write context to group root" works for Codex the way it might for another agent — Codex's walk structurally excludes anything above the repo's own root marker (Finding 1). Any shared-context mechanism must be per-repository-root (`AGENTS.override.md` at each repo root), not instance-wide, or it must be explicitly declared unavailable for Codex at the instance/group level.
- **Filename choice is not a free parameter.** A capability contract that lets an implementation "pick a context filename" is unsound for Codex: only `AGENTS.override.md` is guaranteed to win; anything else (including `AGENTS.md`) can be silently shadowed by a repo's own file (Finding 2). A test for "context is materialized" must assert the override filename specifically, not just presence of *a* file.
- **Never write an empty/near-empty context file as a placeholder.** Because an empty file still claims the directory's slot (Finding 2), a naive "always write the file, even if there's nothing to say" implementation actively suppresses fallback content. A conformant implementation must omit the file entirely when there is nothing to write, not write an empty one.
- **Byte-budget declarations require a paired trust guarantee, or they are meaningless.** Any capability contract item like "declare project_doc_max_bytes = N" must either also guarantee/verify the directory is trusted, or explicitly caveat that the declared value is a no-op absent trust (Finding 5). A test should exercise both the trusted and untrusted case, since the untrusted case silently reverts to 32768 with no error signal.
- **Silent truncation means a test cannot rely on stderr/exit code to detect budget overrun.** Any verification step for context-budget correctness must inspect byte length directly against the 32768-or-declared ceiling; there is no runtime signal to assert against (Finding 3).
- **Trust cannot be part of what niwa "implements" for Codex at all.** Since trust is fundamentally the developer's own decision (recorded in their own Codex config, outside any workspace-writable layer, per Finding 4), any capability whose delivery depends on trust must be declared as conditionally available ("available if developer has trusted this directory") rather than either "implemented" or flatly "unavailable." This is a third state the contract may need beyond implemented/unavailable-with-reason, or "unavailable-with-reason" must be worded to capture "unavailable unless the developer trusts the directory."
- **Hooks are the clearest unavailable-with-reason candidate.** Given the spike's explicit "no route... has been demonstrated" (Finding 7), a niwa implementation must not attempt automated hook installation for Codex as if it were solved; the contract should carry an explicit declared-unavailable entry citing the blocking-prompt problem, not a partial/silent implementation.
- **Named subagents are an outright missing primitive under Codex**, not a wiring gap — a capability contract item for "subagent types" must be declared unavailable for Codex with reason "Codex copies plugin `agents/` directories into its cache but never surfaces them" (Finding 8), not attempted.
- **GitHub-sourced marketplace installation carries a cross-agent dependency** that a capability contract should surface explicitly: reachability depends on Claude Code being installed and having already fetched the marketplace. A test asserting this capability must not pass in an environment lacking Claude Code, or the contract must scope the capability to local-path marketplace sources only.
- **A test that materializes content above a repo root and expects a Codex session inside that repo to see it must fail** — this is precisely the failure mode the spike documents as the first wrong attempt's mistake. This is a strong, directly testable structural property: "content placed at instance or group root is invisible to Codex sessions working inside a cloned repo" should be a first-class assertion in any structural test suite the contract implies.

## Surprises

- The spike is unusually emphatic that two independent outside-in attempts got this wrong in *opposite* directions (one assumed an upward walk existed and built on it; a later probe assumed nothing above the working directory is ever read, because its test setup had no root marker at all). This is presented as the whole reason the document exists, and it's a strong signal that this area is exactly where an implementation is likely to be re-wrong a third time by intuition rather than by consulting this document.
- Skills are the one category that loads from an *untrusted* project layer with no gating — this cuts against a plausible assumption that "trust gates the whole `.codex/` layer uniformly." The spike is explicit this was measured, not inferred, specifically to correct that assumption.
- The Claude-plugin-manifest compatibility (Finding 8) is a genuine capability channel the spike treats as already working today, unmodified — but bundled with two limits (no named subagents, and a GitHub-source dependency on Claude Code itself) that make it not a clean drop-in.

## Open Questions

The spike does not address (stated as such rather than filled in):
- How the eight remaining denylisted config keys (beyond provider URLs, `notify`, profiles) affect anything else the project layer might want to carry.
- Whether a non-interactive/headless Codex invocation (vs. the interactive TUI) also blocks on the hook trust prompt, or behaves differently — the spike only describes "an interactive session" blocking (Finding 7).
- Whether any workaround exists to pre-seed `[hooks.state].trusted_hash` from outside the developer's own config (the spike says no route has been *demonstrated*, which is not the same as proven impossible).
- Whether `shell_environment_policy.set` (Finding 6) is itself trust-gated the same way other config keys are — Finding 6 says it "parses cleanly at this layer" without stating whether an untrusted directory's declared env vars actually take effect at runtime, the way Finding 5 explicitly tested for budget and MCP servers. The summary section lists env vars among the trust-gated set, but Finding 6 itself doesn't report a trusted-vs-untrusted comparison test the way Finding 5 does for budget/MCP.

## Summary

The spike is a measured (not inferred) map of codex-cli 0.147.0's discovery mechanics: a bounded downward walk from the nearest `.git`-marked root, strict single-file-per-directory precedence topped by `AGENTS.override.md`, and a shared byte budget that drains outermost-first and truncates silently — three properties that structurally rule out instance/group-level shared context for Codex and make filename and budget choices non-negotiable for any writer. Trust gates the project config layer unevenly and cannot be self-granted: skills load untrusted, but budget overrides, MCP servers, and environment variables require a trust entry the workspace itself cannot create, while hooks, marketplace/plugin registration, trust, and root-marker configuration are excluded from the project layer entirely, with hook installation additionally blocked by an unsolved trust-hash/modal-prompt tradeoff. Claude Code plugin manifests install into Codex unmodified for skills, but named subagents never surface and GitHub-sourced marketplaces depend on Claude Code itself being installed — making named-subagent support and hook automation the clearest concrete items a niwa capability contract must declare unavailable-with-reason for Codex rather than attempt.
