# Lead: What is on the closed `docs/dual-agent-workspace` branch, and which parts are lift-able?

## A. The Failure, Precisely

**The core mechanism: the branch does not choose an agent at materialization time. It always does both, unconditionally, at every niwa-owned level.**

`internal/workspace/content.go:20`:
```go
var materializedAgents = []agent.Agent{agent.AgentClaude, agent.AgentCodex}
```
`internal/workspace/apply.go:1502-1510` loops over `materializedAgents` (not `a.Agent`) to write the workspace-root and instance-root context files for *both* agents on every apply, with the comment stating it outright: "a.Agent does not gate it, because preparation is unconditional."

At the group level (`apply.go:1556-1568`) and the repo level (`apply.go:1619, 1627`), the Claude writer is called with the constant `agent.AgentClaude` hardcoded as the argument — not a variable derived from the resolved session agent — immediately followed by a *separate*, unconditional call to the Codex-specific composer (`InstallGroupCodexContext`, `InstallRepoCodexOverride`). Comments narrate this explicitly: "This runs as Claude whatever a.Agent says" (apply.go:1556, 1619).

The worktree path repeats the same pattern in `internal/workspace/worktree_content.go`: `agent.AgentClaude` is hardcoded at lines 503, 511, 640, and `installWorktreeContextLayer` (defined `worktree_content.go:747`) takes an `ag agent.Agent` parameter that its body never reads — the docstring says the file "runs unconditionally on the Claude pass regardless of the workspace's selected agent."

**`Applier.Agent`: set in five places, read in exactly one, and that one read forwards it into a field that is read in zero places.**

- Declared: `internal/workspace/apply.go:49`.
- Set: `internal/cli/apply.go:201`, `internal/cli/create.go:230`, `internal/cli/init.go:199`, `internal/cli/reset.go:152`, `internal/cli/instance_from_hook.go:501` (hardcoded to `agent.AgentClaude`, not resolved).
- Read: exactly once, `internal/workspace/apply.go:2246`, to populate `WorktreeApplyOptions.Agent` on the worktree-refresh path inside `Apply`.
- `WorktreeApplyOptions.Agent` (`internal/workspace/worktree_content.go:443`) is itself set at two sites (`apply.go:2246` and `internal/cli/session_lifecycle_cmd.go:339`) and read at **zero**. `installWorktreeCodex` (the function that actually does Codex worktree delivery) does not take an `Agent` parameter at all (`internal/workspace/codex_worktree.go:50`); `ApplyToWorktree` never touches `opts.Agent`.

So the entire chain — CLI flag/env/config resolution (`agent.ResolveAgent`, `resolveSessionAgent` in `internal/cli/agent.go:16`) → `applier.Agent` → `WorktreeApplyOptions.Agent` — terminates in a field nothing ever reads. It exists at both ends of the plumbing and nowhere in the middle.

**Only one call site makes a real decision on the resolved agent**, and it does not go through `Applier.Agent` at all — it calls `resolveSessionAgent` independently: `internal/cli/dispatch.go:234-240`, which refuses `niwa dispatch` outright when the workspace's resolved agent isn't Claude ("dispatch only knows how to launch a Claude worker").

**Zero-caller accessors on `agent.Agent`:**
- `LocalContextFileName()` (`internal/agent/agent.go:72`) — defined, documented, never called anywhere in the tree outside its own file and tests. Its docstring even says the Codex-facing equivalent is written by "the dedicated Codex materializer rather than through this accessor," i.e., the function was left in place as a stub that nothing exercises.
- `RootContextFileName()` is called, but every Codex-side call site invokes it on the hardcoded constant `agent.AgentCodex.RootContextFileName()` (`internal/workspace/codex_payload.go:239`, `internal/workspace/codex_context.go:66,159`), never on a resolved variable. The only *variable*-based calls (`content.go:57,86`, `root_materializer.go:375`) iterate the hardcoded `materializedAgents` slice, not `a.Agent`.

**`ClaudeEnabled` gates Codex delivery too, despite its name.** `internal/workspace/override.go:1061` defines it as "whether Claude content installation... should be performed," reading `override.Claude.Enabled`. But it gates the Codex per-repo override and payload-link steps as well: `apply.go:1607` (before conflict detection, which drives both agents' write refusals), `apply.go:1623` (repo-level Claude content, immediately followed by the Codex override composer inside the same `if` block's continuation), `apply.go:1694` (the `.codex` link delivery loop), and `worktree_content.go:176,500` (worktree Codex delivery is skipped when `ClaudeEnabled` is false — `ApplyToWorktree` returns early with only the context layer when `!ClaudeEnabled`). There is no separate `CodexEnabled` — the one opt-out flag, named for one agent, silently governs both.

**Codex `config.toml` declares exactly one key.** `internal/workspace/codex_payload.go`, `renderCodexPayloadConfig` (line ~198) writes only `project_doc_max_bytes` into `config.toml` — a comment block plus that single `fmt.Fprintf`. There is no `mcp_servers` table and no reference anywhere in `codex_*.go` to `.mcp.json`. Grepping the whole tree for `.mcp.json` / `mcp_servers` turns up exactly one place it's produced: `internal/workspace/scaffold.go:80-84`, a Claude-only file-distribution config comment ("Claude Code project `.mcp.json` available to sessions started at those levels"). So `.mcp.json` reaches Claude sessions through the general file-distribution mechanism but has no Codex-side counterpart at all — confirmed exactly as the review states.

## B. Lift-able Inventory

All files below are genuinely **Codex mechanics** — none of them branch on `a.Agent`/`opts.Agent` or contain orchestration logic; they are pure "given these inputs, write/compute this Codex-specific artifact" functions. The call *sites* that invoke them (in `apply.go`, `worktree_content.go`) are what must be rewritten behind the new capability interface — the dispatch pattern (loop over hardcoded constants, sequential hardcoded Claude-then-Codex blocks) is exactly what must not survive.

**What must NOT be lifted as-is:** the *call sites* in `apply.go` (materializedAgents loop; the paired `agent.AgentClaude` hardcode + separate unconditional Codex-composer call, three times over at group/repo/link levels) and `worktree_content.go` (same pattern, plus the fully dead `Agent`/`opts.Agent` plumbing). These are the orchestration/dispatch shape PR 1's new interface exists to replace — every one of them needs to become a loop over declared/implemented capabilities rather than a hardcoded two-pass sequence with an unused discriminator threaded alongside it for show.

## C. The Acceptance Bar (15 scenarios)

All in `test/functional/features/codex-agent.feature` (812 lines), Feature: "prepare every instance for both agents." 13 are `@critical` (offline, no live agent needed); 2 are `@codex-live` (require `codex` on PATH + a usable sandbox, skip-not-fail when absent).

1. **@critical** *a codex-default workspace still materializes the whole Claude tree* — asserts a `default_agent = "codex"` workspace still writes `CLAUDE.md`, `tools/app/CLAUDE.local.md`, etc. in full, and never writes `AGENTS.md` inside a repo (only `AGENTS.override.md` would be legitimate there); re-applies clean.
2. **@critical** *niwa dispatch refuses in a codex-default workspace* — asserts `niwa dispatch` exits non-zero with an error naming `NIWA_AGENT=claude` as the escape hatch when the workspace's resolved agent isn't Claude, before any instance is created.
3. **@critical** *a claude-default workspace materializes both agents' context too* — the mirror of #1: default (Claude) workspace still gets `AGENTS.md` at the instance root, a reachable Codex payload, and a Codex trust entry.
4. **@critical** *a prepared instance serves a Codex session from the instance root down* — asserts Codex's own first-match discovery rule (nearest `.git`, per-directory read, `AGENTS.override.md` beats `AGENTS.md`) actually selects niwa's composed file at every depth including a directory three levels deep with an intervening committed `AGENTS.md`, that the repo's own committed `AGENTS.md` is untouched (byte-identical to git HEAD) alongside it, that the payload is link-reachable from the repo, that no hooks/credentials are declared, and that git status stays clean.
5. **@critical** *a workspace with nothing to say leaves the repository's own context in place* — asserts that with zero configured content, niwa writes no `AGENTS.override.md` at all (the never-empty rule) so the repo's own committed `AGENTS.md` remains what Codex selects.
6. **@critical** *the declared budget covers a context chain past Codex's default* — asserts a chain that exceeds Codex's stock `project_doc_max_bytes` default is nonetheless fully within the budget niwa declares in `config.toml`, and the innermost (repo) layer survives (isn't silently truncated).
7. **@critical** *the workspace's skills reach Codex whole and namespaced* — asserts a configured plugin's whole tree (manifest, references, scripts) lands byte-identical under `.codex/skills/<name>`, resolves through symlink target-matching, and re-applying twice leaves exactly one link (no duplication).
8. **@critical** *trust entries are canonical, one per repository, and additive* — asserts trust entries are keyed by the *canonical* (symlink-resolved) path, exactly one per repo, that the developer's pre-existing config content (`model`, `[tui]` table) is untouched, no global key is added, the credential file is never touched, and three applies produce the same two entries (no accumulation).
9. **@critical** *an unreadable credential file fails neither create nor apply* — asserts `niwa create`/`niwa apply` both succeed and still write the trust entry even when `~/.codex`'s credential file can't be read (trust writing never opens it).
10. **@critical** *a worktree carries the workspace context and its own framing* — asserts a `niwa worktree create` gets its own composed `AGENTS.override.md` (selected over any repo-level file) carrying instance content plus purpose/branch framing, a reachable payload, clean git status, and that the *repository's* single trust entry (not a new per-worktree entry) is what covers it.
11. **@critical** *re-applying three times adds nothing* — asserts the git-exclude patterns, the payload's config-file count (1), the trust-entry count (1), and the composed content are unchanged/non-duplicated across three `niwa create`+`apply` runs.
12. **@critical** *changed content replaces the previous content everywhere* — asserts editing the source content and re-applying replaces (not appends to) the composed file both in the clone and in an existing worktree, with old sentinel text absent from both.
13. **@critical** *committed content at niwa's names degrades loudly and is never overwritten* — three sub-cases in one scenario: a committed `.codex/config.toml` suppresses link+override+trust entirely (reported, git HEAD untouched); a committed `AGENTS.override.md` alone suppresses only the composed context (payload/trust unaffected); a committed `AGENTS.md` that is a *symlink* to the credential file is refused at open ("was not inlined") so its target bytes never leak into composed context, and the credential file itself stays unchanged.
14. **@codex-live** *a live Codex session writes a file on its first attempt* — gated on `codex` on PATH + a usable sandbox; asserts `codex exec` in a freshly-prepared repo can actually write a file on the first try, no setup step first (this is what the trust bootstrap exists to guarantee).
15. **@codex-live** *a live interactive Codex session starts clean from the root and from a nested directory* — gated on `codex` on PATH; asserts an interactive `codex` session under a pty reaches its ready state with no trust/approval prompt shown, both at the repo root and from a directory nested inside it.

**Step definitions** (`test/functional/codex_dual_agent_steps_test.go`, 1450 lines, `registerCodexDualAgentSteps`, godog `ScenarioContext`): staging helpers (staged files/dirs/symlinks pushed into fixture repos), Codex context-chain resolution mirroring Codex's own discovery algorithm (`codexContextChain`, `codexProjectRoot`, regex-parsing `project_doc_max_bytes` out of `config.toml` via `projectDocMaxBytesRE`), payload/skills-link assertions (symlink-target comparison, tree-diffing via `readTreeFiles`), developer-config assertions (canonical-path trust lookups, credential-file hash/mtime comparisons, "grew only by project entries" diffing), git-status/exclude assertions, and the live-gate steps (`codexIsAvailable`, `theCodexSandboxCanRunHere`, PTY-driven `iStartInteractiveCodexAt`/`theCodexSessionReachedReadyState`/`theCodexSessionShowsNoTrustPrompt`). All of it depends on a shared `testState` fixture type from the broader functional suite (git server, registry, instance/config helpers) and real `git`/`codex` binaries — this is an end-to-end filesystem-and-process suite, not a unit-test mock layer.

## Design vs. delivery

`docs/designs/current/DESIGN-dual-agent-workspace.md`'s Decision 7 (lines 531-620) **correctly diagnosed exactly this class of failure in advance** and prescribed the fix: retire `LocalContextFileName()`'s dead Codex branch and a `WritesRepoLevelContext()` accessor entirely ("Retiring rather than keeping them means the seam cannot silently assert a contract this design abandons"), and explicitly narrows the `Agent` field's meaning to "survives only where launch-time selection is real: `niwa dispatch`'s refusal and the model category resolver." The Implementation Approach section (lines 971-1036), batch 1, restates it as an instruction: "retire the two dead accessors and their tests."

**What shipped diverges from what was prescribed on both counts.** `LocalContextFileName()` is still present and still uncalled (design said retire it; it wasn't). The `Agent` field wasn't narrowed to the two places the design said it should survive — it's threaded through five CLI entry points into `Applier.Agent` and then `WorktreeApplyOptions.Agent`, neither of which is read anywhere, and even the one legitimate use case the design named (the model category resolver, `internal/cli/dispatch_model.go`) doesn't consume the resolved value either — `resolveDispatchModel` is called with the hardcoded `agent.AgentClaude` (`dispatch.go:353`), not a resolved variable. The dispatch refusal (the other named legitimate use) does work, but by calling `resolveSessionAgent` fresh rather than reading `Applier.Agent`. So even under the design's own reduced ambition for what the `Agent` field should do, the delivered code does less than that — the field carries zero decisions anywhere in the pipeline it's threaded through.

## Implications

- **PR 1's contract must make "unread field" and "hardcoded constant at a call site" structurally impossible, not merely discouraged.** The prior attempt had explicit design-doc language calling out the exact anti-pattern it then re-introduced. A field/constant that compiles clean but is never consulted is not something code review reliably catches in a 6000-line diff; the new abstraction needs either (a) no separate "resolved agent" value distinct from "the list of capability implementations to run," so there's nothing to leave unread, or (b) a test that asserts every accessor/field has a caller (grep-based or reflection-based), enforced in CI.
- **The materialization call sites are the actual rewrite target, not the Codex-specific files.** Every file in the Lift-able table survives close to as-is; what has to change is `apply.go`'s and `worktree_content.go`'s control flow — replacing "call agent.AgentClaude writer, then separately and unconditionally call the Codex composer" with a loop over declared capability implementations, so a third agent (or Codex being turned off) is a data change, not a third hardcoded block.
- **`ClaudeEnabled` needs a real rename or a real generalization**, not another agent-named boolean that quietly governs both agents' writers. Whatever PR 1 introduces for "is this repo opted out of niwa-written context" should not carry an agent's name if it's meant to gate every agent's delivery.
- **The trust-adapter's nil-by-default function-pointer seam is worth preserving as a pattern** for PR 2's Codex implementation — it is the one place in the branch where an agent-specific side effect (editing the developer's real config) is wired in explicitly by every real CLI entry point rather than defaulting on, and it already has test-friendly injection built in.

## Surprises

- The design doc's Decision 7A analysis is essentially a pre-mortem of the exact bug the review found — it names the two dead accessors by file:line and says to delete them, and the PR shipped with one of them (`LocalContextFileName`) still present, uncalled, and undocumented as dead in the shipped code (its doc comment reads as if it's meaningfully used).
- `Applier.Agent`/`WorktreeApplyOptions.Agent` is dead *twice over*, in two different struct hierarchies threaded through six CLI entry points, and none of the six code paths that set it are the one code path (`dispatch.go`) that actually makes a decision from the resolved agent — that path recomputes it independently.
- `ClaudeEnabled` gating Codex delivery (not just Claude delivery) was not something I expected going in; it's a real coupling that a capability-per-agent contract needs to either preserve deliberately (rename to something agent-neutral) or explicitly split.

## Open Questions

- Does PR 1's chosen contract need a *compile-time* mechanism (e.g., a capability list iterated by the pipeline, with no way to write a bare `agent.AgentClaude` literal at a call site without it being visibly out of place) or is a CI-enforced "every exported accessor has ≥1 caller" grep sufficient? The prior attempt suggests review discipline alone did not catch this even with an explicit design-doc warning.
- The `@codex-live` scenarios depend on PTY-driving a real `codex` binary and gate on kernel sandbox support. Does the new capability contract need its own "declared unavailable with a reason" surface exercised by an equivalent live/gated scenario for the *capability-not-implemented* case (e.g., a third hypothetical agent with no live binary), or is that out of scope for PR 1/PR 2 and only relevant once a third agent exists?

## Summary

The branch's core failure is structural, not accidental: every niwa-owned level always writes both agents' files unconditionally via a hardcoded `materializedAgents` slice and hardcoded `agent.AgentClaude`/`agent.AgentCodex` literals at each call site, while the resolved-agent value is threaded through `Applier.Agent` → `WorktreeApplyOptions.Agent` and read by nothing — the design doc even predicted and prescribed retiring this dead plumbing, and the delivered code kept it anyway. Nearly all of the Codex-specific mechanics (`codex_compose.go`, `codex_conflict.go`, `codex_link.go`, `codex_payload.go`, `codex_trust.go`, `codex_worktree.go`, and the trust-adapter wiring pattern) are agent-mechanics files with no orchestration logic baked in and are directly reusable by PR 2; what must not be reused is the `apply.go`/`worktree_content.go` call-site shape that invokes them. The 15-scenario `codex-agent.feature` suite is a legitimate, comprehensive acceptance bar (13 offline @critical scenarios covering discovery precedence, budget sizing, skills delivery, trust bootstrap idempotency, worktree parity, refresh-not-append, and conflict degradation, plus 2 gated @codex-live scenarios for real-session behavior) that PR 2 should be able to satisfy largely unchanged once it's driven through a real capability contract instead of the two hardcoded passes.
