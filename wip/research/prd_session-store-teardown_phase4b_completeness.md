# Completeness Review (round 2)

Target: `docs/prds/PRD-session-store-teardown.md` (status: In Progress, R1..R25)
Downstream: `docs/designs/DESIGN-session-store-teardown.md` (status: Planned)
Code verified against: `internal/cli`, `internal/worktree`, `internal/workspace`, `internal/watch`, `internal/config` at HEAD `de16b51` (pre-fix; no Go source modified in the worktree).

## Verdict: FAIL

The acceptance criteria and cross-references are in good shape, but five decisions an implementer needs are absent from the requirements and had to be invented in the design, two statements in R10 and the Decisions section are factually wrong about today's code, and three requirement clusters (R15, R16, R22-R23) have no anchor in the Problem Statement, Goals, or User Stories.

## Issues Found

1. **`--force` is undefined for a session-resolved destroy, on the one command whose whole point is the merged-branch guard.** `niwa worktree destroy --force` exists today and is documented as "Destroy even with uncommitted changes, and delete the branch regardless of merge status" (`internal/cli/session_lifecycle_cmd.go:116`); in `DestroySession` it swaps `git branch -d` for `git branch -D` and disarms both the attach and dirty guards (`internal/worktree/worktree.go:292, 307, 335-340`). R1 lists what the positional accepts and R2 says each worktree is destroyed "with the guards `niwa worktree destroy` applies today", but nothing says what `--force` plus a session id does — and it would mean force-deleting every branch in every active worktree of the instance in one invocation. The design had to decide this on its own (`DESIGN` line ~333: "`--force` with a session id or handle is refused as a usage error (exit 2); forcing stays available one worktree at a time"). Fix: add a requirement stating that `--force` combined with a session id or handle is a usage error, add the row to R9's outcome table, and add an acceptance criterion.

2. **Exit codes 3 and 4 are not new to the `niwa worktree` command group, and the new meanings collide with the existing ones.** The Decisions section asserts "Codes 3 and 4 are new; 0, 1 and 2 keep their meanings." In fact `niwa worktree attach` already exits **3** when the attach lock is held (`internal/cli/sessionattach/attach.go:91, 99`; `detach.go:78-85`) and `niwa worktree detach --force` exits **4** after killing a live holder (`detach.go:98`), both published in the "Attach exit codes" table at `docs/guides/worktree.md:528-537`. After this change, exit 3 inside one command group means both "attach lock held" and "no worktree or session matches", and exit 4 means both "killed a live holder" and "ambiguous value". The second user story is explicitly about a script switching on exit status, so this matters. Fix: correct the claim, and either reconcile the codes across the group or state in a requirement that the destroy codes are scoped to `destroy` and that `docs/guides/worktree.md` gains a second table.

3. **R10 misstates what `niwa worktree create` does at the root today, and as written it silently changes that exit code.** R10's table says `create`, `apply`, `attach`, `detach` and `niwa go` "already exit 1 at the root today, with a misleading error read from the mapping store, so only the message changes." Verified: bare `niwa worktree create` at the root exits **2**, not 1, via `&ExitCodeError{Code: 2}` with "could not infer repo from working directory" (`internal/cli/session_lifecycle_cmd.go:161-166`) — and that error never touches the mapping store; with an explicit repo it exits 1 through `findRepoInWorkspace` / `ErrSessionUnknownRole`, also not from the mapping store. R10 therefore moves bare `create` from exit 2 to exit 1, which R21 ("existing invocations keep their ... exit codes") forbids and no acceptance criterion catches — the matching AC only exercises the `<x>`-taking forms. (`attach`/`detach` are also loose: they print `session <id> not found` with no path, so "misleading error read from the mapping store" is only true of `apply`, `destroy` and `niwa go`.) Fix: correct the row, and say explicitly whether bare `create` at the root is meant to change from 2 to 1.

4. **"Single-instance layout" is load-bearing but never defined, and the in-between root falls through both branches of R10.** R10's closing paragraph and two Known Limitations turn on the term; Terms defines "Instance of this workspace" and "Instance location" but not this one. Today's production rule is "`EnumerateInstances` returns nothing AND `<root>/.niwa/instance.json` exists" (`internal/cli/apply.go:363-368`), which also matches a freshly initialized workspace and one whose instances were all reaped — and in that state treating the root as the instance puts new worktrees under `<root>/.niwa/worktrees/`, inside the directory `materializeAndSwap` rotates wholesale, where the next refresh destroys them. R10's table is scoped to "the root of a multi-instance workspace" and its AC requires "at least one mapping", so that root is in neither branch. The design noticed and had to tighten the rule itself, inventing `workspace.IsSingleInstanceLayout` as "no child instance, and the root's `instance.json` names an instance" (`DESIGN` line ~280-288) — a change to existing resolution that R21 does not sanction. Fix: define the layout in Terms and state the outcome for a root with no child instances whose `instance.json` names no instance.

5. **R15, R16 and R22-R23 have no anchor in the Problem Statement, Goals, or User Stories.** The Problem Statement's #297 paragraph names exactly four failures — staging collision, lost write, resurrected delete, directory left without config — which map cleanly to R11-R14. Nothing above the Requirements section mentions:
   - **R15's failure**, which is the worst one in the document: a mapping-store read taken mid-swap looks empty, and the reaper's backstop eligibility is precisely "no session mapping for that instance path" (`internal/cli/reap.go:592-640`, `dispatchBackstopTTL = 30 * time.Minute` at `reap.go:29`), so a live, mapped dispatch instance becomes reclaimable and is deleted.
   - **R16** (an interrupted refresh leaving the directory unusable).
   - **R22-R23**, whose motivating failure — a torn read of the root `instance.json` dropping `ephemeral_session_mode` and silently stopping ephemeral provisioning for the whole workspace — appears only in a Decisions bullet. Verified: `initState, _ := LoadState(workspaceRoot)` at `internal/workspace/apply.go:481` ignores the error, `saveWorkspaceRootDisclosures` (`apply.go:2727-2748`) rewrites from it, and `SaveState` is a bare `os.WriteFile` with no temp-and-rename (`internal/workspace/state.go:297-313`), unlike `WriteSessionMapping` (`session_map.go:159-165`) and `watch.writeHandledState` (`internal/watch/state.go:182-200`).

   Fix: add a Problem Statement paragraph covering mid-swap reads, interrupted refreshes and the root-state write, plus at least one goal and one user story for the instance.json case.

6. **R17's bounded-wait failure has no exit code, no row in R9's contract table, and breaks R21.** R17 says the command "fails with an error that names the configuration directory"; the acceptance criterion only asserts "exits non-zero within 2 seconds". R9 is the table a cleanup script reads, and it has no row for this. Worse, R21 says existing invocations keep their exit codes, but the design notes that destroy by worktree id now reads the root mapping store and so "under contention past the 30-second bound it can fail with R17's error" — a new failure mode on an invocation that always succeeds today, with no carve-out in R21. Fix: name the exit code, add the R9 row, and carve the exception into R21.

7. **`niwa worktree list --json` at the root is unspecified.** R10 says `list` at the root prints the redirect on stderr, no table, exit 0. `--json` exists and prints a JSON array on stdout (`internal/cli/session_lifecycle_cmd.go:654-665`). The design had to assume: "`niwa worktree list --json` at the root still prints `[]` on stdout, since R21 keeps existing output" (`DESIGN` line ~272-274). Fix: add the `--json` row to R10's table.

8. **`NIWA_INSTANCE_ROOT` is not addressed by R3 or R10.** Both requirements are stated purely in terms of cwd, but `resolveInstanceRoot` returns `NIWA_INSTANCE_ROOT` verbatim before any cwd walk (`internal/cli/session.go:136-145`), and it is a documented setup-script contract (`docs/guides/setup-scripts.md:47`). Since the design puts the root refusal inside `resolveInstanceRoot`, whether the override is refused at a root is a real behavioral question it had to assume away ("`NIWA_INSTANCE_ROOT` stays a verbatim override and is never refused", `DESIGN` line ~269). Fix: state the override's precedence in R3 or in Terms.

9. **A fourth, unlocked mapping-store reader is neither covered by R15 nor excused in Known Limitations.** R15 names the reaper and `niwa worktree destroy`; Known Limitations excuses the ephemeral hook's `ephemeral_session_mode` read and the upward config search. But `workspace.ephemeralInstancePaths` (`internal/workspace/state.go:447-470`), reached from `EnumerateInstanceRecords` (`state.go:416-436`) and used by `niwa list`, does its own `os.ReadDir` of `<root>/.niwa/sessions` with an inline decode, bypassing `ListSessionMappings` entirely — so a mid-swap read there shows ephemeral instances as non-ephemeral. Fix: either add it to R15 or name it in the "Other readers ... can still see a swap" limitation.

10. **The provenance marker's non-atomic in-place rewrite is uncovered.** R22 requires atomic `instance.json` writes but says nothing about `.niwa-snapshot.toml` (`ProvenanceFile`, `internal/workspace/state.go:39`), which the GitHub no-drift path rewrites **in the live directory** with `os.OpenFile(..., O_WRONLY|O_CREATE|O_TRUNC, 0o644)` rather than through a swap (`internal/workspace/snapshotwriter.go:186-194`; `provenance.go:43`). Since `provenanceMarkerExists` is the gate that decides whether a directory is in the snapshot model at all (`snapshotwriter.go:113`), a concurrent reader seeing it truncated is consequential. R14's acceptance criterion even asserts the marker is present after a swap, so the PRD is aware of the file. Fix: extend R22 to the marker, or add it to Known Limitations.

11. **R11's caller list omits two real callers, and the design was misled by the omission.** R11 names `niwa dispatch`, `niwa create`, `niwa apply`, `niwa reset` and the ephemeral-session hook, with a catch-all. Also refreshing: `niwa watch`, whose `stageReview` calls the shared provisioner (`internal/cli/watch.go:781` → `instance_from_hook.go:454`), and `niwa config set global`, which calls `MaterializeFromSource` on the global config dir directly (`internal/cli/config_set.go:76`). The design's Decision 1 records the key assumption "`niwa watch` never refreshes config" (`DESIGN` line ~148-150), which the `watch.go:781` path contradicts. The catch-all technically covers them, but naming them would have prevented the wrong assumption. Fix: add both to R11's list.

12. **The Terms' "newest mapping" claim about `niwa list` is over-broad.** The newest-`Created`-with-session-id-tiebreak rule does exist at `internal/cli/list.go:179-192`, but it governs only the displayed session name (`list.go:201-203`). `resume` deliberately uses the *last* mapping in session-id order (`list.go:187-189`, with a comment saying so); `keep_alive` and `accepts_session_messages` OR across all mappings (`list.go:181-186`); and the reaper's own join takes the last in session-id order (`reap.go:346-350`). There is no shared helper today — the design adds `workspace.NewestMappingPerInstance` and has `list.go` "also adopt" it. Fix: narrow the sentence to "the ordering `niwa list` uses to pick an instance's session name".

13. **Destroying the worktree you are standing in is unaddressed.** R3 explicitly blesses running teardown "from inside a niwa-managed worktree" and R2 destroys *every* active worktree in the session's instance, so running teardown from inside one of the target session's own worktrees removes the cwd. There is no cwd guard in `DestroySession` today — only the attach and dirty guards (`internal/worktree/worktree.go:292, 307`) — and the matching AC says "from inside a niwa-managed worktree" without saying whose. Fix: say whether this is refused or allowed, and pin it in the AC.

14. **R9 introduces a second shape for an existing output line, and leaves one placeholder undefined.** Today destroy prints `session: destroyed %s\n` — the id alone (`internal/cli/session_lifecycle_cmd.go:593`). R9's session-resolved line is `session: destroyed <worktree-id> (<repo>) at <path>`, and the AC keeps the by-worktree-id path byte-identical, so `session: destroyed` now has two shapes depending on how the target resolved. That may be intended, but the PRD never says so. Separately, the "no active worktree" row uses `<instance>` where the adjacent row uses `<path>` — name or path is unstated. (`<repo>` is derivable: `SessionLifecycleState.Repo`, `internal/worktree/session_lifecycle.go:41`.) Fix: state that the two shapes are deliberate, and define `<instance>`.

15. **Three requirement clauses have no acceptance criterion.** R3's "From any directory outside the workspace, the command fails as it does today"; R10's "Shell completion of worktree ids | Offers nothing, as today" (`completeSessionIDs` shares `resolveInstanceRoot`, `internal/cli/completion.go:97-116`, so the root refusal does reach it and is worth pinning); and R10's "The WorktreeRemove hook | Logs and exits 0, as today" (`runFromHookRemove` returns nil by contract, `internal/cli/session_from_hook_cmd.go:249-265`). All three are cheap to test and each guards a path the design changes.

## Suggested Improvements

1. **Widen the AC preamble's range from R11-R13 to R11-R14.** R14 is proven by the same class of forced writer test — the "mapping write while a swap is renaming the directory" criterion is exactly its proof — so the preamble's sanctioning sentence should cover it.
2. **Add root-level worktree aggregation to Out of Scope.** The Decisions section says `niwa worktree list` at the root "could list every instance's worktrees, but that's a new feature." That belongs in Out of Scope, where it prevents scope creep, not only in the rationale.
3. **Reconcile the second user story's outcome list with R9.** The story names four script-visible outcomes; R9 defines five (ambiguity, exit 4), and R17 adds an unspecified sixth. Either the story or R9 should be the authority.
4. **Reword the single-instance Known Limitation.** "not covered by R12-R16" is partly vacuous, since R12 and R13 are about mappings specifically; say instead that the ordering guarantee does not extend to lifecycle records in that layout.
5. **Note in Terms that a handle is taken verbatim.** `withHandle` sets `rec.Handle = filepath.Base(dir)` with no shape check (`internal/cli/session_records.go:212-224`), and the 8-hex layout is documented as empirically observed (`internal/cli/job_state.go:176-182`). The PRD's hedge ("in every observed case") is already accurate; saying the handle is unvalidated makes clear *why* R4's fallback is limited to exactly 8 hex.
6. **Strengthen the watch-state Known Limitation.** It reads as a passive gap, but `niwa watch`'s own `stageReview` triggers a refresh (`watch.go:781`) *before* writing the records that the refresh does not carry (`materializeAndSwap` carries only `instance.json`, `dispatch-briefs/` and `sessions/`, `snapshotwriter.go:443-464`), so watch routinely destroys its own handled-set. Worth saying, since it affects how urgent the follow-up issue is.
7. **Add #297 to the frontmatter.** `source_issue: 292` traces only half the feature; the PRD covers #292 and #297 throughout.

## Coverage summary by evaluation question

1. **Sufficient requirements?** No — issues 1, 4, 6, 7, 8 are each a decision the implementer must make and the design demonstrably made on its own.
2. **Problem-statement gaps?** Yes — issue 5. Three requirement clusters, including the two most damaging failure modes, appear only in the Requirements and Decisions sections.
3. **AC coverage?** Strong. Every requirement has at least one criterion except the three clauses in issue 15, and the pre-fix-fails markers are placed on the criteria that actually discriminate.
4. **User stories?** Six of seven scenarios map to requirements. Missing: a developer whose ephemeral provisioning silently stops after parallel dispatches (R22-R23), and the reaper deleting a live mapped worker (R15).
5. **Out of Scope?** Clear and unusually well-argued; the eight bullets each name the thing excluded and why. Two additions would close the remaining drift paths (Suggested Improvement 2, and `--force` from issue 1 if the answer is "refused").
6. **Numbering?** Clean, as above.
