# Clarity Review

## Verdict: FAIL
The PRD is precise in most places. It fails on four points that would lead two developers to build different things: the output contract a cleanup script depends on, partial-failure behavior across several worktrees, per-command latitude in R8, and a direct conflict between R9's "any number ... all complete" and R15's bounded-wait failure.

## Ambiguities Found

1. **Goals (bullet 2), User Story 2, R6: script-readable outcome.** The text says a script "can tell from exit status and output whether teardown acted, found nothing to act on, or failed to resolve the id." But R6 gives "destroyed", "nothing to destroy", "instance already removed" and "destroyed but kept a branch" all exit 0, and gives "no match", "ambiguous" (R5), "guard refusal" and possibly "mapping outside workspace" (R7) all just "non-zero". So the script has to parse human-readable output, and the PRD never says what that output looks like: no stable strings, no stream assignment (only the kept-branch warning is pinned to stderr, and only in an AC), no machine-readable mode. One developer might ship free-form prose while another ships fixed prefixes or distinct exit codes, and both would satisfy the text. -> **Suggested clarification:** Pick one contract and state it. Either give distinct exit codes (for example 0 acted, 0 or 3 nothing to act on, 2 unresolved id, 1 guard refusal), or name fixed, documented output tokens per outcome and the stream each goes to (for example a `kept-branch:` line on stderr). Add an AC that checks each outcome against that contract.

2. **R2 / R6 / AC "worktree with uncommitted changes": partial failure across several worktrees.** R6 says a guard refusal "exits non-zero after reporting which worktrees were and weren't destroyed." That allows three different implementations: stop at the first refusal, keep going and destroy every worktree that passes its guards, or pre-check them all and destroy nothing if any would refuse. The AC ("reports which other worktrees (if any) were destroyed") accepts all three, and which worktrees get destroyed depends on iteration order. -> **Suggested clarification:** State the policy. For example: "Every worktree is checked and each one that passes its guards is destroyed; worktrees that refuse are left in place; the command exits non-zero if any refused." Or, alternatively, "all-or-nothing pre-check." Pin iteration order if the answer depends on it.

3. **R9 vs R15: "any number" vs bounded wait.** R9 says any number of concurrent refreshes "all complete without an error caused by another command's refresh." R15 says a command waiting past the bounded wait fails with an error naming the directory, and that error *is* caused by another command's refresh. With enough concurrent commands, or one slow critical section, the two requirements contradict each other. R10 ("a mapping write never fails because a refresh moved the directory") has the same gap relative to R15. -> **Suggested clarification:** Put a bound on R9: "up to N concurrent commands (at least 4, matching the AC), each completing its critical section within X, all succeed." Or carve out explicitly: "except the R15 timeout error, which must not occur under the conditions in the AC."

4. **R14 / R15 / Decisions ("Waiting is bounded and short"): the bound is unspecified.** "Bounded wait" and "short" have no value, order of magnitude, or statement of whether it's configurable. The AC "a refresh whose fetch is held for longer than the bounded wait" can't be written without knowing it, and "short" is subjective. -> **Suggested clarification:** Give a default (for example "30 s by default") or at least a ceiling ("no more than 60 s"). Say whether an env var or flag overrides it, or state explicitly that the DESIGN sets the value but it must be a named constant the tests can override.

5. **R8 and the AC for `list/apply/attach/detach/go`: behavior is left to each command.** "Either resolve per R1-R3 or fail with a message" lets each of five subcommands pick independently. R1 only extends `destroy`, so it's unclear whether `attach <session-id>` or `go <session-id>` from the root is required, allowed, or out of scope. The Open Question admits this for `list`. Also, "fail" (R8) and "prints a message" (AC) don't say whether the exit is non-zero. -> **Suggested clarification:** Give the behavior per subcommand in a small table: which ones accept a session id at the root, and which print "run inside an instance or pass a session id" with a stated exit code. Resolve the Open Question before sign-off. Also say whether `niwa worktree create` at the root is covered, since the AC omits it.

6. **R17 vs R8: "no change to exit codes of existing successful invocations."** Today, `niwa worktree list` (and others) at the workspace root succeeds with an empty result read from the mapping store. R8 turns that into a failure with a message. That is a change to the exit code of an existing successful invocation, so as written R17 forbids what R8 requires. -> **Suggested clarification:** Add "except the root-level invocations R8 changes" to R17, or require the R8 message path to exit 0.

7. **R5: what counts as the collision.** R5 and its AC cover an 8-hex value that equals "a session's handle." It doesn't say whether a match through R4's unique session-id prefix (a handle-less mapping) also counts as a collision with a worktree id. It also doesn't cover a non-8-hex handle that equals a worktree id. -> **Suggested clarification:** "A value collides when it resolves as a worktree id in the current instance *and* resolves to a session by any R1/R4 rule (recorded handle or unique prefix)." Drop the 8-hex qualifier, or state why only 8-hex values can collide.

8. **R5: "run from the other location" has no escape to the worktree reading.** A collision can only happen inside an instance, since worktree ids don't resolve at the root (R8). Moving to the root gets you the session. Passing the full session id also gets you the session. Neither route lets the developer say "I meant the worktree." -> **Suggested clarification:** Name the way to disambiguate toward the worktree (for example `--by-path`, or a new `--worktree`/`--session` selector if that doesn't breach R17's "no new flags" user story), and have the refusal message print both commands.

9. **R4: precedence between a recorded-handle match and a prefix match.** If a value equals mapping A's recorded handle and is also the unique session-id prefix of handle-less mapping B, R4 doesn't say whether that resolves to A, counts as ambiguous, or is something else. It also doesn't say whether recorded handles are unique across mappings, or whether hex matching is case-sensitive. -> **Suggested clarification:** "The value is matched against recorded handles and against session-id prefixes of handle-less mappings; if more than one mapping matches by any rule, refuse and name them all. Hex matching is case-insensitive" (or case-sensitive, whichever is intended).

10. **R2 and elsewhere: "active niwa-managed worktree" is undefined.** The first AC implies "active" means "record not marked ended," but a record could also be not ended while the directory is gone, or ended while the directory is still present. -> **Suggested clarification:** Define it once: "a worktree whose lifecycle record in the instance is not marked ended," and say what happens when the record is active but the directory is missing.

11. **R7 and its AC: reporting and exit status for an out-of-workspace mapping.** "Reported and not acted on" gives no exit code. "Names an instance of the same workspace" doesn't say how that's decided (path prefix after symlink resolution? an instance marker file?). The AC only tests a path *outside* the workspace, not an in-workspace path that isn't an instance, such as the root itself or `.niwa/`. -> **Suggested clarification:** Say how "is an instance of this workspace" is determined, give the exit code (presumably non-zero, since it's closer to "unresolved" than "nothing to do"), and add an AC for an in-workspace non-instance path.

12. **R12: "never left missing its configuration content."** It's unclear whether a transient absence during the swap, visible to a concurrent reader, violates R12, or only a final state after all commands finish. "Configuration content" isn't defined either (workspace.toml? the whole snapshot?). No AC maps to R12. -> **Suggested clarification:** "After every concurrent command has finished, the directory contains the configuration files from the most recent successful refresh." Add an AC, or fold R12 into an existing one explicitly.

13. **AC "repeated enough times in the test that the pre-fix code fails it."** "Enough" is subjective and the result is nondeterministic, so a reviewer can't verify it objectively. -> **Suggested clarification:** Either force the interleaving with a test hook (as the next two ACs do), or state a threshold (for example "fails on pre-fix code in at least 9 of 10 CI runs at N iterations").

14. **AC reaper-during-swap.** Unlike the neighbouring mapping ACs, this one doesn't say the ordering is forced or that it fails on pre-fix code, and it doesn't mention the 30-minute backstop age the Decisions section says triggers the loss. -> **Suggested clarification:** "In a test that forces the reaper's mapping read to occur mid-swap, against an unmapped-looking dispatch instance older than the backstop threshold, the reaper does not destroy it; the test fails on pre-fix code."

15. **AC "with no file changes."** The scope is unclear. Does this include worktree lifecycle records, logs, or timestamps written by the resolution itself? -> **Suggested clarification:** "No worktree directory, branch, or worktree record is created, modified, or removed."

16. **R16 and the final AC: macOS and the "non-unix GOOS".** R16 promises the ordering guarantee on macOS, but the ACs only exercise Linux. "A non-unix GOOS" doesn't name one. "The underlying primitive" is never named, so "platforms without it" can't be enumerated. -> **Suggested clarification:** Name the target (for example `GOOS=windows go build ./...`), name the primitive (for example advisory file locks via flock), and either add a macOS CI run or say macOS correctness is by construction and untested.

17. **Goals / User Story 4: "working instance" and "resumable".** The four-parallel-dispatch AC checks exit 0 and four distinct mappings, but not that each instance is usable or each session resumable. -> **Suggested clarification:** Define "resumable" concretely (for example "each mapping's instance directory exists and `niwa list` shows all four") and check it in the AC, or drop the word from the goal.

18. **R3: "from inside a worktree" and other locations.** It's unclear whether this means only niwa-managed worktrees or any git worktree, or what happens in a workspace-root subdirectory that isn't an instance (for example inside `.niwa/`), or outside the workspace entirely. -> **Suggested clarification:** List the supported working directories and the error for anything else.

## Suggested Improvements

1. **Add an outcome table for `niwa worktree destroy`.** One row per case: worktree id, session with worktrees, session with none, instance gone, no match, ambiguous, guard refusal, mapping outside the workspace. Columns for exit code, stdout and stderr. The rationale: it collapses ambiguities 1, 2, 7, 8 and 11 into one checkable artifact, and it's exactly what User Story 2's script author needs.
2. **Reconcile R9, R10, R15 and R17 in one sentence each.** The rationale: these are the only outright contradictions in the document, and they'll surface as reviewer disputes in the DESIGN or the PR if they aren't settled here.
3. **Resolve the Open Question and make R8 per-command.** The rationale: an Open Question that R8 explicitly leaves to the implementer guarantees the choice happens implicitly in code review.
4. **Replace "bounded" and "short" with a number or a named, test-overridable constant.** The rationale: two ACs depend on the value, and without one they can't be written consistently.
5. **Make every concurrency AC deterministic (forced ordering) and state "fails on pre-fix code" uniformly.** The rationale: the refresh-vs-refresh and reaper ACs are the only ones a reviewer can't verify objectively.
6. **Define "active worktree", "handle", and "instance of this workspace" once, near R1.** The rationale: these terms carry the resolution logic, and each is currently inferred from context.

## Summary
The problem statement is concrete and evaluable, the user stories map cleanly to test cases, and most acceptance criteria are binary. The gaps sit where the PRD hands behavior to the implementer without saying so: the script-facing output contract, partial-failure semantics, R8's per-command choice, and an unquantified bounded wait that contradicts R9's "any number" guarantee. A short outcome table for teardown, plus a few reconciling sentences for R9, R10, R15 and R17, would bring it to a PASS.
