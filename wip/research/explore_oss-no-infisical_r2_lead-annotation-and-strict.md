# Lead: How would two newly-decided requirements actually land in niwa's code?

Round 2. Builds on `wip/explore_oss-no-infisical_findings.md`. Two mechanisms:
(A) comment annotations for unresolved keys in generated env output, and (B) a
strictness switch that turns the lenient default back into a hard failure.

---

## Findings

### A. Comment annotations in the generated `.local.env`

#### A1. The writer is one 106-line leaf package with a single call site

`internal/envformat/envformat.go` is the whole serializer. `Marshal(format, kvs)`
dispatches to three writers over an ordered `[]KV` (`envformat.go:36-47`). There
is exactly one production call site: `internal/workspace/materialize.go:1361`,
inside `(*EnvMaterializer).Materialize` (`materialize.go:1303`). Nothing else in
the repo calls `envformat.*` — verified by grep across all non-test Go files.
So the annotation lands in one function and flows to every target automatically.

The dotenv writer already emits a comment: a fixed header,
`"# Generated by niwa - do not edit manually\n"` (`envformat.go:33`), shared with
the shell writer (`envformat.go:97`). The JSON writer does **not** emit it
(`envformat.go:68-91`) — JSON has no comment syntax, and niwa already silently
drops the header there. That precedent settles the format question: dotenv and
shell get `#` comment lines, JSON gets nothing, and the stderr report is the
format-independent channel.

#### A2. Today an unresolved key is written as an empty value, not omitted

The resolver's downgrade branches return a zero `config.MaybeSecret{}`
(`resolve.go:531` for `?required=false`, `resolve.go:535` for
`--allow-missing-secrets`), and `walkTable` writes that zero value straight back
into the map: `values[key] = resolved` (`resolve.go:389`). The key therefore
survives into `envCfg.Secrets.Values`, `ResolveEnvVars` calls
`maybeSecretString(v)` on it (`materialize.go:1198`), which returns `m.Plain`
(`materialize.go:38-43`) — the empty string. Result on disk: `KEY=`.

That is the current behaviour for both `?required=false` and
`--allow-missing-secrets`, and it is exactly what the chosen remedy says must
stop.

#### A3. Emptiness is NOT a usable signal — this is the load-bearing constraint

`resolveOne` short-circuits on an already-empty slot: `if ms.Plain == "" { return
ms, nil }` (`resolve.go:466-468`). So a config that deliberately writes
`[env.vars] FOO = ""` produces a byte-identical zero `MaybeSecret` to a
downgraded vault miss. If the materializer decides "omit when empty", it silently
deletes intentional empty values — a real behaviour regression with no way for
the author to opt out.

The design therefore **must** carry an explicit marker. Concrete proposal:

```go
// internal/config/maybesecret.go
// UnresolvedReason records why the resolver left this slot empty. The zero
// value (ReasonNone) means the slot was never a vault reference or resolved
// fine -- an empty Plain with ReasonNone is a deliberate empty value and is
// written as KEY= like any other.
type UnresolvedReason uint8

const (
	ReasonNone UnresolvedReason = iota
	ReasonProviderUnreachable // provider declared, backend absent/unauthenticated
	ReasonKeyNotFound         // provider answered; the key is not there
	ReasonNoValueSupplied     // declared in a *.required/*.recommended/*.optional
	                          // sub-table, no entry in the parent Values map
)

type MaybeSecret struct {
	Plain  string
	Secret secret.Value
	Token  vault.VersionToken
	Unresolved UnresolvedReason // NEW
}
```

Adding the field is safe: `MaybeSecret` decodes via `UnmarshalText`
(`maybesecret.go:61-70`), which only sets `Plain`, so no TOML shape changes.
`copyEnvVarsTable` (`override.go:1267`) copies values wholesale, so the marker
survives every merge.

`ReasonNoValueSupplied` is the persona-A case and has no `MaybeSecret` to attach
to — the key exists only in `t.Required`/`t.Recommended`/`t.Optional`, never in
`t.Values`. Two options: synthesize a marker-only `MaybeSecret` into `Values`
during the required check, or pass a separate list to the materializer.
**Recommendation: synthesize.** It puts both personas on one code path,
`collectMissing` (`required.go:111`) already computes exactly this set, and the
materializer then needs one input (the Values map) rather than two.

#### A4. Descriptions are reachable at workspace level but NOT at repo level

Descriptions live in `EnvVarsTable.Required/Recommended/Optional`
(`config.go:216-220`), `map[key]description`. `copyEnvVarsTable`
(`override.go:1267-1290`) preserves all four maps, and `MergeWorkspaceOverlay`
merges the sub-tables base-wins (`override.go:875`, `:891`).

But `MergeOverrides` — the function that builds the per-repo `EffectiveConfig`
the materializer reads — copies `ws.Env` via `copyEnv` (`override.go:72`) and
then merges **only `.Values`** from the repo override (`override.go:142-157`).
The per-repo `Required`/`Recommended`/`Optional` maps are never merged in. So
`ctx.Effective.Env.Secrets.Required` carries workspace-level descriptions only;
a `[repos.app.env.secrets.required]` description is invisible to the
materializer, while `checkRequiredKeys` sees it fine because it reads
`cfg.Repos[name]` directly (`required.go:63-71`).

This is a latent gap the annotation work has to close: extend `MergeOverrides`
to merge the three description maps repo-wins-per-key, mirroring the `.Values`
merge immediately above it.

#### A5. Rewrite is a full overwrite — comments regenerate cleanly, ordering is already sorted

`Materialize` builds `data` from scratch and calls `os.WriteFile(abs, data,
secretFileMode)` (`materialize.go:1365`). There is no read-modify-write, no
merge, no preservation of prior content. So:

- Comments do not "survive" a rewrite; they are re-derived every apply. Correct
  behaviour by construction.
- A re-apply after the secret becomes resolvable removes the comment with no
  special handling.
- Ordering is deterministic: `keys` is `sort.Strings`-sorted at
  `materialize.go:1319-1322` before the `[]KV` is built. The round-1
  nondeterminism finding is about `warnRecommended` (`required.go:147-157`, raw
  map iteration), **not** about the file writer. The file has always been sorted.

**Recommendation on placement: interleave, do not append a trailing block.**
Emit the comment at the sorted position the key would occupy. When the key
becomes resolvable the diff is a single changed line rather than a line deleted
from one block and inserted into another.

#### A6. Concrete signature

Keep `envformat` a leaf package by widening `KV` rather than `Marshal`:

```go
// internal/envformat/envformat.go
type KV struct {
	Key   string
	Value string

	// Unresolved marks a declared key niwa could not supply a value for. The
	// dotenv and shell writers emit a comment line naming the key (and its
	// Description when non-empty) instead of a KEY=value line; the json writer
	// omits the entry entirely, matching how it already omits the header.
	Unresolved  bool
	Description string
}
```

`TestMarshalDotenv_ByteCompatibleWithHistorical`
(`internal/envformat/envformat_test.go:9-21`) pins the exact bytes for a
resolved-only set; a zero-value `Unresolved` keeps that test green untouched.
Widening `Marshal`'s parameter list would break it.

#### A7. Proposed annotation text

Reuse the `# niwa:` namespace niwa already owns in `.env.example` files
(`env_example.go:145`, `extractInlineAnnotation`). No collision risk: that parser
only recognizes the marker as a *trailing* comment on a `KEY=VALUE` line
(`trailingComment`, `env_example.go:163-193`), and whole-line comments are
skipped before it ever runs (`env_example.go:82-84`).

```
# Generated by niwa - do not edit manually
API_URL=https://example.test
# niwa: unset ANTHROPIC_API_KEY - Anthropic API key for the coding agent
# niwa: unset TAVILY_API_KEY
LOG_LEVEL=debug
```

Shell format is identical (`#` is a comment there too). JSON emits nothing.

Constraint compliance: the text names the key and repeats the description the
config author wrote. It states no reason, names no config layer, and is sayable
verbatim to someone who has never heard of an overlay. "unset" is deliberately
chosen over "missing"/"unresolved" — it describes the state of the file, not a
judgement about why, and cannot be read as "something you should have had".

Do **not** put the reason in the file. `ReasonProviderUnreachable` vs
`ReasonNoValueSupplied` is diagnostic information that belongs on stderr, where
it can be phrased once with care; per-line reasons in a file that gets read by
contributors invite exactly the disclosure the constraint forbids.

#### A8. Description sanitization is a security requirement, not a nicety

Descriptions are config-author-controlled strings from TOML, and TOML supports
multi-line basic strings. A description containing a newline would inject
arbitrary lines into a generated `.local.env`:

```toml
[env.secrets.required]
FOO = """not set
EVIL=attacker-value"""
```

That forges an env var that `parseEnvFile` (`materialize.go:1438-1457`) and every
downstream dotenv consumer will read as real. The writer must strip
`\r`/`\n`/`\t`, collapse runs of whitespace, and truncate (200 chars is
reasonable — the existing required-miss error prints descriptions unbounded, but
that goes to a terminal, not a machine-parsed file). This is a genuine
injection surface that does not exist today because nothing writes descriptions
into a file.

#### A9. Consumers: one real reader, and the annotation is load-bearing for it

- **`parseEnvFile`** (`materialize.go:1438-1457`) skips blank lines and lines
  whose trimmed form starts with `#` (`:1447`). Comments are safe.
- **`readCloneEnvOutput`** (`worktree_content.go:334-367`) is the one consumer
  that matters. On the worktree path niwa re-reads the instance clone's
  already-materialized `.local.env` through `parseEnvFile` and uses the result to
  satisfy `[claude.env] promote` (`materialize.go:939-947`). Today a downgraded
  key is present as `KEY=`, so promote finds it and writes an empty value.
  **Under omission it disappears, and `materialize.go:961` becomes a hard error
  on the worktree path** — `claude.env: promoted key %q not found in resolved env
  vars`. That is a new failure introduced by requirement A, at the exact gate
  round 1 catalogued as gate 4.

  This turns the annotation from cosmetic into a wire format. Recommendation:
  teach the env-file reader to recognize `# niwa: unset <KEY>` and return the
  unresolved key set alongside the values, so the worktree path can distinguish
  "omitted because niwa could not resolve it" (skip the promote, report) from
  "named in `promote` but declared nowhere" (a typo — stays fatal). The
  annotation is then the only thing that makes the instance→worktree handoff
  lossless, which is a strong argument for the feature independent of its
  human-readability value.
- **`[env.files]` / `DiscoverEnvFiles`** (`discover.go:140`) read
  `<configDir>/env/workspace.env` and `<configDir>/env/repos/<repo>.env`, both
  under the config directory. Generated `.local.env` files live in repo working
  trees and are never inputs. No feedback loop.
- **`inheritEnvOutputs`** (`worktree_content.go:229`) byte-copies the clone file
  into the worktree (`:333-341`). Comments propagate verbatim, which is correct.
- **Claude Code** never reads `.local.env`. Promoted keys reach it through
  `.claude/settings.local.json` (`SettingsMaterializer`, `materialize.go:1004`).

#### A10. There is no `.env.example` generation to mirror

Round 1's lead pointed at "existing `.env.example` machinery". What exists is a
**reader** (`internal/workspace/env_example.go`) plus a failure-policy ladder
(`internal/config/env_example_policy.go`). niwa never writes a `.env.example`.
So requirement A duplicates nothing. What it *should* borrow is the
`# niwa:` comment namespace (A7), and what requirement B should borrow is the
`Action` enum and precedence ladder (B4).

### B. A strictness switch

#### B1. Which gates it should govern

Round 1's four gates, with a recommendation for each:

| Gate | Site | Under the new default | Governed by strict? |
|---|---|---|---|
| 1. `vault://` ref, no `[vault]` provider declared | `validate_vault_refs.go:234-239` | **stays fatal** | **No** |
| 2. `ErrProviderUnreachable` | `resolve.go:550-556` | downgrade, mark `ReasonProviderUnreachable` | **Yes** |
| 3a. required miss, provider unreachable or never supplied | `required.go:111-128` | report, continue | **Yes** |
| 3b. required miss, `ErrKeyNotFound` (provider answered) | `resolve.go:526-547` → `required.go:118` | **stays fatal** | **No** |
| 4. `[claude.env] promote` of an unresolved key | `materialize.go:961` | omit from settings, report | **Yes** |
| 4b. promote of a key declared nowhere | same site | **stays fatal** | **No** |

Gate 1 is a static authoring error with no environment dependence — the config
names a mechanism it never declared, and no runtime condition can make it valid.
Gate 3b is the "strict-when-reachable" clause from the exploration's chosen
remedy stated precisely: the backend answered and the key genuinely is not
there. Gate 4b is a typo in `promote`.

**Per-gate granularity is not needed at v1.** Gates 2, 3a, and 4 collapse into
one user-visible question: may niwa build an environment with holes in it? Three
flags for one question is worse than one. If granularity is ever wanted, the
`.env.example` per-category ladder (`env_example_policy.go:120-156`) is the
in-repo template for how to add it without redesigning.

#### B2. Relationship to `--allow-missing-secrets`: they compose, neither replaces the other

They act on disjoint conditions:

- `--allow-missing-secrets` downgrades **`ErrKeyNotFound` only**
  (`resolve.go:526-547`) — it never touches `resolve.go:550`. Round 1 established
  this; the flag's help text ("downgrade unresolved `vault://` references",
  `apply.go:24-26`) overstates it.
- The new switch governs unreachability and never-supplied, which
  `--allow-missing-secrets` cannot reach.

For a **required** key they never overlap at all: R34 already blocks
`--allow-missing-secrets` from downgrading a required miss (`required.go:39-46`,
`apply.go:1321-1327`), so gate 3b is fatal today with or without the flag, and
stays fatal under the new model. For a **non-required** key the flag's effect
changes from "write `KEY=`" to "omit and annotate" — the same downgrade, better
placed. Its name still fits.

**Recommendation: keep both, fix the help text.** Replacing
`--allow-missing-secrets` would break the one behaviour it does correctly
(letting a genuinely-absent optional key through) and would need a deprecation
cycle for no gain.

#### B3. Naming

niwa's existing boolean flags all pair a verb-ish prefix with the object they
act on: `--allow-missing-secrets`, `--allow-plaintext-secrets`, `--allow-dirty`,
`--no-install-plugins`, `--no-cascade`, `--no-worktree-delegation`,
`--no-ephemeral-sessions`, `--check-vault`, `--audit-secrets`, `--audit-auth`.
There is not one bare adjective in the set.

| Candidate | Assessment |
|---|---|
| `--strict` | Names no object and no failure. Violates round 1's prior-art discipline *and* niwa's own vocabulary — it would be the first bare adjective flag in the CLI. dotenvx does spell it this way, but dotenvx has one subject; niwa's `apply` already carries two other secret-related downgrades that `--strict` would ambiguously seem to cover. **Reject.** |
| `--strict-secrets` | Names the object. Still says nothing about which failure. Acceptable runner-up. |
| `--fail-on-unresolved-secrets` | Most precise; matches Doppler's `--no-exit-on-<failure>` discipline exactly. Long, and the negative-space naming reads awkwardly as an opt-in. |
| `--require-secrets` | Verb + object, the exact positive inverse of `--allow-missing-secrets`, the flag it must compose with. One ambiguity: readers may tie it to the `*.required` sub-table. That reading is close to correct — it *does* make declarations enforceable — so the ambiguity is benign. |

**Recommendation: `--require-secrets`**, with `--strict-secrets` as the
fallback if reviewers find the `*.required` overlap confusing. Help text:

```
--require-secrets   fail instead of continuing when a declared env key cannot
                    be resolved (an unreachable vault backend, or a key no
                    configuration layer supplies). Does not change the
                    already-fatal cases: an undeclared vault provider, or a
                    key the provider itself reports as absent.
```

Make it **tri-state**, using the existing `triBoolValue` type
(`dispatch_keepalive.go:54-74`, already used for `--keep-alive`), so
`--require-secrets=false` can force leniency against a config that sets
strictness. The one-shot-flag-overrides-config-in-both-directions pattern is
already documented at `dispatch_keepalive.go:76-84`.

#### B4. Reach: the config setting is the primary mechanism; the flag is a convenience

`realProvisionInstance` (`instance_from_hook.go:351-423`) — the single funnel for
`niwa dispatch`, the SessionStart hook, and `niwa watch` — takes no flags. But it
already loads **two** config rungs that a strictness setting could ride:

1. `config.Load(configPath)` at `instance_from_hook.go:359` → the workspace's
   own `workspace.toml`.
2. `config.LoadGlobalConfig()` at `instance_from_hook.go:394` → the host-level
   `~/.config/niwa/config.toml` `[global]` block (`registry.go:26-76`), already
   consulted here for `CloneWorkers` and `ConfigSourceURL`.

So both a project rung and a host rung reach the launch-coupled paths with no new
plumbing. **This is the answer to round 1's "the escape hatch is unreachable by
construction" finding: make the setting config-level and the reach problem
disappears.**

Proposed schema, reusing the existing `config.Action` enum
(`env_example_policy.go:9-34`) rather than inventing a bool — it already has
`UnmarshalText` validation, a `warn` default, and precedent as a severity knob:

```toml
# workspace.toml — the project rung
[workspace]
unresolved_secrets = "warn"   # or "fail"; unset means inherit

# ~/.config/niwa/config.toml — the host rung
[global]
unresolved_secrets = "fail"
```

Go:

```go
// config.go, WorkspaceMeta — sits beside ReadEnvExample / EnvExamplePolicy /
// EnvOutput, which are the other three project-scope env knobs.
UnresolvedSecrets *Action `toml:"unresolved_secrets,omitempty"`

// registry.go, GlobalSettings
UnresolvedSecrets *Action `toml:"unresolved_secrets,omitempty"`
```

#### B5. Merge order: the overlay cannot set it, and that is a feature

`config.WorkspaceOverlay` (`overlay.go:18-26`) has fields for `Sources`,
`Groups`, `Repos`, `Claude`, `Env`, `Files`, `Vault` — and **no `Workspace`
field**. A config overlay structurally cannot set anything in `[workspace]`.
Putting `unresolved_secrets` on `WorkspaceMeta` therefore means a private
overlay can never silently tighten (or loosen) the policy for a contributor who
does not have it. That is precisely the right property for this feature and
should be locked with a test asserting the overlay ignores the key.

The base/overlay merge (`MergeWorkspaceOverlay`, `override.go:708`) is
base-wins-additive for everything it does merge, so nothing changes there.

For the two rungs that *can* set it: `EffectiveEnvExamplePolicy`
(`env_example_policy.go:120-156`) puts project **above** personal. Copying that
order here would let a lenient workspace override a maintainer's host-level
`fail`, which is backwards — strictness on my own machine is my call.

**Recommendation: most-strict-wins across the rungs, with the tri-state flag as
the only one-shot override in both directions.** `fail` set anywhere wins; the
flag overrides everything. This sidesteps the ordering argument entirely, needs
no justification for inverting an existing ladder, and gives both parties what
they actually want — a project floor plus a personal ratchet.

```go
// EffectiveUnresolvedSecrets returns the action for one apply.
// flag is the tri-state --require-secrets value (nil when not passed) and wins
// in both directions; otherwise `fail` set at any rung wins; default warn.
func EffectiveUnresolvedSecrets(flag *bool, ws *WorkspaceConfig, global *GlobalSettings) Action
```

#### B6. Reporting: use the deferred-warning channel, not per-repo stderr

`EnvMaterializer.Materialize` runs once per repo, so a workspace-level unresolved
key would emit N identical warnings across an N-repo workspace. The Reporter
already has the right primitive: `DeferWarn` + `FlushDeferred`
(`reporter.go:158`, `:165`), the same pair the provider-shadow notice uses
(`apply.go:1050-1054`). Emit one deduplicated block after the materializer loop:

```
warning: 2 declared env keys could not be supplied and were left unset:
  ANTHROPIC_API_KEY - Anthropic API key for the coding agent
  TAVILY_API_KEY    - Tavily search key for the research skill
  These names are recorded as comments in the generated env files.
  Set them in your environment or re-run once the values are available.
```

Constraint-safe: names and author-written descriptions only, no reason, no
mention of any configuration layer. Note `warnRecommended` (`required.go:146-157`)
must be sorted at the same time — it iterates maps raw while the required block
immediately above it is explicitly sorted (`required.go:88-93`).

## Implications

1. **The annotation is not cosmetic — it is the instance→worktree wire format.**
   Omitting a key without annotating it converts a silent empty-value promote
   into a hard worktree failure (A9). The two requirements are coupled through
   gate 4 and cannot be planned independently.

2. **Requirement A cannot be built on "value is empty".** Without an explicit
   `UnresolvedReason` marker, omission destroys deliberate empty values (A3).
   That marker is also what lets `checkRequiredKeys` implement
   "strict-when-reachable" without plumbing vault bundles into it (B1) — one
   struct field serves both requirements.

3. **The reach problem dissolves once the setting is config-level.**
   `realProvisionInstance` already loads both rungs a policy could live on
   (B4). The flag stops being load-bearing and becomes a convenience for
   interactive `apply`/`create`.

4. **The overlay's structural inability to set `[workspace]` is a security
   property worth naming in the design** (B5): a private layer can never change
   the strictness a public contributor experiences.

5. **The blast radius is smaller than round 1 estimated.** Splitting gate 3 into
   "provider answered" vs "provider silent" means
   `TestApplyAllowMissingSecretsDoesNotDowngradeRequired` — the test round 1
   flagged as needing amendment — survives unchanged, and R34 does not need
   rewriting, only qualifying.

6. **Two adjacent bugs get pulled in as prerequisites**: `MergeOverrides`
   dropping per-repo requirement descriptions (A4), and `warnRecommended`'s
   unsorted output (B6). Neither is optional if the feature is to behave the same
   for repo-scoped and workspace-scoped declarations.

## Surprises

- **`--allow-missing-secrets` and the required check have never actually
  interacted for the persona-A case.** The flag downgrades `ErrKeyNotFound`; the
  required check fires on an empty post-resolve value. For a key with no
  `vault://` ref at all there is no resolver step, so the flag was never in the
  path. R34's careful "the flag does not downgrade required" language describes a
  collision that only occurs for vault-backed keys.

- **`MergeOverrides` silently drops per-repo `required`/`recommended`/`optional`
  descriptions** (`override.go:142-157`). Nobody noticed because the only
  consumer, `checkRequiredKeys`, bypasses `EffectiveConfig` and reads
  `cfg.Repos` directly (`required.go:63-71`). The moment a second consumer
  appears, the gap bites.

- **The JSON writer already drops the header comment** (`envformat.go:68-91`)
  while dotenv and shell emit it. The format-asymmetry question requirement A
  raises is already answered by existing behaviour.

- **`config.Action` ("warn"/"fail") is a perfect fit for the strictness setting**
  and already ships with `UnmarshalText` validation, a `warn` default, and a
  four-rung precedence resolver. The strictness feature needs almost no new
  config machinery.

- **`triBoolValue` already exists** (`dispatch_keepalive.go:54-74`) for exactly
  the "flag overrides config in both directions" semantics a strictness switch
  needs.

- **Descriptions are an injection vector the moment they touch a file** (A8).
  They are currently only ever printed to a terminal, so the hazard is entirely
  new.

## Open Questions

1. **Should `?required=false` refs be reported at all?** They are the author's
   explicit "this is fine when absent". `TestApplyVaultRequiredFalseDowngradesSilently`
   (`apply_vault_test.go:482`) pins total silence. Should they still get a
   `# niwa: unset` comment in the file (documentation value) while staying silent
   on stderr? Leaning yes — the file annotation is descriptive, the stderr line is
   a warning, and they need not have the same threshold.

2. **Does the SourceFingerprint rollup need to change?**
   `sourceForMaybeSecret` (`materialize.go:1257-1289`) currently hashes an
   unresolved key's empty plaintext into a `SourceKindPlaintext` entry
   (`sha256("")`). Omitting the key from the file but keeping the source entry
   means the transition unresolved→resolved will report `rotated <path>` on the
   next apply (`TestApplyEmitsRotatedOnVaultRotation`, `apply_vault_test.go:572`).
   That is arguably correct — the file did change — but "rotated" is the wrong
   word for "first became available". Not investigated further.

3. **What exit code should the SessionStart hook use when strictness is on and
   a key is unresolved?** Round 1 flagged Claude Code's non-zero SessionStart
   semantics as undocumented. `reconcileFailedHookCreate`
   (`session_from_hook_cmd.go:145-158`) shows the worktree hook's answer
   (reconcile then fail), but the provisioning hook has no equivalent. Still open.

4. **Should `unresolved_secrets` also be settable per-repo?** The `.env.example`
   ladder has a per-repo rung (`env_example_policy.go:124-126`). Strictness feels
   workspace-scoped (the resolver runs once, pre-merge, for the whole config),
   but a monorepo with one repo that genuinely needs a live token might want it.
   Recommendation is to omit it at v1; the ladder can grow.

5. **Does anything outside this repo parse `.local.env`?** Repo setup scripts
   (`setup_dir`) run inside the instance and could `source` or grep it. Comments
   are safe for `source` (shell format) and for any dotenv library, but a naive
   `grep KEY= .local.env | cut -d= -f2` in someone's setup script would now find
   nothing instead of an empty string. Unbounded surface; worth a release note.

## Summary

The annotation lands in one 106-line leaf package with a single call site and a
file that is already fully rewritten and key-sorted on every apply, so
idempotency and ordering come free — but it cannot key off "value is empty",
because a deliberate `FOO = ""` and a downgraded vault miss produce byte-identical
zero `MaybeSecret` values, so the resolver must carry an explicit
`UnresolvedReason` marker that also lets the required check implement
strict-when-reachable without plumbing vault bundles into it. The strictness
switch should be a `config.Action` (`"warn"`/`"fail"`) on `[workspace]` and
`[global]` rather than primarily a flag, because `realProvisionInstance` already
loads both rungs — which dissolves round 1's "the escape hatch is unreachable
from dispatch and the hook" finding — and because `WorkspaceOverlay` has no
`Workspace` field, a private layer structurally cannot change the strictness a
public contributor sees. The biggest open question is gate 4: omitting a key
instead of writing `KEY=` turns a silent empty promote into a hard worktree
failure via `readCloneEnvOutput`, which means the `# niwa: unset <KEY>` comment
has to be machine-read on the way back in, making the annotation load-bearing
rather than cosmetic.
