# Architecture Review

**Verdict:** FAIL

Three of the four prior issues are genuinely closed, but the newly written oversized-refusal paragraph specifies the opposite of R17 in its first sentence and contradicts its own next two sentences, so the one state the revision was written to add is unreachable as described.

## Prior Issues

**1. The CR/LF rule — closed.** The design now states one rule and states it once: inside a paste block, a lone carriage return and a carriage-return line-feed pair each become one line feed, and every other byte appends untouched; outside a paste block, bytes route through the gesture table. The two surfaces no longer disagree, because the table is explicitly scoped "Bytes outside a paste" — so `0x0D` submitting is a typed-input rule and cannot collide with the paste-internal normalization. The carriage-return flag now has a home: it is the cross-chunk half of the paste-internal rule (and it can only bite inside a paste, since outside one the CR has already submitted before the next chunk arrives). The PRD amendment carries it: R41 states the normalization and its "no other byte inside a pasted block SHALL be altered" bound, R10's exception list now names three exceptions including R41, R4 was widened to "a carriage return, a line feed, or both," and there is a command-level criterion for CR-only and CRLF pastes. The design's own fidelity driver was updated in lockstep — it now enumerates the same three exceptions rather than claiming unqualified byte-for-byte. The design also gives the reason for choosing normalization over normalizing at the worker, which is the choice the prior round said had to be made explicitly.

**2. R5's paste-boundary line feed — closed.** It is now the third enumerated piece of cross-chunk state, with both halves of its lifecycle stated: set when a pasted block ends on an unterminated line, flushed immediately before the next byte is appended. The design explains why the deferral is load-bearing ("Setting it at the end-of-paste marker unconditionally would give a bare paste a trailing newline it never had"), which is precisely the failure the exact-comparison criterion would catch. That is implementable as written. Three edges are left to the implementer and none of them blocks: whether a second paste following an unterminated first one flushes the break (R5 says "typed text"), whether deletion clears a pending break, and whether the flushed line feed counts against the ceiling on the append that triggers it. See non-blocking 1.

**3. R17, R18, R29 — partially closed.** R18 and R29 are closed. The refusal message's content is now specified against R18's three constraints (both byte counts, direct to file-and-reference), and the whitespace-only refusal is placed with the reason it was needed — the design correctly notes the existing check runs before the capture and compares against the empty string, so the capture path validates its own result. The single-return-value question is answered head-on and in the right place: "Crossing the ceiling is loop state, never an outcome." R17's own mechanism, however, is stated backwards — see blocking 1 and 2.

**4. R34's pre-exec re-check — closed.** The check immediately before the worker process starts is now placed, and the design says why it is not redundant (the keep-alive instruction is prepended after validation, and whether it arms depends on settings that do not exist until the instance is provisioned). The honesty about the dependency is accurate, not hedged: I verified `internal/cli/dispatch.go:81` still carries `maxPromptBytes = 128 * 1024` with no reserve and the "shorten it" wording at `:145`, so "the corrected cap has not landed, so this work establishes it" is a true statement about the tree as it stands.

## Requirement Coverage

One gap, non-blocking: **R27** is still only implied. The Security section refers to "the prompt that says how large the input is," but no pre-first-read banner is named in the rendering rule, the terminal lifecycle, or the implementation approach, and R27's criterion is specific (non-empty human-readable text before the first read, after escape sequences are stripped). It needs one sentence, not a mechanism.

Everything else has a mechanism. R13 and R31 are not named but are structurally free — the capture returns a string and two sentinels before the attach decision is reached, so `--detach` composes and the sentinels become the command's ordinary error status. R3's two-or-more-arguments error is covered only as "the arity change."

## Blocking Issues

1. **The ceiling refusal drops the input that crossed, which is the behavior R17 exists to forbid — and the paragraph contradicts itself two sentences later.** As written: "When an append would take the buffer past `limit`, the loop appends nothing, emits a refusal record ... and continues reading. A buffer over the ceiling marks the capture unsubmittable ... Deletion clears the mark once the buffer fits." If an append past `limit` appends nothing, the buffer can never be over the ceiling, so the unsubmittable mark can never be set and the deletion-clears-the-mark path is unreachable. The refusal message is self-refuting under the same reading: it names "the buffer's size," which under drop semantics is always at or below the limit, while R18 requires the size of the input. R17 requires the opposite behavior explicitly — "SHALL retain the entire buffer including the input that crossed the ceiling, so the developer can delete down to a submittable size" — the acceptance criterion pins it ("the refusal fires, the buffer still contains A and B"), the PRD spent a revision settling it, and its Decisions section rejects the discard by name: "Discarding the overflowing paste instead would satisfy the letter of 'retain the text already entered' while losing exactly what the requirement exists to save." Decision 1's sketch has it right (`wip/design_dispatch-paste-prompt_decision_1_report.md:367`: append, then `if len(c.buf) > ceiling { c.overCeiling = true; renderRefusal }`). An implementer reading the design literally builds the version that fails the stated criterion. The fix is one sentence, but it is the sentence that decides the requirement.

2. **Bounded retention does not say what happens in the case that dominates the refusal path, and the reading that matches its wording reinstates the discard.** "The buffer holds up to a small multiple of the ceiling ... input beyond that cap is refused without being retained" is ambiguous between refusing the portion above the cap (retain up to the cap, truncated) and refusing the whole append (retain nothing). The PRD says essentially everyone who sees this refusal will have pasted an entire run — its own measurements put a full CI log at about 582 KB against a 130,433-byte ceiling, roughly 4.5x, so the central case exceeds any "small multiple" cap in a single append from an empty buffer. Under the refuse-the-whole-append reading the developer loses the entire paste and has nothing to delete down, which is exactly the outcome R17 and the PRD's Decisions section rule out; under the truncate reading the buffer silently holds a partial paste, which is defensible but is never stated. The memory concern behind the cap is real and well argued in Security Considerations — the objection is not to bounding retention, it is that the bound's interaction with R17 is presented as unproblematic when in the dominant case it is the tension. State which reading applies; if it is refuse-the-whole-append, R17 needs the same kind of amendment R41 just received rather than a silent narrowing.

## Non-Blocking Observations

1. **Three edges around the pending break are left open** (second paste after an unterminated first, deletion while a break is pending, ceiling accounting for the flushed byte). All settle either way without violating a requirement; worth one clause so they are decided once rather than per implementer.

2. **An append-only transcript has no stated rendering for deletion, and the ceiling flow depends on one.** R17's recovery loop is: refuse, developer deletes, buffer becomes submittable. With an append-only transcript the display no longer matches the buffer after any deletion, so the developer cannot tell when they have deleted below the ceiling — which is the one moment R35's "see what will be sent" is doing real work rather than being a convenience. A bounded record on delete (a current-size line, say) settles it; the design says nothing.

3. **The rendering rule has a hole for large reads outside a paste block.** "Reads of 64 bytes or fewer echo verbatim; a pasted block emits a count line plus its first and last line" leaves a 5 KB read that is not inside a paste block — the ordinary case on a terminal without paste delimiters — unclassified.

4. **`ctx` is still decorative.** The core blocks in `stdin.Read`, which a context cancellation cannot interrupt without a reader goroutine the design does not describe. Nothing in the PRD requires it, and `Pick` — the idiom being mirrored — takes no context. Drop it or say it is carried for signature symmetry.

5. **A real SIGINT does not produce `ErrCanceled` and does not exit with the ordinary error status.** The handler restores and re-raises, so the process dies at 128+N; only the in-band `0x03` returns the sentinel. Consistent with R39, which scopes itself to R7 and R9, but a reader who takes signal-driven abandonment to be abandonment will read it against R31. One sentence.

6. **Ctrl-Z cannot reach the SIGTSTP handler**, because clearing ISIG makes `0x1A` a payload byte — which is the point. The suspend/resume criterion must therefore be driven by an external `kill -TSTP`, and the plan should say so or the scenario gets written against a gesture that does not exist.

7. **Rune-aware deletion over a byte buffer that admits invalid UTF-8 is unspecified.** "Remove the last rune" meets a buffer whose fidelity guarantee explicitly includes invalid UTF-8 and NUL. `utf8.DecodeLastRune` returning `(RuneError, 1)` is the right byte-wise fallback; an implementer reaching for `[]rune(string(buf))` violates R10 on the deletion path.

8. **The held-back prefix should be stated as a bounded accumulator, not a one-boundary carry.** At chunk size one a six-byte marker spans six chunks, and the abandoned-prefix path has to replay held bytes through the gesture table — one of which is `ESC`, which the table gives meaning to. Two multi-byte lookahead classes share one carry.

9. **Suspend mid-paste is still not in Consequences.** An external `kill -TSTP` with a paste in flight restores cooked mode while the remainder arrives through the line discipline, possibly consuming the terminator before SIGCONT re-arms. Inherent rather than fixable, but it belongs beside the other accepted degradations.

10. **The prior round's items 5 and 8 were absorbed correctly.** The forged paste-end marker is now a named Security Considerations case with the right blast radius (a truncated prompt, not code execution, since the argv guarantee holds), and the design's no-new-dependency claim is stated carefully enough ("the existing picker already drives raw mode with it") not to inherit the crossvalidation's incorrect claim about `SetBracketedPasteMode`.

11. **Structural fit remains right.** `internal/promptcapture` depends on stdlib plus `golang.org/x/term`; `internal/cli` depends on it; `internal/tui` and its byte-for-byte sync obligation are untouched. No cycle, no new inward dependency on `cli`. The `Read`/`read` split mirrors `Pick`/`pick` faithfully, and the one deliberate divergence — raw mode on the stdin descriptor rather than the stderr descriptor the picker raws — is correct and justified in the text.

## Summary

The revision closed the CR/LF rule with a real choice and a matching PRD amendment, gave R5's deferred break a precise set-and-flush lifecycle, placed R18 and R29, and placed R34's pre-exec re-check with an accurate account of the still-unlanded dependency. What it did not get right is the one requirement whose mechanism it was most specifically asked to write down: the oversized-refusal paragraph says the crossing append is dropped, which makes the unsubmittable state it introduces in the next sentence unreachable and fails R17's stated acceptance criterion, and the retention cap beside it never says what happens to the whole-log paste that is the only realistic way to reach the refusal at all. Both are confined to one paragraph pair in "The size ceiling in the loop" and both are fixed by stating append-then-mark and saying which half of an over-cap append survives.
