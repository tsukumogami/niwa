# PRD: enforced agent conformance

## Status

Done

## Problem Statement

niwa starts every dispatched worker at the root of a workspace instance,
the directory that holds the cloned repos. Claude Code loads project
hooks only from the settings of the directory a session was launched
in, and niwa writes its `WorktreeCreate`/`WorktreeRemove` delegation to
`niwa worktree from-hook` -- or the `EnterWorktree` deny it uses on
harnesses too old for the hook -- only into each repo's
`.claude/settings.local.json`. The instance root's
`.claude/settings.json` is generated by niwa too, and carries none of
it. Ephemeral sessions are launched at the workspace root, whose
settings niwa also writes without any worktree integration.

A root session that wants an isolated checkout therefore fails in one
of two ways. Built by hand with `git worktree add` and entered with
`EnterWorktree(path)`, it hits Claude Code's "permission-root
relocation" safety prompt, which no permission rule can pre-approve
outside bypass mode, and then fails after approval because the
session's directory isn't a git repository. Entered with
`EnterWorktree(name)` after a `cd`, it takes Claude Code's built-in git
path and makes a native `<repo>/.claude/worktrees/<name>` checkout that
niwa can't list, protect, or clean up. Even with the delegation
installed, `niwa worktree from-hook` refuses a request made from the
bare instance root, because it maps the session's directory to a repo
and the root is under none.

The evidence is on disk and in transcripts. Six dispatched instances
inspected during the investigation held only native checkouts under
`<repo>/.claude/worktrees/` and nothing under `.niwa/worktrees/`, and
across 24 recorded `EnterWorktree` calls, every path-form call made
from outside the target repo stalled on a prompt and then failed.
Operators find out when a background run sits waiting on an approval
nobody is there to give. The only fix available to them today is
another line of prose in a generated context file or in dot-niwa, and
the transcripts show agents taking the hand-built route regardless of
the guidance already present.

## Glossary

- **Workspace root**: the directory holding `.niwa/workspace.toml`
  and the instances.
- **Instance root**: the directory holding `.niwa/instance.json` and
  the `<group>/<repo>` clones.
- **Root-launched session**: a session whose launch directory is a
  workspace root or an instance root.
- **niwa worktree**: a worktree under `<instance>/.niwa/worktrees/`
  with a niwa session record.
- **Purpose**: the `purpose` field of the niwa session record.
- **Harness check**: `SupportsWorktreeHooks`, which compares
  `claude --version` against the baseline `2.1.183`; in tests it is
  stubbed to pass or fail.
- **Trusted root**: a directory whose realpath has
  `hasTrustDialogAccepted: true` in Claude Code's user config.

## Goals

- A root-launched session gets a niwa worktree of the repo its request
  names, with its working directory moved into that worktree and no
  permission prompt, in default, auto and bypass modes.
- A worktree request that can't be resolved, or a route that can't
  work from the root, fails at the call with text naming the form that
  works and the repos available.
- No rule in this feature lives in CLAUDE.md, a generated context
  file, or dot-niwa content. The facts an agent still needs arrive from
  niwa at session start and are re-delivered after compaction.
- Settings and worktree behavior for sessions launched inside a repo
  or a niwa worktree don't change.

## User Stories

- As an operator who dispatches background workers, I want a worker
  launched at the instance root to isolate its work in a niwa worktree
  without asking me anything, so that I can leave it running and find
  the work on a branch niwa tracks.
- As a developer with an interactive session at an instance root
  holding several repos, I want to name the repo when I ask for a
  worktree and end up working inside it, so that I don't have to `cd`
  first or know about settings scopes.
- As an agent that reached for `git worktree add` or passed
  `EnterWorktree` a path, I want the refusal to tell me the form that
  works and which repos exist, so that my next call succeeds.
- As an operator using ephemeral sessions provisioned at the workspace
  root, I want the same worktree behavior once the session has moved
  into its instance, so that ephemeral and dispatched work don't
  diverge.
- As an operator who opted an instance out of worktree delegation, I
  want no niwa worktree hook, guard or worktree guidance to reach that
  instance's sessions, so that the opt-out means what it says.
- As an operator whose instance roots aren't trusted by Claude Code, I
  want `niwa apply` to tell me so and what to do, so that I don't find
  out from a stalled run.
- As a niwa maintainer, I want each rule enforced by a niwa-installed
  mechanism covered by tests, so that I can remove the prose that used
  to carry it.

## Requirements

### Functional

- **R1. Delegation at the instance root.** `niwa apply` writes the
  same worktree integration it writes per repo -- `WorktreeCreate` and
  `WorktreeRemove` hooks invoking `niwa worktree from-hook`, or a
  `permissions.deny` on `EnterWorktree` and `ExitWorktree` when the
  harness check fails -- into the instance root's
  `.claude/settings.json`. The harness check runs once per apply, and
  every scope the apply writes (instance root and repos) gets the same
  choice. Per-repo settings output is otherwise unchanged.
- **R2. Delegation at the workspace root.** Every command that writes
  the workspace root's `.claude/settings.json` today (`niwa init` and
  `niwa apply`) writes the same integration into it, governed by a
  workspace-level setting that defaults to on. The file stays
  niwa-generated and is rewritten whole, as it is today.
- **R3. Opt-out.** An instance created with `--no-worktree-delegation`
  gets no worktree hooks, no deny, no guard (R8-R9), and no worktree
  sentence in its session-start context (R11), at its instance root or
  any repo. Because the workspace root is shared, a `from-hook` call
  that resolves into an opted-out instance from a workspace-root launch
  exits non-zero with a message naming the opt-out. Turning the setting
  off at workspace level removes the integration from the workspace
  root on the next apply. The workspace-level setting is a boolean in
  `workspace.toml`, named by the design, and the per-instance opt-out
  stays fixed at instance creation, as it is today. Inside an
  opted-out instance the workspace-root guard passes every call, and a
  `WorktreeRemove` from the workspace root for a worktree in that
  instance exits 0 and changes nothing. At the workspace root with no
  instance resolved, the guard refuses the R8 and R9 forms with text
  listing instance directory names in place of repos.
- **R4. Repo named in the request.** The `name` a `WorktreeCreate`
  carries is split on `/`. If its first segment exactly
  (case-sensitively) matches the name of a repo cloned in the
  session's instance, that repo is the target and the remaining
  segments, rejoined with `/`, are the request's slug. If its first two
  segments exactly match `<group>/<repo>` of a cloned repo, that repo
  is the target and the rest is the slug. Repo names are unique within
  an instance, so the one-segment form never matches two repos. A name
  whose leading segments match no repo has no prefix; its slug is the
  whole name. A prefix with an empty slug (`niwa/`) is refused with the
  R6 message. The purpose niwa records is the slug after the existing
  name sanitization.
- **R5. Resolution order.** `from-hook` picks the target repo in this
  order, stopping at the first that applies:
  1. a repo prefix in `name` (R4);
  2. the repo whose clone contains the session's directory;
  3. the only repo, when the instance has exactly one;
  4. refusal (R6).
  When the prefix and the session's directory name different repos,
  the prefix wins. A session directory inside the instance but not
  inside a repo (the instance root, a group directory, `.niwa/`) counts
  as no repo for step 2.
- **R6. Actionable refusal.** When no repo resolves, `from-hook` exits
  with a non-zero code and its stderr contains: the phrase `no repo
  selected`, every repo of the instance by name, and the example
  `<repo>/<slug>` written with the alphabetically first repo's real
  name. When the
  session's directory is inside no instance, the stderr contains
  `not inside a niwa instance` and lists up to 20 instance directory
  names under the workspace root, or says there are none.
- **R7. Remove.** A `WorktreeRemove` for a niwa worktree, sent from any
  scope that has the integration and from any directory, removes it
  when its tree has no uncommitted or untracked changes, and keeps it
  when it has any, exiting 0 in both cases, as removal does today. A
  `WorktreeRemove` for a path that isn't a niwa worktree, or no longer
  exists, exits 0 and changes nothing.
- **R8. Path-form refusal.** A niwa-installed `PreToolUse` guard,
  matched on `EnterWorktree`, refuses a call whose `path` resolves --
  after joining with the session's directory, cleaning `.`/`..`, and
  resolving symlinks -- to anything other than a directory under the
  session instance's `.niwa/worktrees/`. The refusal text contains the
  phrase `use EnterWorktree with name`, the instance's repo names and
  the `<repo>/<slug>` example. A call with `name`, or with neither
  field, passes.
- **R9. Hand-built worktree refusal.** The same guard, matched on Bash,
  refuses a command when any simple command in it -- after splitting on
  `;`, `&&`, `||`, `|` and newlines, and stripping leading `VAR=value`
  assignments and `env` -- is `git`, optionally followed by global
  options (`-C <dir>`, `-c <k=v>`, `--git-dir=<d>`, `--work-tree=<d>`),
  then `worktree add`. Separators inside single or double quotes don't
  split, and any other option before `worktree` is skipped as a global
  option. Every other command passes, including other
  `git worktree` subcommands (`list`, `move`, `remove`, `lock`,
  `unlock`, `prune`, `repair`) and text that only mentions the words.
  Strings passed to `bash -c`, `sh -c`, `eval`, command substitution and
  shell aliases are not inspected. The guard steers agents and is not
  a security boundary.
- **R10. Guard scope.** The guard is installed in the instance-root
  and workspace-root settings only. Repo-level
  `.claude/settings.local.json` and niwa-worktree settings don't get
  it.
- **R11. Session-start context.** A `SessionStart` hook in the
  instance-root settings, registered for the `startup`, `resume`,
  `clear` and `compact` sources, emits `additionalContext` containing:
  the sentence `This directory is a niwa instance root.`; a list of the
  instance's repos as `<group>/<repo>`; and, unless the instance opted
  out, the sentence `Worktrees here are created with EnterWorktree
  using a name of the form <repo>/<slug>.` The text contains no
  sentence beginning with an imperative verb. Ephemeral sessions, which
  already receive niwa's provisioning context, get the same block
  appended to it for the instance they were given.
- **R12. Prose removed.** The generated `workspace-context.md` no
  longer contains the two bullets the "Working in this workspace"
  section uses to tell agents to move into a repo before git commands
  and before making changes, and no niwa-generated CLAUDE.md contains a
  worktree instruction. R8, R9 and R11 replace them.
- **R13. Trust.** When `niwa apply` writes the integration or the guard
  to an instance root or workspace root that has no trusted root at or
  above it, it writes one warning line to stderr containing the root's
  path, the word `untrusted`, and the remedy `trust_instances = true`.
  A worker started by `niwa dispatch` runs the integration and the
  guard whenever Claude Code lets it start, without niwa changing the
  `trust_instances` setting or the user's trust config as a side
  effect. (Amended during design: Claude Code refuses to start a
  background session in a directory with no trusted ancestor and runs
  no hook source there, so a running dispatched worker is always under
  a trusted root.)

### Non-functional

- **R14. No new prompt.** In each of default, auto and bypass
  permission modes, a root-launched session's `EnterWorktree` call with
  a resolvable `name` completes with no permission prompt. A guard
  refusal (R8-R9) is a tool error, not a prompt.
- **R15. Guard cost and failure.** The guard's decision makes no
  network call and starts no subprocess. On any internal failure --
  unreadable or malformed hook input, a panic in the decision, a niwa
  binary that lacks the guard subcommand -- the call proceeds and the
  error goes to stderr; the guard never blocks Bash because of its own
  failure.
- **R16. Hook output contract.** On success `from-hook` writes exactly
  one line to stdout: the worktree's absolute path with symlinks
  resolved, no `.` or `..` segments, and a single trailing newline. All
  other output goes to stderr.
- **R17. Context size.** The R11 context is at most 2,000 characters
  for an instance of 20 repos whose `<group>/<repo>` names average 30
  characters.
- **R18. Root settings stay niwa-owned.** The additions live in the
  existing generated settings documents and go through apply's
  existing drift check, so a hand edit to one of them is reported by
  apply exactly as hand edits are today. No new file is introduced
  that the operator must maintain.

## Out of Scope

- **Changing where `niwa dispatch` starts workers.** Starting them
  inside the target repo needs a primary-repo selector, demotes sibling
  repos, and doesn't help ephemeral sessions; the root-scope fix covers
  both launch paths.
- **niwa's other repo-only default hooks at the root** (the shirabe
  PR-body and work-summary hooks). Root sessions miss them today too,
  but adding them changes behavior for every root session for a reason
  unrelated to worktrees; a follow-up can apply the same pattern.
- **Adopting, migrating or deleting native `.claude/worktrees`
  checkouts** that earlier sessions created. They stay where they are
  and niwa keeps not managing them.
- **Rewriting a path-form call into a name-form call.** Refusal with
  guidance was chosen instead (see Decisions and Trade-offs).
- **Inspecting nested shells, `eval`, aliases and command
  substitution** in the Bash guard (R9).
- **Metrics or logs of refusals** beyond the stderr text the agent and
  operator see.
- **The wider prose-to-mechanism program** (wip cleanup and references,
  edits to generated files, emoji and banned-word checks, koto
  state-aware guards). Each reuses this pattern as its own feature.
- **Changes to Claude Code, to shirabe skills, or to the koto plugin's
  hook layout.**

## Decisions and Trade-offs

- **An explicit repo prefix wins over the session's directory.** The
  prefix is what the agent asked for at the moment of the call; the
  directory may be left over from earlier work. Directory-first would
  silently create a worktree in a repo the agent didn't name. The risk
  of a wrong prefix is bounded because a prefix only counts when it
  exactly matches a cloned repo. (Closes the BRIEF's precedence
  question.)
- **Refuse rather than rewrite path-form calls.** Rewriting to `name`
  saves a turn but silently changes what the agent asked for and can
  leave a hand-built checkout next to the new one. A refusal costs one
  turn, stays visible in the transcript, and carries the guidance.
  (Closes the BRIEF's rewrite-or-refuse question.)
- **Worktree integration only, not the other repo-only hooks.** Keeps
  the change on the failure the BRIEF frames. (Closes the BRIEF's
  question about other hooks.)
- **Native checkouts are left alone.** Adopting them needs session
  records niwa never wrote; deleting them risks unpushed work. (Closes
  the BRIEF's question about native worktrees.)
- **The guard fails open.** It runs on every Bash call in a root
  session; failing closed on a stale or broken niwa binary would block
  all shell use. The `WorktreeCreate` hook stays the backstop for the
  `EnterWorktree` route.
- **The guard lives only at root scope.** Inside a repo the built-in and
  niwa paths already work, and a hand-run `git worktree add` there may
  be legitimate.
- **Workspace-root delegation, with runtime opt-out.** Ephemeral
  sessions never read instance-root settings, so the workspace root
  needs the integration too. It is shared by every instance, so a
  per-instance opt-out is honored when `from-hook` resolves the
  instance rather than by leaving the shared file out.
- **The guard parses simple commands and stops there.** Covering
  nested shells and aliases would need a shell interpreter for a
  steering aid; the `WorktreeCreate` hook and the context cover the
  common route.
- **Trust as an outcome, not a mechanism.** Claude Code skips project
  hooks in an untrusted workspace and `trust_instances` is off by
  default. R13 fixes the outcome -- dispatched workers get the hooks
  without niwa widening trust -- and leaves the delivery to the design.
